## 7. Runtime Guardrails and Production Security (11%)
## 7. Guardrail lúc chạy và bảo mật production (11%)

**What this domain tests.** Whether you can place the decisive control in the right layer: prompts shape what the model tries to do, but irreversible or high-impact actions must be gated by deterministic code, the OS, or downstream systems. You are also tested on defending agents against direct and indirect prompt injection, and on running agents with short-lived identities, minimal secrets and attributable audit logs.
**Domain này kiểm tra gì.** Bạn có đặt đúng lớp kiểm soát quyết định hay không: prompt chỉ định hướng điều model cố làm, còn hành động không thể hoàn tác hoặc tác động lớn phải được chặn bằng code xác định, OS hoặc hệ thống downstream. Domain cũng kiểm tra cách phòng thủ agent trước direct/indirect prompt injection, và cách chạy agent với danh tính ngắn hạn, ít secret và audit log truy vết được.

### [7.1] Runtime Guardrail Systems
### [7.1] Hệ thống guardrail lúc chạy

- **Core idea:** Guardrails are layers. Prompt instructions are probabilistic; hooks, permission rules, sandbox and downstream authorization are deterministic. For delete, payment, prod deploy, force-push or external email, the decisive layer must not be the model's judgment. (Interp)
- **Ý chính:** Guardrail là nhiều lớp. Chỉ dẫn trong prompt mang tính xác suất; hook, permission rule, sandbox và phân quyền downstream thì xác định. Với xóa dữ liệu, thanh toán, deploy prod, force-push, gửi email ra ngoài, lớp quyết định không được là phán đoán của model.
- **Core idea:** Input/output screening uses a small cheap model (docs use Claude Haiku 5.5) that returns a structured boolean. The same pattern applies to tool outputs before they go back as `tool_result` (if `injection_suspected` is true, return an error or stripped summary). If the screener itself returns a refusal, treat it as "harmful" (fail closed).
- **Ý chính:** Lọc input/output dùng model nhỏ, rẻ (docs dùng Claude Haiku 5.5) trả về boolean có cấu trúc. Cùng mẫu này áp dụng cho kết quả tool trước khi trả về dạng `tool_result` (nếu `injection_suspected` là true thì trả lỗi hoặc bản tóm tắt đã lọc). Nếu chính screener từ chối, coi như "harmful" (fail closed).
- **Core idea:** Evaluation order matters. Claude Code permission rules go deny → ask → allow, first match wins, so a broad deny beats a narrower allow. In the Agent SDK the order is hooks → deny rules → ask rules → permission mode → allow rules → `canUseTool`. Hence a hook deny or deny rule holds even in `bypassPermissions`, while `canUseTool` never sees auto-approved calls.
- **Ý chính:** Thứ tự đánh giá rất quan trọng. Permission rule của Claude Code đi deny → ask → allow, khớp đầu tiên quyết định, nên deny rộng thắng allow hẹp. Trong Agent SDK thứ tự là hooks → deny → ask → permission mode → allow → `canUseTool`. Vì vậy hook deny hoặc deny rule vẫn có hiệu lực kể cả trong `bypassPermissions`, còn `canUseTool` không bao giờ thấy các lời gọi đã được tự duyệt.
- **Core idea:** Text-matching rules are weaker than OS enforcement. A Bash deny rule matches the command as written and misses the same program invoked by path or inside `sh -c`; the sandbox (Seatbelt on macOS, bubblewrap on Linux/WSL2, plus a domain-allowlist proxy) is enforced by the OS on the running process regardless of what the model ran. Note non-Bash tools (Read, Edit, WebFetch, MCP, hooks) run outside the sandbox.
- **Ý chính:** Rule so khớp văn bản yếu hơn cưỡng chế ở mức OS. Deny rule cho Bash khớp lệnh "như được viết", bỏ sót cùng chương trình gọi qua đường dẫn hoặc trong `sh -c`; sandbox (Seatbelt trên macOS, bubblewrap trên Linux/WSL2, cộng proxy allowlist domain) do OS ép lên tiến trình bất kể model chạy gì. Lưu ý tool không phải Bash (Read, Edit, WebFetch, MCP, hook) chạy ngoài sandbox.
- **Core idea:** Refusals are a distinct class. A refusal is HTTP 200 with `stop_reason: "refusal"` plus `stop_details.category`; it is not an error and not a rate limit. Handle it via a fallback model, discard partial output, and never just retry the same model with backoff. Screening also has a false-positive/false-negative trade-off: tune with benign and adversarial labeled sets, strict for irreversible actions, lenient plus logging for low-risk reads. (Interp)
- **Ý chính:** Refusal là một lớp riêng. Refusal là HTTP 200 với `stop_reason: "refusal"` kèm `stop_details.category`; không phải lỗi, cũng không phải rate limit. Xử lý bằng fallback model, bỏ output dở dang, không retry cùng model với backoff. Screening còn có đánh đổi false-positive/false-negative: tinh chỉnh bằng bộ test benign và adversarial có nhãn, chặt với hành động không hoàn tác, nới + ghi log với đọc rủi ro thấp.
- **Must-know facts:** Hook exit 0 = success; exit 2 = blocking error; other codes (including exit 1 without valid JSON) are non-blocking and the action proceeds (Doc). `PreToolUse` supports `permissionDecision` allow/deny/ask/defer plus `permissionDecisionReason` (Doc). Exit 2 stays blocked even if JSON says allow; exit 0 with no output is "no decision", not approval (Doc). `continue: false` alone does not block a PreToolUse call; add `permissionDecision: "deny"` (Doc). A timed-out PreToolUse command hook does not block unless `onFailure: "block"` (Doc). The hook `if` filter is best-effort; use permissions for hard allow/deny (Doc). `PostToolUse` exit 2 only shows stderr, the tool already ran (Doc). A PreToolUse `allow` does not bypass deny or ask rules (Doc). `allowed_tools` does not constrain `bypassPermissions`; use `disallowed_tools`, or `allowedTools` with `permissionMode: "dontAsk"` for a locked-down agent (Doc). Subagents inherit `bypassPermissions`/`acceptEdits`/`auto`/`plan` from the main session (Doc). `.claudeignore` has no effect; block reads with `Read(./.env)` deny rules (Doc). `blockWritesOutsideWorkingDirectories` does not limit shell commands, MCP tools or hook programs (Doc). Sandbox escape hatch: `dangerouslyDisableSandbox` retry; disable with `allowUnsandboxedCommands: false` and set `failIfUnavailable`; `excludedCommands` run with full access (Doc). Native Windows runs unsandboxed (Doc). Refusal categories: `cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms` or null; `explanation` text is unstable, display but do not parse (Doc). `reasoning_extraction` has no recommended fallback model: change the prompt (Doc). Server-side `fallbacks: "default"` is beta, not on the Batches API, not on Haiku 5.5 (Doc). 429 `rate_limit_error`, 529 `overloaded_error`; SDK auto-retries twice with exponential backoff; refusal is outside this error family (Doc). Treating FP/FN tuning thresholds by action risk is practice, not a documented setting (Interp).
- **Kiến thức phải nhớ:** Hook exit 0 = thành công; exit 2 = lỗi chặn; mã khác (kể cả exit 1 không có JSON hợp lệ) không chặn và hành động vẫn chạy (Doc). `PreToolUse` hỗ trợ `permissionDecision` allow/deny/ask/defer cùng `permissionDecisionReason` (Doc). Exit 2 vẫn chặn dù JSON ghi allow; exit 0 không output là "không quyết định", không phải duyệt (Doc). Riêng `continue: false` không chặn PreToolUse; phải thêm `permissionDecision: "deny"` (Doc). Hook command PreToolUse hết thời gian sẽ không chặn trừ khi đặt `onFailure: "block"` (Doc). Bộ lọc `if` của hook chỉ best-effort; muốn allow/deny cứng hãy dùng permission (Doc). `PostToolUse` exit 2 chỉ hiện stderr, tool đã chạy xong (Doc). `allow` của PreToolUse không vượt được deny/ask rule (Doc). `allowed_tools` không giới hạn `bypassPermissions`; dùng `disallowed_tools`, hoặc `allowedTools` + `permissionMode: "dontAsk"` cho agent khóa chặt (Doc). Subagent kế thừa `bypassPermissions`/`acceptEdits`/`auto`/`plan` từ session chính (Doc). `.claudeignore` vô tác dụng; chặn đọc bằng deny rule `Read(./.env)` (Doc). `blockWritesOutsideWorkingDirectories` không giới hạn lệnh shell, MCP tool hay chương trình do hook chạy (Doc). Lối thoát sandbox: retry bằng `dangerouslyDisableSandbox`; tắt bằng `allowUnsandboxedCommands: false` và đặt `failIfUnavailable`; `excludedCommands` chạy với toàn quyền (Doc). Windows native chạy không sandbox (Doc). Category refusal: `cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms` hoặc null; text `explanation` không ổn định, chỉ hiển thị, đừng parse (Doc). `reasoning_extraction` không có fallback model khuyến nghị: đổi prompt (Doc). `fallbacks: "default"` phía server là beta, không có trên Batches API, không trên Haiku 5.5 (Doc). 429 `rate_limit_error`, 529 `overloaded_error`; SDK tự retry hai lần với exponential backoff; refusal không thuộc họ lỗi này (Doc). Chọn ngưỡng FP/FN theo mức rủi ro hành động là thực hành, không phải setting có tài liệu (Interp).
- **Decision rule:** When an action is irreversible, or a policy must hold even in bypass/auto-approve modes → choose a deny rule or `PreToolUse` hook exiting 2 (plus sandbox/scoped credentials) because these run before the mode check and are enforced outside the model. Trap: "strengthen the system prompt", "log and alert" (PostToolUse cannot undo), exit 1 in the hook, relying on a timeout or `if` filter, or putting the check in `canUseTool` (skipped for auto-approved calls).
- **Quy tắc quyết định:** Khi hành động không hoàn tác được, hoặc policy phải giữ cả trong chế độ bypass/auto-approve → chọn deny rule hoặc hook `PreToolUse` exit 2 (kèm sandbox/credential có phạm vi) vì chúng chạy trước kiểm tra mode và được ép ngoài model. Bẫy: "viết system prompt chặt hơn", "log và cảnh báo" (PostToolUse không hoàn tác được), exit 1 trong hook, dựa vào timeout hay bộ lọc `if`, hoặc đặt kiểm tra trong `canUseTool` (bị bỏ qua với lời gọi đã tự duyệt).
- **Decision rule:** When the model returns `stop_reason: "refusal"` → choose fallback model/middleware and discard partial output (for `reasoning_extraction`, fix the prompt) because it is not a transient error. Trap: retry with backoff as for 429/5xx; also failing open when the screener refuses.
- **Quy tắc quyết định:** Khi model trả `stop_reason: "refusal"` → chọn fallback model/middleware và bỏ output dở dang (với `reasoning_extraction` thì sửa prompt) vì đây không phải lỗi tạm thời. Bẫy: retry backoff như 429/5xx; hoặc fail-open khi screener từ chối.

### [7.2] Threat Defense and Adversarial Testing for Agentic Systems
### [7.2] Phòng thủ mối đe dọa và kiểm thử đối kháng cho hệ thống agentic

- **Core idea:** Two threat models. Jailbreak/direct injection: the user is the adversary. Indirect injection: the user is trusted but web pages, emails, documents or tool results carry hidden instructions. Scanning only user input misses the second one. (Doc)
- **Ý chính:** Hai mô hình đe dọa. Jailbreak/direct injection: người dùng là kẻ tấn công. Indirect injection: người dùng đáng tin nhưng trang web, email, tài liệu hay tool result chứa chỉ dẫn ẩn. Chỉ quét input người dùng sẽ bỏ sót loại thứ hai.
- **Core idea:** Handle untrusted content structurally: place it only in `tool_result` blocks, label its source, JSON-encode untrusted strings, state an untrusted-content policy in the system prompt, and never put your own instructions inside a tool result (send them in the next user turn). Combine with least privilege, sandboxing, narrow permissions, output screening and pre-deployment red-teaming.
- **Ý chính:** Xử lý nội dung không tin cậy bằng cấu trúc: chỉ đặt trong block `tool_result`, ghi rõ nguồn, JSON-encode chuỗi không tin cậy, nêu chính sách nội dung untrusted trong system prompt, và không đặt chỉ dẫn của mình trong tool result (gửi ở user turn kế tiếp). Kết hợp least privilege, sandbox, quyền hẹp, lọc output và red-team trước khi triển khai.
- **Core idea:** The "lethal trifecta" (private data + untrusted content + ability to communicate externally) is a third-party concept. The fix is to remove at least one leg, and cutting the exfiltration path is usually the most practical; adding a "better classifier" is not enough because filters are probabilistic.
- **Ý chính:** "Lethal trifecta" (dữ liệu riêng tư + nội dung không tin cậy + khả năng giao tiếp ra ngoài) là khái niệm của bên thứ ba. Cách sửa là bỏ ít nhất một chân, và cắt đường exfiltration thường thực tế nhất; thêm "classifier tốt hơn" là không đủ vì bộ lọc mang tính xác suất.
- **Core idea:** Red-team design: seed documents, emails and tool outputs with injections; test each trifecta leg, tool poisoning, memory persistence and exfiltration through allowed channels; measure attack success rate before/after each layer; automate as a regression eval; include humans, who outperform automated red teams on novel vectors. (Interp, anchored on Doc)
- **Ý chính:** Thiết kế red-team: gieo injection vào tài liệu, email, output tool; thử từng chân trifecta, tool poisoning, memory persistence và exfiltration qua kênh được phép; đo attack success rate trước/sau mỗi lớp; tự động hóa thành regression eval; có người tham gia vì người vượt red team tự động ở vector mới.
- **Must-know facts:** Anthropic reports adaptive-attacker success of 8.0% model-only vs 1.4% with improved safeguards on an Opus 4.5 browser-agent test, and says prompt injection is "far from a solved problem" (Doc). Repeat offenders should be throttled/banned and outputs monitored (Doc). Extra classifiers run over screenshots/page text for computer/browser use (Doc). OWASP Top 10 for LLM Apps 2025: LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM03 Supply Chain, LLM04 Data and Model Poisoning, LLM05 Improper Output Handling, LLM06 Excessive Agency, LLM07 System Prompt Leakage, LLM08 Vector and Embedding Weaknesses, LLM09 Misinformation, LLM10 Unbounded Consumption (Doc). LLM06 root causes: excessive functionality, permissions, autonomy; mitigations include avoiding open-ended tools (shell, arbitrary URL fetch), read-only DB roles, user-scoped OAuth, human approval, and complete mediation downstream rather than trusting the LLM; logging and rate limiting only limit damage (Doc). NIST AI RMF 1.0 (26 Jan 2023); Generative AI Profile NIST-AI-600-1 (26 Jul 2024) (Doc). RMF functions Govern/Map/Measure/Manage (Doc, weakly sourced). - **Kiến thức phải nhớ:** Anthropic báo cáo tỷ lệ tấn công thành công của kẻ thích ứng là 8.0% chỉ-model so với 1.4% với safeguard cải tiến trong thử nghiệm browser-agent Opus 4.5, và nói prompt injection "far from a solved problem" (Doc). - **Decision rule:** When an agent has private data, reads untrusted input and can send data out → choose to remove one trifecta leg (cut egress, drop the data, or require approval on outbound) because classifiers leave residual attack success. Trap: "add a stronger classifier", "use a bigger model", "scan user input only".
- **Quy tắc quyết định:** Khi agent có dữ liệu riêng tư, đọc input không tin cậy và gửi được dữ liệu ra ngoài → chọn bỏ một chân trifecta (cắt egress, bỏ dữ liệu, hoặc bắt duyệt khi gửi ra) vì classifier vẫn để lại xác suất tấn công thành công. Bẫy: "thêm classifier mạnh hơn", "dùng model lớn hơn", "chỉ quét input người dùng".
- **Decision rule:** When an MCP server receives a client's token and forwards it downstream → identify token passthrough and choose audience validation with a separate downstream token because tokens must be issued for the server. Trap: treating it as a logging gap; for a proxy with a static client ID and dynamic registration the answer is per-client consent. Third-party servers: trust review, managed allowlist, sandbox.
- **Quy tắc quyết định:** Khi MCP server nhận token của client rồi chuyển tiếp xuống downstream → nhận diện token passthrough và chọn audience validation với token downstream riêng vì token phải được cấp cho chính server. Bẫy: coi là thiếu log; với proxy dùng static client ID và dynamic registration thì đáp án là consent theo từng client. Server bên thứ ba: rà soát tin cậy, allowlist quản lý, sandbox.

### [7.3] Identity, Secrets, and Audit at Scale
### [7.3] Danh tính, secret và audit ở quy mô lớn

- **Core idea:** Give each workload its own named non-human identity (an Anthropic service account `svac_...`), not a shared admin key, so every action is attributable. Least privilege applies to tools too: narrow scopes, read-only DB roles, user-scoped OAuth, progressive scope elevation. (Interp, supported by Doc)
- **Ý chính:** Mỗi workload có danh tính non-human riêng có tên (service account Anthropic `svac_...`), không dùng chung admin key, để mọi hành động truy vết được. Least privilege cũng áp dụng cho tool: scope hẹp, DB role chỉ đọc, OAuth theo người dùng, nâng scope dần dần.
- **Core idea:** Workload Identity Federation (WIF) eliminates static secrets: the workload presents a signed JWT from its own IdP (AWS IAM, Google Cloud, GitHub Actions, Kubernetes, SPIFFE, Entra ID, Okta) and receives a short-lived Anthropic token, so there is nothing to mint, store in CI, rotate or leak. Rotating static keys more often is the wrong answer.
- **Ý chính:** WIF loại bỏ static secret: workload đưa JWT đã ký từ IdP của mình (AWS IAM, Google Cloud, GitHub Actions, Kubernetes, SPIFFE, Entra ID, Okta) và nhận token Anthropic ngắn hạn, nên không có gì để tạo, lưu trong CI, xoay vòng hay làm lộ. Xoay key tĩnh thường xuyên hơn là đáp án sai.
- **Core idea:** WIF is only as strong as the upstream IdP; pair it with workload identity binding, conditional access and audit logging. Audit logs should record tool calls, denials, approvals, scope elevations and auth exchanges with correlation IDs. (Doc for the IdP caveat; log contents Interp)
- **Ý chính:** WIF chỉ mạnh bằng IdP phía trên; kết hợp với workload identity binding, conditional access và audit logging. Audit log nên ghi tool call, từ chối, phê duyệt, nâng scope và trao đổi xác thực kèm correlation ID.
- **Must-know facts:** Three Console resources: federation issuer `fdis_`, service account `svac_`, federation rule `fdrl_` (Doc). A rule matches on subject prefix/audience/claims/CEL and sets OAuth scope (default `workspace:developer`) and `token_lifetime_seconds` 60-86,400, default 3,600 (Doc). Exchange is `POST /v1/oauth/token` with the RFC 7523 jwt-bearer grant, returning `sk-ant-oat01-...` (Doc). Token lifetime is the lesser of the rule lifetime and 2x remaining IdP JWT lifetime, min 60 s; SDK refresh advisory at expiry-120 s, mandatory at expiry-30 s (Doc). JWTs with `jti` are single-use by default; disabling `check_jti` removes replay protection for all rules on that issuer (Doc). Credential precedence: constructor args → `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_PROFILE` → federation env vars → active profile; a leftover API key silently overrides federation, so configure WIF in parallel, check `ant auth status`, unset then delete the key (Doc). On AWS, the request ID `x-amzn-requestid` is primary and indexed in CloudTrail, `request-id` secondary (Doc). 401 `authentication_error` = key problem; 403 `permission_error` = lacks permission (Doc). Claude Code stores credentials in macOS Keychain, or Linux file mode 0600 (Doc). Cloud sessions: GitHub credentials never enter the VM, the proxy rejects branch deletions and non-branch pushes, operations are audit-logged (Doc). Managed settings: `allowManagedPermissionRulesOnly`, `ConfigChange` hooks to audit/block mid-session changes, OpenTelemetry metrics (Doc). Specific PII-redaction products were not documented; redaction is an application-layer step outside the model (Interp; details Unverified).
- **Kiến thức phải nhớ:** Ba resource Console: federation issuer `fdis_`, service account `svac_`, federation rule `fdrl_` (Doc). Rule khớp theo subject prefix/audience/claims/CEL và đặt OAuth scope (mặc định `workspace:developer`) và `token_lifetime_seconds` 60-86.400, mặc định 3.600 (Doc). Trao đổi là `POST /v1/oauth/token` với grant jwt-bearer RFC 7523, trả `sk-ant-oat01-...` (Doc). Thời hạn token là giá trị nhỏ hơn giữa lifetime của rule và 2x thời gian còn lại của JWT IdP, tối thiểu 60 s; SDK refresh khuyến nghị ở expiry-120 s, bắt buộc ở expiry-30 s (Doc). JWT có `jti` dùng một lần theo mặc định; tắt `check_jti` làm mất chống replay cho mọi rule của issuer đó (Doc). Thứ tự ưu tiên credential: tham số constructor → `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_PROFILE` → biến môi trường federation → profile đang active; API key còn sót sẽ âm thầm đè federation, nên cấu hình WIF song song, kiểm `ant auth status`, unset rồi xóa key (Doc). Trên AWS, request ID `x-amzn-requestid` là chính và được index trong CloudTrail, `request-id` là phụ (Doc). 401 `authentication_error` = vấn đề key; 403 `permission_error` = thiếu quyền (Doc). Claude Code lưu credential ở macOS Keychain, hoặc file mode 0600 trên Linux (Doc). Cloud session: credential GitHub không vào VM, proxy từ chối xóa branch và push không phải branch, mọi thao tác được audit log (Doc). Managed settings: `allowManagedPermissionRulesOnly`, hook `ConfigChange` để audit/chặn thay đổi giữa session, metric OpenTelemetry (Doc). Sản phẩm redact PII cụ thể không có trong tài liệu; redaction là bước tầng ứng dụng ngoài model (Interp; chi tiết Unverified).
- **Decision rule:** When CI, Kubernetes or a cloud workload uses a static `ANTHROPIC_API_KEY` → choose WIF with a per-workload service account and a narrow federation rule because it removes the long-lived secret. Trap: rotating the key more often, a shared generic admin key, "WIF alone makes it secure", or ignoring a leftover `ANTHROPIC_API_KEY` that still wins in precedence.
- **Quy tắc quyết định:** Khi CI, Kubernetes hoặc workload cloud dùng `ANTHROPIC_API_KEY` tĩnh → chọn WIF với service account riêng cho từng workload và federation rule hẹp vì nó loại bỏ secret dài hạn. Bẫy: xoay key thường xuyên hơn, dùng chung admin key, "chỉ WIF là đủ an toàn", hoặc bỏ qua `ANTHROPIC_API_KEY` còn sót vẫn thắng trong thứ tự ưu tiên.

### Self-check / Tự kiểm tra

1. Q: A PreToolUse hook crashes with exit 1 while enforcing a block. Does it block? A: No; exit 1 is non-blocking, use exit 2 or deny JSON.
   Hỏi: Hook PreToolUse crash với exit 1 khi đang chặn lệnh. Có chặn không? Đáp: Không; exit 1 không chặn, dùng exit 2 hoặc JSON deny.
2. Q: In `bypassPermissions`, what still blocks a call? A: Deny rules, ask rules and hook denies, evaluated before the mode.
   Hỏi: Trong `bypassPermissions`, cái gì vẫn chặn lời gọi? Đáp: Deny rule, ask rule và hook deny, được đánh giá trước mode.
3. Q: Which SDK step is skipped for allow-rule-approved calls? A: `canUseTool`; use a PreToolUse hook instead.
   Hỏi: Bước nào của SDK bị bỏ qua với lời gọi được allow rule duyệt? Đáp: `canUseTool`; dùng hook PreToolUse thay thế.
4. Q: What is the lethal trifecta and the main fix? A: Private data + untrusted content + external communication; remove one leg, often egress.
   Hỏi: Lethal trifecta là gì và cách sửa chính? Đáp: Dữ liệu riêng tư + nội dung không tin cậy + giao tiếp ra ngoài; bỏ một chân, thường là egress.
5. Q: `stop_reason: "refusal"` (category `cyber`) on a benign task: backoff retry or fallback? A: Fallback; a refusal is not a transient error.
   Hỏi: `stop_reason: "refusal"` (category `cyber`) trên tác vụ lành tính: retry backoff hay fallback? Đáp: Fallback; refusal không phải lỗi tạm thời.
6. Q: Where does third-party email text go in the API call? A: In a `tool_result`, labeled and JSON-encoded, with an untrusted-content policy in the system prompt.
   Hỏi: Nội dung email bên thứ ba đặt ở đâu trong lời gọi API? Đáp: Trong `tool_result`, có nhãn nguồn và JSON-encode, kèm chính sách untrusted trong system prompt.
7. Q: What does MCP forbid about tokens? A: Token passthrough; servers accept only tokens issued for them (audience validation).
   Hỏi: MCP cấm gì về token? Đáp: Token passthrough; server chỉ nhận token cấp cho chính nó (audience validation).
8. Q: A WIF-migrated workload still uses the old key. Why? A: `ANTHROPIC_API_KEY` outranks federation; unset it and delete the key.
   Hỏi: Workload đã chuyển sang WIF vẫn dùng key cũ. Vì sao? Đáp: `ANTHROPIC_API_KEY` ưu tiên hơn federation; unset và xóa key.
9. Q: Which OWASP 2025 item covers an agent with shell access and a high-privilege identity? A: LLM06 Excessive Agency.
   Hỏi: Mục OWASP 2025 nào cho agent có shell và danh tính quyền cao? Đáp: LLM06 Excessive Agency.
10. Q: Why is a sandbox stronger than a Bash deny rule for blocking egress? A: The OS enforces it regardless of command text; deny rules match the command as written.
    Hỏi: Vì sao sandbox mạnh hơn Bash deny rule để chặn egress? Đáp: OS ép bất kể văn bản lệnh; deny rule chỉ khớp lệnh như được viết.

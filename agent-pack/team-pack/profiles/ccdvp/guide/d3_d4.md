## 3. Observability and Production Monitoring (12%)
## 3. Observability và giám sát production (12%)

**What this domain tests.** Whether you can instrument a production Claude system so failures, cost and quality drift can be explained after the fact, while respecting privacy limits such as zero data retention (ZDR). It also tests how you turn raw signals into SLIs, SLOs, alerts and, at high volume, into systemic findings via sampling and cohort analysis.
**Domain này kiểm tra gì.** Bạn có biết đo đạc (instrument) một hệ thống Claude production để giải thích được lỗi, chi phí và quality drift sau sự việc, mà vẫn tôn trọng giới hạn riêng tư như zero data retention (ZDR) hay không. Domain cũng kiểm tra cách biến tín hiệu thô thành SLI, SLO, alert và, ở khối lượng lớn, thành phát hiện mang tính hệ thống nhờ sampling và cohort analysis.

### [3.1] Telemetry and Instrumentation
### [3.1] Telemetry và đo đạc

- **Core idea:** Claude systems have three telemetry layers. (1) Response-level data you already receive: the `usage` object, `stop_reason`, and the `request-id` header; it is the cheapest layer, so log it on every call. (2) OpenTelemetry traces, metrics and events, from Claude Code / Agent SDK, from the Anthropic SDK plus API tracing (beta), or from your own spans. (3) Admin-side usage and cost reporting, which is organization-wide and authoritative for billing but delayed.
- **Ý chính:** Hệ thống Claude có ba lớp telemetry. (1) Dữ liệu cấp response bạn đã nhận sẵn: object `usage`, `stop_reason`, header `request-id`; rẻ nhất nên log ở mọi lần gọi. (2) Trace, metric, event OpenTelemetry từ Claude Code / Agent SDK, từ Anthropic SDK cộng API tracing (beta), hoặc span của chính app. (3) Báo cáo usage/cost phía admin: phạm vi toàn tổ chức, là nguồn chuẩn cho billing nhưng có độ trễ.

- **Core idea:** An agent loop is traced as one tree: a root span per user prompt, child spans per model request and per tool call, and subagent spans nested under the parent's tool span so a whole delegation chain is a single trace. Example: a slow run shows `llm_request` with high `ttft_ms` versus a `tool.execution` that took 40 s, which tells you which step to fix. Aggregate latency dashboards cannot localize a step.
- **Ý chính:** Vòng lặp agent được trace thành một cây: một root span cho mỗi prompt của user, child span cho mỗi model request và mỗi tool call, subagent lồng dưới tool span của cha nên cả chuỗi ủy quyền là một trace. Ví dụ: run chậm cho thấy `llm_request` có `ttft_ms` cao hay `tool.execution` mất 40 giây, từ đó biết bước nào cần sửa. Dashboard latency tổng hợp không khoanh vùng được bước.

- **Core idea:** Token and cost metrics must be split by token type (input, output, cache read, cache creation) and attributed by model, agent, skill or tool. The split is what lets you diagnose caching: `input_tokens` counts only the uncached tail after the last breakpoint, so a cost spike from lost caching shows up as cache_read falling and cache_creation rising, not as more `input_tokens`.
- **Ý chính:** Metric token và cost phải tách theo loại token (input, output, cache read, cache creation) và gán theo model, agent, skill hoặc tool. Việc tách này giúp chẩn đoán caching: `input_tokens` chỉ đếm phần chưa cache sau breakpoint cuối, nên chi phí tăng do mất cache biểu hiện bằng cache_read giảm và cache_creation tăng chứ không phải `input_tokens` tăng.

- **Core idea:** Debugging a wrong answer needs join keys. Log one structured event per API request, error, tool result and refusal, each carrying stable IDs (`request_id`, `prompt.id`, `tool_use_id`, session/conversation ID) plus retrieved chunk IDs and the stop reason. Full prompt/response capture is the strongest aid but conflicts with privacy.
- **Ý chính:** Debug một câu trả lời sai cần các khóa nối (join key). Ghi một structured event cho mỗi API request, lỗi, tool result và refusal, mang các ID ổn định (`request_id`, `prompt.id`, `tool_use_id`, session/conversation ID) cùng ID chunk đã retrieve và stop reason. Capture toàn bộ prompt/response là công cụ debug mạnh nhất nhưng xung đột với quyền riêng tư.

- **Core idea:** Under ZDR the design is "metadata always on, content gated". Structural data (timings, token counts, model, status, IDs) is safe by default; content (prompts, responses, tool I/O) is opt-in, sent only to an approved store, sampled, and kept briefly. ZDR limits what Anthropic stores, not what your own logs hold, and because Anthropic cannot replay your prompt, your telemetry is the only debugging record.
- **Ý chính:** Dưới ZDR, thiết kế là "metadata luôn bật, content có cổng kiểm soát". Dữ liệu cấu trúc (thời gian, số token, model, status, ID) an toàn mặc định; content (prompt, response, tool I/O) phải opt-in, chỉ gửi tới kho được duyệt, có sampling và lưu ngắn hạn. ZDR giới hạn việc Anthropic lưu trữ, không giới hạn log của bạn; và vì Anthropic không phát lại prompt cho bạn, telemetry của bạn là hồ sơ debug duy nhất.

- **Must-know facts:** Every response has a `request-id` header (same value as `request_id` in error bodies); SDKs expose `_request_id`; include it in support tickets (Doc). Error bodies look like `{"type":"error","error":{...},"request_id":...}` (Doc). Error types: 400 invalid_request, 401 authentication, 402 billing, 403 permission, 404 not_found, 409 conflict, 413 request_too_large, 429 rate_limit, 500 api_error, 504 timeout, 529 overloaded (Doc). An error can occur after a 200 in streaming (Doc). SDK auto-retries with exponential backoff, 2 retries by default, honoring `retry-after`, set via `max_retries` (Doc). `usage` has `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`; total input = read + creation + `input_tokens` (Doc). Both cache fields 0 with no error usually means the prompt is below the minimum cacheable length (Doc). 5-minute cache write costs 1.25x, 1-hour (`"ttl":"1h"`) 2x base input (Doc). In API OTel spans `gen_ai.usage.input_tokens` already includes cache tokens, so do not add them again (Doc). Claude Code telemetry: `CLAUDE_CODE_ENABLE_TELEMETRY=1` plus `OTEL_METRICS_EXPORTER` / `OTEL_LOGS_EXPORTER` / `OTEL_TRACES_EXPORTER`; traces are beta and also need `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`; default intervals metrics 60 s, logs 5 s, traces 5 s (Doc). Metrics include `claude_code.token.usage` with `type` input/output/cacheRead/cacheCreation and `claude_code.cost.usage` (Doc). Events: `api_request`, `api_error`, `api_refusal`, `tool_result`, `tool_decision`; joins via `prompt.id`, `request_id`, `tool_use_id` (Doc). Span tree: `claude_code.interaction` -> `claude_code.llm_request` (`ttft_ms`, `stop_reason`, `error_class`, `attempt`) and `claude_code.tool` -> `tool.blocked_on_user`, `tool.execution` (Doc). The Agent SDK emits no telemetry itself: the CLI child process exports; in TypeScript `options.env` replaces the environment (spread `process.env`), in Python it is merged; never use the `console` exporter there; export failures are silent unless `CLAUDE_CODE_OTEL_DIAG_STDERR=1` (Doc). Tag with `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES` (`enduser.id`, `tenant.id`) (Doc). OTLP config belongs in managed settings; repo `.claude/settings.json` cannot enable telemetry or content capture (Doc). Privacy gates, all off by default: `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_ASSISTANT_RESPONSES`, `OTEL_LOG_TOOL_DETAILS`, `OTEL_LOG_TOOL_CONTENT` (truncated at 60 KB), `OTEL_LOG_RAW_API_BODIES` (implies consent to all others) (Doc). Claude API tracing (beta): SDK tracing needs no permission, API tracing is a Console destination needing Admin; content modes `metadata_only` (default) and `content`, 0.75 MB per-span limit, `anthropic.content.truncated=true` on truncation (Doc). With ZDR you may still use full content for Messages API; Managed Agents are not ZDR-eligible; the destination platform applies its own retention (Doc). Span token counting: one source only, dedupe by trace ID + span ID; spans are best-effort, use the Usage and Cost Analytics API grouped by `api_key_id` for authority (Doc). ZDR orgs cannot call the API from a browser (CORS 401) (Doc). OTel GenAI conventions are status "Development" and may change; metrics include `gen_ai.server.time_to_first_token`; `gen_ai.agent.name` must be low cardinality (Doc). Exact `execute_tool` and `gen_ai.client.token.usage` attribute tables are (Unverified).
- **Kiến thức phải nhớ:** Mỗi response có header `request-id` (cùng giá trị `request_id` trong body lỗi); SDK có `_request_id`; đưa vào ticket support (Doc). Body lỗi dạng `{"type":"error","error":{...},"request_id":...}` (Doc). Loại lỗi: 400 invalid_request, 401 authentication, 402 billing, 403 permission, 404 not_found, 409 conflict, 413 request_too_large, 429 rate_limit, 500 api_error, 504 timeout, 529 overloaded (Doc). Khi streaming, lỗi có thể xảy ra sau HTTP 200 (Doc). SDK tự retry với exponential backoff, mặc định 2 lần, tôn trọng `retry-after`, chỉnh bằng `max_retries` (Doc). `usage` gồm `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`; tổng input = read + creation + `input_tokens` (Doc). Hai trường cache đều 0 mà không có lỗi thường là prompt dưới độ dài tối thiểu có thể cache (Doc). Ghi cache 5 phút giá 1.25x, 1 giờ (`"ttl":"1h"`) giá 2x giá input gốc (Doc). Trong span OTel của API, `gen_ai.usage.input_tokens` đã gồm token cache, đừng cộng lại (Doc). Telemetry Claude Code: `CLAUDE_CODE_ENABLE_TELEMETRY=1` cộng `OTEL_METRICS_EXPORTER` / `OTEL_LOGS_EXPORTER` / `OTEL_TRACES_EXPORTER`; trace là beta và cần thêm `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`; chu kỳ mặc định metrics 60 s, logs 5 s, traces 5 s (Doc). Metric gồm `claude_code.token.usage` với `type` input/output/cacheRead/cacheCreation và `claude_code.cost.usage` (Doc). Event: `api_request`, `api_error`, `api_refusal`, `tool_result`, `tool_decision`; nối bằng `prompt.id`, `request_id`, `tool_use_id` (Doc). Cây span: `claude_code.interaction` -> `claude_code.llm_request` (`ttft_ms`, `stop_reason`, `error_class`, `attempt`) và `claude_code.tool` -> `tool.blocked_on_user`, `tool.execution` (Doc). Agent SDK tự nó không phát telemetry: tiến trình con CLI export; ở TypeScript `options.env` thay thế môi trường (phải spread `process.env`), ở Python thì được merge; không dùng exporter `console` ở đây; lỗi export im lặng trừ khi đặt `CLAUDE_CODE_OTEL_DIAG_STDERR=1` (Doc). Gắn tag bằng `OTEL_SERVICE_NAME` và `OTEL_RESOURCE_ATTRIBUTES` (`enduser.id`, `tenant.id`) (Doc). Cấu hình OTLP đặt trong managed settings; `.claude/settings.json` của repo không thể bật telemetry hay content capture (Doc). Các cổng riêng tư, mặc định tắt: `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_ASSISTANT_RESPONSES`, `OTEL_LOG_TOOL_DETAILS`, `OTEL_LOG_TOOL_CONTENT` (cắt ở 60 KB), `OTEL_LOG_RAW_API_BODIES` (ngầm đồng ý mọi cổng khác) (Doc). Claude API tracing (beta): SDK tracing không cần quyền, API tracing là một destination trong Console cần Admin; chế độ content `metadata_only` (mặc định) và `content`, giới hạn 0.75 MB mỗi span, cắt thì đặt `anthropic.content.truncated=true` (Doc). Với ZDR vẫn dùng được full content cho Messages API; Managed Agents không đủ điều kiện ZDR; nền tảng đích áp dụng retention riêng (Doc). Đếm token từ span: chỉ một nguồn, dedupe theo trace ID + span ID; span là best-effort, nguồn chuẩn là Usage and Cost Analytics API nhóm theo `api_key_id` (Doc). Org ZDR không gọi API từ trình duyệt được (CORS 401) (Doc). Chuẩn OTel GenAI ở trạng thái "Development", có thể đổi; có metric `gen_ai.server.time_to_first_token`; `gen_ai.agent.name` phải low cardinality (Doc). Bảng thuộc tính chính xác của `execute_tool` và `gen_ai.client.token.usage` là (Unverified).

- **Decision rule:** When you must prove a cost spike came from lost caching → compare `cache_read_input_tokens` vs `cache_creation_input_tokens` per request (or `claude_code.token.usage` by `type`) because `input_tokens` excludes cached tokens. Trap: summing only `input_tokens` and concluding input shrank. Also: to tie a complaint to one call, search by `request-id`, not timestamps; to localize a slow step, use per-request and per-tool spans, not averages.
- **Quy tắc quyết định:** Khi phải chứng minh chi phí tăng do mất cache → so `cache_read_input_tokens` với `cache_creation_input_tokens` từng request (hoặc `claude_code.token.usage` theo `type`) vì `input_tokens` không gồm token đã cache. Bẫy: chỉ cộng `input_tokens` rồi kết luận input giảm. Thêm: gắn khiếu nại với một lần gọi thì tìm theo `request-id`, không theo timestamp; khoanh vùng bước chậm thì dùng span từng request/tool, không dùng số trung bình.

- **Decision rule:** When an org has ZDR and still wants debuggability → metadata-only spans by default, content mode only to an approved destination with short retention and access control (or sampled). Trap: "turn off all telemetry because of ZDR" (loses debuggability; ZDR is about Anthropic's storage) and "ZDR means my observability vendor keeps nothing" (it follows its own policy). For fleet-wide Claude Code telemetry, use managed settings, not repo settings.
- **Quy tắc quyết định:** Khi org có ZDR mà vẫn cần debug → span metadata-only theo mặc định, chỉ bật content tới đích được duyệt với retention ngắn và kiểm soát truy cập (hoặc sampling). Bẫy: "tắt hết telemetry vì ZDR" (mất khả năng debug; ZDR nói về nơi Anthropic lưu) và "ZDR nghĩa là vendor observability không giữ gì" (họ theo chính sách riêng). Để bật telemetry Claude Code toàn công ty, dùng managed settings, không dùng repo settings.

### [3.2] Production Monitoring and Alerting
### [3.2] Giám sát production và cảnh báo

- **Core idea:** Pick SLIs across five families for an LLM service: availability/error rate split by class (4xx, 429, 5xx/529, mid-stream errors, refusals, timeouts, tool failures, schema-invalid output); latency as TTFT and total duration at p50/p95/p99 per model; saturation (429 rate); cost per request or task; and quality (task success from sampled evals, LLM-judge or feedback, groundedness, refusal rate). Quality SLIs are the ones infrastructure monitoring misses.
- **Ý chính:** Chọn SLI từ năm nhóm cho dịch vụ LLM: availability/error rate tách theo loại (4xx, 429, 5xx/529, lỗi giữa stream, refusal, timeout, lỗi tool, output sai schema); latency gồm TTFT và tổng thời gian ở p50/p95/p99 theo model; mức bão hòa (tỷ lệ 429); chi phí mỗi request hoặc task; và chất lượng (tỷ lệ thành công từ eval lấy mẫu, LLM-judge hay feedback, groundedness, refusal rate). SLI chất lượng là thứ giám sát hạ tầng bỏ sót.

- **Core idea:** Alert on symptoms users feel (SLO burn rate), not every cause. Separate pages from tickets, and use per-error-class thresholds so a 529 spike (provider side) is not mixed with a 400 spike (your bug). Cost alerts should watch rate of change as well as absolute budget. Numeric SLO values are business choices, and error budgets can decide when to freeze changes.
- **Ý chính:** Cảnh báo theo triệu chứng user cảm nhận được (SLO burn rate), không theo từng nguyên nhân. Tách page khỏi ticket, đặt ngưỡng theo từng loại lỗi để đợt tăng 529 (phía provider) không lẫn với tăng 400 (lỗi của bạn). Alert chi phí nên theo tốc độ thay đổi chứ không chỉ ngân sách tuyệt đối. Giá trị SLO là quyết định kinh doanh, và error budget có thể quyết định khi nào đóng băng thay đổi.

- **Core idea:** Drift detection after a model or prompt update: run the same fixed canary/golden set and compare quality, refusal rate, token usage and latency to baseline; segment production metrics by `model` and release version; watch behavioral signals (`stop_reason` mix, output length, tool-call count, retry rate); and treat unusual tokens per key/workspace/user as anomalous usage (leaked key, loop, abuse).
- **Ý chính:** Phát hiện drift sau khi đổi model/prompt: chạy lại cùng bộ canary/golden cố định và so chất lượng, refusal rate, token, latency với baseline; chia metric production theo `model` và phiên bản release; theo dõi tín hiệu hành vi (cơ cấu `stop_reason`, độ dài output, số tool call, retry rate); coi lượng token bất thường theo key/workspace/user là usage bất thường (lộ key, loop, lạm dụng).

- **Core idea:** Build separate dashboards: reliability (error classes, latency), cost (tokens by type, cache hit ratio, cost by workspace/model), quality (eval scores, feedback) and agent behavior (loop length, tool failure rate). For a near-real-time cost guard, compute from per-request `usage` in your own pipeline and use the admin API only to reconcile, because admin data lags.
- **Ý chính:** Tạo dashboard riêng: độ tin cậy (loại lỗi, latency), chi phí (token theo loại, cache hit ratio, cost theo workspace/model), chất lượng (điểm eval, feedback) và hành vi agent (độ dài loop, tỷ lệ lỗi tool). Muốn cost guard gần real-time thì tính từ `usage` từng request trong pipeline của bạn, dùng admin API chỉ để đối soát vì dữ liệu admin có độ trễ.

- **Must-know facts:** Usage API granularity `1m` (default 60, max 1,440 buckets), `1h` (24/168), `1d` (7/31); groupable by API key, workspace, model, service tier, context window, `inference_geo`, `speed` (Doc). Cost API: USD, daily `1d` only; group by `workspace_id` and `description`; Priority Tier is not in the cost endpoint (use usage with `service_tier=priority`); code execution cost appears only in cost endpoint (Doc). Needs an Admin API key (`sk-ant-admin01-...`), workspace keys fail, and it is unavailable to Team plan or individual Console accounts (Doc). Endpoints `/v1/organizations/usage_report/messages` and `/v1/organizations/cost_report` are the legacy API; the Usage and Cost Analytics API is recommended for new work, with Claude Code per-user cost via `products[]=claude_code&group_by[]=actor` (Doc). Freshness claims differ: about 5 minutes on the legacy page, up to 4 hours on the OTel page; do not build real-time alerting on admin APIs (Doc for the claims, Interp for the advice). Poll at most about once per minute sustained and cache for dashboards (Doc). Playground usage has `api_key_id = null`; default workspace has `workspace_id = null` (Doc). Partner dashboards: CloudZero, Datadog, Grafana Cloud, Harness, Honeycomb, Tempo, Vantage (Doc). 429 includes ramp limits: a sharp traffic increase can 429 even under limits (Doc). Stop reasons to track: `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, `refusal`, `model_context_window_exceeded` (Doc); a rising `max_tokens` share means truncation risk and rising `refusal` means classifier/prompt issues (Interp). Claude Code spans expose `ttft_ms`, `first_content_ms`, `duration_ms`, `error_class`, `stop_reason` (Doc). `gen_ai.server.time_to_first_token` covers queue plus prefill (Doc). Rising tool-calls-per-run median as an early loop sign comes from a third-party snippet (Unverified). SLI/SLO design, drift and alert thresholds are engineering practice, not official docs (Interp).
- **Kiến thức phải nhớ:** Độ chi tiết Usage API: `1m` (mặc định 60, tối đa 1.440 bucket), `1h` (24/168), `1d` (7/31); group theo API key, workspace, model, service tier, context window, `inference_geo`, `speed` (Doc). Cost API: USD, chỉ `1d`; group theo `workspace_id` và `description`; Priority Tier không có trong cost endpoint (dùng usage với `service_tier=priority`); chi phí code execution chỉ ở cost endpoint (Doc). Cần Admin API key (`sk-ant-admin01-...`), workspace key không dùng được, và không có cho gói Team hay tài khoản Console cá nhân (Doc). Hai endpoint `/v1/organizations/usage_report/messages` và `/v1/organizations/cost_report` thuộc API legacy; Usage and Cost Analytics API được khuyên dùng cho tích hợp mới, với cost Claude Code theo user qua `products[]=claude_code&group_by[]=actor` (Doc). Thông tin độ tươi của dữ liệu khác nhau: khoảng 5 phút ở trang legacy, tới 4 giờ ở trang OTel; không xây alert real-time trên admin API (Doc cho các tuyên bố, Interp cho lời khuyên). Poll tối đa khoảng một lần mỗi phút liên tục và cache cho dashboard (Doc). Usage từ Playground có `api_key_id = null`; workspace mặc định có `workspace_id = null` (Doc). Dashboard đối tác: CloudZero, Datadog, Grafana Cloud, Harness, Honeycomb, Tempo, Vantage (Doc). 429 gồm cả ramp limit: traffic tăng vọt có thể bị 429 dù chưa chạm giới hạn (Doc). Stop reason cần theo dõi: `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, `refusal`, `model_context_window_exceeded` (Doc); `max_tokens` tăng nghĩa là rủi ro bị cắt, `refusal` tăng nghĩa là vấn đề classifier/prompt (Interp). Span Claude Code có `ttft_ms`, `first_content_ms`, `duration_ms`, `error_class`, `stop_reason` (Doc). `gen_ai.server.time_to_first_token` gồm hàng đợi cộng prefill (Doc). Median tool-call mỗi run tăng là dấu hiệu sớm của loop lấy từ đoạn trích bên thứ ba (Unverified). Thiết kế SLI/SLO, drift và ngưỡng alert là thực hành kỹ thuật, không phải tài liệu chính thức (Interp).

- **Decision rule:** When quality drops after a model switch but error rate and latency are flat → add a quality SLI and a canary eval on a fixed golden set, compared by the `model` dimension. Trap: "HTTP success is 100% so there is no regression". When spend suddenly doubles → group usage by `api_key_id`/workspace/model, then check cache read vs creation and `service_tier`/`speed`; suspect a leaked key, loop, cache invalidation or fast mode. Trap: assuming a price change.
- **Quy tắc quyết định:** Khi chất lượng giảm sau khi đổi model mà error rate và latency phẳng → thêm SLI chất lượng và canary eval trên golden set cố định, so theo chiều `model`. Bẫy: "HTTP success 100% nên không có regression". Khi chi tiêu đột ngột gấp đôi → group usage theo `api_key_id`/workspace/model, rồi kiểm tra cache read vs creation và `service_tier`/`speed`; nghi lộ key, loop, mất cache hoặc fast mode. Bẫy: cho rằng giá đổi.

- **Decision rule:** For alert routing → 529/5xx = provider side (backoff, fallback, maybe incident comms); 400 spike = your deploy (malformed request, unsupported parameter); 429 = capacity/limits (check ramp limits, spend caps); each with its own runbook (semantics Doc, runbooks Interp). Chat UI latency SLO → TTFT primary, total duration secondary. Trap: averaging total latency only, alerting on average tokens only, using a workspace key on Admin endpoints, or polling the admin API every few seconds.
- **Quy tắc quyết định:** Định tuyến alert → 529/5xx = phía provider (backoff, fallback, có thể thông báo sự cố); 400 tăng = do deploy của bạn (request sai, tham số không hỗ trợ); 429 = năng lực/giới hạn (kiểm tra ramp limit, spend cap); mỗi loại một runbook (ngữ nghĩa là Doc, runbook là Interp). SLO latency cho chat UI → TTFT là chính, tổng thời gian là phụ. Bẫy: chỉ lấy trung bình tổng latency, chỉ alert trên token trung bình, dùng workspace key với endpoint Admin, hoặc poll admin API mỗi vài giây.

### [3.3] Trace Analysis at Scale
### [3.3] Phân tích trace ở quy mô lớn

- **Core idea:** At high volume you cannot read traces one by one. Use three tools: sampling (what to keep), aggregation (metrics computed from all spans before sampling), and failure-cohort analysis (group failing traces by shared attributes and compare to the healthy population). These findings are engineering practice, with the docs supplying only the data fields (Interp).
- **Ý chính:** Ở khối lượng lớn không thể đọc từng trace. Dùng ba công cụ: sampling (giữ gì), aggregation (metric tính từ toàn bộ span trước khi sampling) và failure-cohort analysis (nhóm các trace lỗi theo thuộc tính chung rồi so với nhóm khỏe). Các phát hiện này là thực hành kỹ thuật, tài liệu chỉ cung cấp các trường dữ liệu (Interp).

- **Core idea:** Head-based sampling decides at trace start: cheap but it can miss rare failures. Tail-based sampling decides after completion: keep all errors, refusals, slow, expensive and low-score traces plus a uniform random baseline. Stratify by model/route/tenant so small cohorts are not drowned. The baseline allows reweighting so oversampled errors do not distort true rates.
- **Ý chính:** Head-based sampling quyết định ngay khi trace bắt đầu: rẻ nhưng có thể bỏ lỡ lỗi hiếm. Tail-based sampling quyết định sau khi trace kết thúc: giữ mọi lỗi, refusal, trace chậm, đắt, điểm thấp cộng một mẫu ngẫu nhiên đều làm baseline. Phân tầng theo model/route/tenant để cohort nhỏ không bị chìm. Baseline cho phép reweight để lỗi bị lấy mẫu dư không làm méo tỷ lệ thật.

- **Core idea:** Failure-cohort analysis: slice failures by model version, prompt version, tool, tenant, input-length bucket, language, retrieval source, cache hit/miss and time window, and look for an attribute whose failure rate is far above the base rate (lift). Quantify requests, share of failures and cost. Example: failures only when context exceeds N tokens, or only for tenant X, or only after deploy Y, invisible in any single trace.
- **Ý chính:** Failure-cohort analysis: cắt lỗi theo phiên bản model, phiên bản prompt, tool, tenant, nhóm độ dài input, ngôn ngữ, nguồn retrieval, cache hit/miss và khung thời gian, tìm thuộc tính có tỷ lệ lỗi cao vượt xa tỷ lệ nền (lift). Định lượng số request, phần trăm trong tổng lỗi và chi phí. Ví dụ: lỗi chỉ khi context vượt N token, chỉ với tenant X, hoặc chỉ sau deploy Y, không thấy được trong từng trace riêng lẻ.

- **Core idea:** Rollups need low-cardinality dimensions (`team`, `workspace`, model); high-cardinality IDs (user, request, session) belong on trace and log attributes for drill-down. Putting a user ID on a metric label blows up cardinality.
- **Ý chính:** Rollup cần chiều low-cardinality (`team`, `workspace`, model); ID cardinality cao (user, request, session) thuộc về thuộc tính trace và log để drill-down. Gắn user ID làm label metric sẽ làm cardinality bùng nổ.

- **Must-know facts:** Claude Code trace attributes to slice on: `model`, `speed`, `effort`, `query_source`, `attempt`, `status_code`, `error_class`, `stop_reason`, `cache_read_tokens`, `bash_command_class`, `tool_name`, `duration_ms` (Doc). Metrics carry `agent.name`, `skill.name`, `plugin.name`, `mcp_server.name`, `mcp_tool.name`; real names only with `OTEL_LOG_TOOL_DETAILS=1` (Doc). Resource attributes `service.version`, `deployment.environment`, `enduser.id`, `tenant.id` enable cohorting by release/tenant (Doc). Spans of failed/aborted requests may omit token counts, so span-derived token aggregates can under-count failures (Doc). API span export is best-effort; a caller can drop spans by clearing the sampled flag in `traceparent`; dedupe by trace ID + span ID (Doc). Managed Agents: group by `anthropic.session.id` (whole session) or `gen_ai.conversation.id` (one thread) (Doc). Claude Code traces are beta, names may change (Doc). `event.sequence` is a per-process counter, so sort by `event.timestamp` first (Doc). Content truncation: 60 KB in Claude Code, 0.75 MB per span for API tracing (Doc). Sampling and cohort methodology is practice (Interp).
- **Kiến thức phải nhớ:** Thuộc tính trace của Claude Code để cắt lát: `model`, `speed`, `effort`, `query_source`, `attempt`, `status_code`, `error_class`, `stop_reason`, `cache_read_tokens`, `bash_command_class`, `tool_name`, `duration_ms` (Doc). Metric mang `agent.name`, `skill.name`, `plugin.name`, `mcp_server.name`, `mcp_tool.name`; tên thật chỉ có khi `OTEL_LOG_TOOL_DETAILS=1` (Doc). Resource attribute `service.version`, `deployment.environment`, `enduser.id`, `tenant.id` cho phép chia cohort theo release/tenant (Doc). Span của request lỗi/bị hủy có thể thiếu số token, nên tổng token từ span có thể đếm thiếu lỗi (Doc). Export span của API là best-effort; caller có thể bỏ span bằng cách tắt cờ sampled trong `traceparent`; dedupe theo trace ID + span ID (Doc). Managed Agents: group theo `anthropic.session.id` (cả session) hoặc `gen_ai.conversation.id` (một thread) (Doc). Trace của Claude Code là beta, tên có thể đổi (Doc). `event.sequence` là bộ đếm theo từng process nên sắp theo `event.timestamp` trước (Doc). Giới hạn nội dung: 60 KB ở Claude Code, 0.75 MB mỗi span ở API tracing (Doc). Phương pháp sampling và cohort là thực hành (Interp).

- **Decision rule:** When about 1% of requests fail in a way users hate but no single trace looks abnormal → cohort analysis of the failure flag vs attributes (model, prompt version, input size, tool, tenant) and compute lift. Trap: reading more individual traces or raising the log level. When head sampling at 1% misses a 0.1% failure → switch to tail-based sampling keeping all errors/refusals/low-quality plus a random baseline. Trap: "increase retention" (traces never sampled cannot be recovered).
- **Quy tắc quyết định:** Khi khoảng 1% request lỗi theo cách user ghét nhưng không trace riêng lẻ nào trông bất thường → cohort analysis cờ lỗi so với thuộc tính (model, prompt version, kích thước input, tool, tenant) và tính lift. Bẫy: đọc thêm từng trace hoặc tăng log level. Khi head sampling 1% bỏ lỡ lỗi 0.1% → chuyển sang tail-based sampling giữ mọi lỗi/refusal/chất lượng thấp cộng baseline ngẫu nhiên. Bẫy: "tăng retention" (trace chưa từng được lấy mẫu thì không thể khôi phục).

- **Decision rule:** When error traces are oversampled and you need the true error rate → use pre-sampling metrics or reweight by sampling probability. Trap: reporting error share from the biased sample. For team cost attribution → low-cardinality `team`/`workspace` on metrics, per-user detail in logs/traces. Trap: user ID as a metric label, storing 100% of full content "to be safe", or summing both SDK and API spans for tokens.
- **Quy tắc quyết định:** Khi trace lỗi bị lấy mẫu dư mà cần tỷ lệ lỗi thật → dùng metric trước sampling hoặc reweight theo xác suất lấy mẫu. Bẫy: báo tỷ lệ lỗi từ mẫu bị lệch. Với phân bổ chi phí theo team → `team`/`workspace` low-cardinality trên metric, chi tiết từng user ở log/trace. Bẫy: user ID làm label metric, lưu 100% content "cho chắc", hoặc cộng cả span SDK lẫn API khi đếm token.

## 4. Advanced Debugging and Incident Response (10%)
## 4. Debug nâng cao và ứng phó sự cố (10%)

**What this domain tests.** Whether you can look at evidence from a messy production failure (multi-turn, multi-agent, non-deterministic, refusals, bad retrieval) and isolate whether the origin is the model output, the agent harness, the tools or the data. It also tests picking the right incident action (mitigate first, roll back, communicate) and closing the loop with regression evals, monitoring and a postmortem.
**Domain này kiểm tra gì.** Bạn có nhìn vào bằng chứng của một lỗi production rối rắm (multi-turn, multi-agent, non-deterministic, refusal, retrieval sai) và xác định nguồn gốc nằm ở output của model, agent harness, tool hay dữ liệu hay không. Domain cũng kiểm tra việc chọn đúng hành động ứng phó (giảm thiểu trước, rollback, truyền thông) và khép vòng lặp bằng regression eval, monitoring và postmortem.

### [4.1] Complex Failure Diagnosis
### [4.1] Chẩn đoán lỗi phức tạp

- **Core idea:** Use four origin buckets. Model output (wrong reasoning, hallucination, format drift, refusal); agent harness (prompt assembly, context truncation, loop control, retry logic, tool-result handling, orchestration); tools (bad schema, wrong or failed results, timeouts, permission denials); data (stale, missing or corrupt knowledge, wrong chunks retrieved, bad inputs). Diagnose by gathering evidence (trace, request/response, tool I/O, retrieved context) and isolating by controlled replay: hold three constant, vary one.
- **Ý chính:** Dùng bốn nhóm nguồn gốc. Output của model (suy luận sai, hallucination, lệch format, refusal); agent harness (ghép prompt, cắt context, điều khiển loop, logic retry, xử lý tool result, orchestration); tool (schema xấu, kết quả sai hoặc lỗi, timeout, bị từ chối quyền); dữ liệu (kiến thức cũ, thiếu, hỏng, retrieve sai chunk, input xấu). Chẩn đoán bằng cách thu bằng chứng (trace, request/response, tool I/O, context đã retrieve) và cô lập qua replay có kiểm soát: giữ cố định ba yếu tố, đổi một.

- **Core idea:** Isolation techniques: replay the exact captured request to the model; inject a recorded tool result to test the harness; run the tool directly with captured args; inspect retrieved chunks before generation; compare a passing and failing trace to find the first divergence. These techniques are practice (Interp). Example: the agent confidently continued after a tool returned garbage. Replaying with that recorded result proves it is a harness/tool error-handling gap, not a "hallucination".
- **Ý chính:** Kỹ thuật cô lập: replay đúng request đã capture lên model; chèn tool result đã ghi để kiểm tra harness; chạy trực tiếp tool với tham số đã capture; xem chunk retrieve trước khi generate; so trace đạt với trace lỗi để tìm điểm rẽ nhánh đầu tiên. Các kỹ thuật này là thực hành (Interp). Ví dụ: agent tự tin đi tiếp sau khi tool trả rác. Replay với kết quả đã ghi chứng minh đó là lỗ hổng xử lý lỗi ở harness/tool, không phải "hallucination".

- **Core idea:** Multi-turn and multi-agent failures accumulate. In multi-turn, an early wrong tool result is carried forward, or truncation/compaction drops a constraint; find the first bad turn and inspect what the harness actually sent each turn. In multi-agent, a handoff loses information, a subagent returns a summary without evidence, parallel agents conflict, or the orchestrator swallows an error; use the trace tree to find the first span that diverged.
- **Ý chính:** Lỗi multi-turn và multi-agent tích lũy dần. Ở multi-turn, một tool result sai từ sớm bị mang đi tiếp, hoặc truncation/compaction làm rơi một ràng buộc; hãy tìm turn sai đầu tiên và xem harness thực sự gửi gì ở mỗi turn. Ở multi-agent, handoff làm mất thông tin, subagent trả tóm tắt thiếu bằng chứng, các agent song song xung đột, hoặc orchestrator nuốt lỗi; dùng cây trace để tìm span đầu tiên bị lệch.

- **Core idea:** Non-deterministic failures are rates, not yes/no bugs. Capture the failing request, run N repeats to estimate the failure rate, then hunt variance sources (sampling, tool latency or ordering, retrieval ties, races between parallel tool calls, cache state). Prove a fix with a pass-rate target over many runs, not one green run.
- **Ý chính:** Lỗi non-deterministic là một tỷ lệ, không phải bug có/không. Capture request lỗi, chạy lặp N lần để ước lượng tỷ lệ lỗi, rồi tìm nguồn biến thiên (sampling, độ trễ hoặc thứ tự tool, hòa điểm retrieval, race giữa các tool call song song, trạng thái cache). Chứng minh bản sửa bằng mục tiêu pass-rate qua nhiều lần chạy, không phải một lần xanh.

- **Core idea:** Refusals are a failure class. They arrive as HTTP 200 with `stop_reason: "refusal"` from safety classifiers, not as an error, so a harness that only checks status or reads `content[0].text` sees an empty or odd answer. Retrieval-grounding failures are diagnosed by stage: is the document in the corpus, did chunking/embedding retrieve it, did reranking keep it, was it in the prompt, did the model use it faithfully. If the evidence was never retrieved, it is a data/retrieval problem.
- **Ý chính:** Refusal là một lớp lỗi. Chúng đến dưới dạng HTTP 200 với `stop_reason: "refusal"` từ classifier an toàn, không phải lỗi, nên harness chỉ kiểm tra status hay đọc `content[0].text` sẽ thấy câu trả lời rỗng hoặc lạ. Lỗi retrieval-grounding được chẩn đoán theo tầng: tài liệu có trong corpus không, chunking/embedding có retrieve được không, reranking có giữ không, có nằm trong prompt không, model có dùng trung thực không. Nếu bằng chứng chưa từng được retrieve thì đó là vấn đề data/retrieval.

- **Must-know facts:** Refusal is HTTP 200; check `stop_reason` on the success path; `stop_details` is `null` for other stop reasons; `category`/`explanation` are `null` if no named category (Doc). Categories: `cyber`, `bio`, `frontier_llm`, `general_harms`, plus `reasoning_extraction` named in the billing section; benign work can trigger them (Doc). Handling: retry on a fallback model; server-side `fallbacks: "default"` with beta header `server-side-fallback-2026-07-01`, or up to three named fallback models; a `fallback` content block marks the handoff; if the fallback is rate-limited/overloaded the refusal returns with `stop_details.recommended_model`; Haiku 5.5 has no server-side fallback (Doc). Refusals before any output are billed only for `bio`, `frontier_llm`, `reasoning_extraction` (as of Sept 2026 per doc); mid-stream refusals bill input plus streamed output (Doc). Claude Code emits `claude_code.api_refusal` with `category` (Doc). Other harness-visible stops: `max_tokens` (truncated), `pause_turn` (server-tool loop hit its default 10-iteration limit; send assistant content back unchanged), `model_context_window_exceeded` (Doc). Common 400 harness bugs: assistant prefill rejected on Claude 4.6+; modifying `thinking`/`redacted_thinking` blocks in the latest assistant message (must be returned exactly, including empty ones); `thinking.type.enabled` rejected on Claude 4.7+ (use adaptive + `output_config.effort`); forced `tool_choice` any/tool unsupported on some models; a thinking block "bound to a different conversation" when history was edited (keep history append-only) (Doc). Sonnet 5.5 cannot use `thinking: disabled` (use `between_tools`); `between_tools` with `xhigh`/`max` effort or per-message effort changes returns 400 (Doc). `request_too_large` 413 limits: Messages 128 MB, Batch 256 MB, Files 500 MB (Doc). Caching bugs: timestamps in a cached block, changed `tool_choice`, unstable JSON key order, parallel requests before the first response (Doc). Claude Code tool diagnostics: `tool.execution` `success`/`error_class`; `tool_result` `error_type`/`success`/`duration_ms`; `tool_decision` reject sources (config, hook, user_reject) (Doc). Thinking `summarized` display shows reasoning summaries; thinking content in OTel raw bodies is redacted (Doc). Bucket model, replay and stage-by-stage retrieval checks are practice (Interp).
- **Kiến thức phải nhớ:** Refusal là HTTP 200; kiểm tra `stop_reason` ở đường thành công; `stop_details` là `null` với stop reason khác; `category`/`explanation` là `null` nếu không có category cụ thể (Doc). Category: `cyber`, `bio`, `frontier_llm`, `general_harms`, thêm `reasoning_extraction` xuất hiện ở phần billing; việc vô hại vẫn có thể bị kích hoạt (Doc). Xử lý: retry trên model fallback; server-side `fallbacks: "default"` với beta header `server-side-fallback-2026-07-01`, hoặc tối đa ba model fallback đặt tên; content block `fallback` đánh dấu chỗ chuyển giao; nếu fallback bị rate limit/quá tải thì refusal được trả về kèm `stop_details.recommended_model`; Haiku 5.5 không có server-side fallback (Doc). Refusal trước khi có output chỉ tính phí với `bio`, `frontier_llm`, `reasoning_extraction` (tính đến Sept 2026 theo doc); refusal giữa stream tính phí input cộng output đã stream (Doc). Claude Code phát `claude_code.api_refusal` kèm `category` (Doc). Các stop khác harness thấy được: `max_tokens` (bị cắt), `pause_turn` (vòng lặp server-tool chạm giới hạn mặc định 10 lần; gửi lại assistant content nguyên vẹn), `model_context_window_exceeded` (Doc). Lỗi 400 phổ biến do harness: assistant prefill bị từ chối trên Claude 4.6+; sửa block `thinking`/`redacted_thinking` trong tin assistant mới nhất (phải trả lại y nguyên, kể cả block rỗng); `thinking.type.enabled` bị từ chối trên Claude 4.7+ (dùng adaptive + `output_config.effort`); `tool_choice` ép any/tool không hỗ trợ ở vài model; thinking block "bound to a different conversation" khi history bị sửa (giữ history chỉ-thêm) (Doc). Sonnet 5.5 không dùng được `thinking: disabled` (dùng `between_tools`); `between_tools` với effort `xhigh`/`max` hoặc đổi effort theo từng message trả 400 (Doc). Giới hạn `request_too_large` 413: Messages 128 MB, Batch 256 MB, Files 500 MB (Doc). Lỗi caching: timestamp trong block được cache, đổi `tool_choice`, thứ tự key JSON không ổn định, gửi song song trước khi có response đầu (Doc). Chẩn đoán tool ở Claude Code: `tool.execution` `success`/`error_class`; `tool_result` `error_type`/`success`/`duration_ms`; nguồn reject của `tool_decision` (config, hook, user_reject) (Doc). Hiển thị thinking `summarized` cho xem tóm tắt suy luận; nội dung thinking trong raw body OTel bị redact (Doc). Mô hình bốn bucket, replay và kiểm tra retrieval theo tầng là thực hành (Interp).

- **Decision rule:** When the final answer is wrong and retrieved chunks lack the fact → fix retrieval/data (chunking, query rewrite, hybrid search, reranking, corpus coverage) because the model never saw the evidence. Trap: blaming the model or tweaking the prompt. If chunks contain the fact but the answer ignores it → grounding/generation fix (citation, uncertainty instruction, chunk placement). Trap: re-indexing. If a tool returned garbage and the agent proceeded → harness/tool error handling; prove by replaying the recorded result. Trap: "model hallucinated".
- **Quy tắc quyết định:** Khi câu trả lời cuối sai và chunk retrieve không chứa sự kiện → sửa retrieval/data (chunking, viết lại query, hybrid search, reranking, độ phủ corpus) vì model chưa từng thấy bằng chứng. Bẫy: đổ cho model hoặc chỉnh prompt. Nếu chunk có sự kiện mà câu trả lời lờ đi → sửa grounding/generation (citation, chỉ dẫn nêu bất định, vị trí chunk). Bẫy: re-index. Nếu tool trả rác mà agent vẫn đi tiếp → lỗi xử lý lỗi của harness/tool; chứng minh bằng replay kết quả đã ghi. Bẫy: "model bị hallucinate".

- **Decision rule:** When output is empty or odd with HTTP 200 → check `stop_reason`: `refusal` (inspect category, use a fallback model or adjust the request, do not retry the same model repeatedly), `max_tokens` (truncation), `pause_turn` (continue). Trap: treating it as transient and retrying with backoff. For "works in playground, fails in production" → diff the assembled request (system prompt, tools, history, truncation, parameters) captured by request body/`request-id`. Trap: tuning the prompt before diffing. Many 400s after a model migration → check unsupported params (prefill, thinking mode, forced `tool_choice`) first.
- **Quy tắc quyết định:** Khi output rỗng/lạ với HTTP 200 → kiểm tra `stop_reason`: `refusal` (xem category, dùng model fallback hoặc chỉnh request, không retry lặp lại cùng model), `max_tokens` (bị cắt), `pause_turn` (tiếp tục). Bẫy: coi là lỗi tạm thời và retry với backoff. Với "chạy được trong playground, lỗi ở production" → so sánh request đã lắp ghép (system prompt, tool, history, truncation, tham số) lấy từ request body/`request-id`. Bẫy: chỉnh prompt trước khi so sánh. Nhiều 400 sau khi migrate model → kiểm tra tham số không hỗ trợ (prefill, thinking mode, `tool_choice` ép buộc) trước tiên.

- **Decision rule:** For intermittent failures or multi-turn drift → measure failure rate across repeated runs and cohorts, and locate the first bad turn or first diverging span (including swallowed subagent errors and incomplete handoffs). Trap: closing on a single success, debugging only the last turn or only the final agent. Distractors: "increase temperature/add retries" for systematic errors, and "switch to a larger model" before isolating the origin.
- **Quy tắc quyết định:** Với lỗi chập chờn hoặc drift nhiều turn → đo tỷ lệ lỗi qua nhiều lần chạy và theo cohort, rồi tìm turn sai đầu tiên hoặc span lệch đầu tiên (gồm lỗi subagent bị nuốt và handoff thiếu). Bẫy: kết luận sau một lần chạy thành công, chỉ debug turn cuối hoặc chỉ agent cuối. Mồi nhử: "tăng temperature/thêm retry" cho lỗi có hệ thống, và "chuyển sang model lớn hơn" trước khi cô lập nguồn gốc.

### [4.2] Incident Response and Learning Loops
### [4.2] Ứng phó sự cố và vòng lặp học hỏi

- **Core idea:** Triage first: confirm and size impact (who, how many, which model/route/tenant, since when), classify the type (provider outage, your deploy, quality regression, cost runaway, safety/privacy incident), set severity and assign roles (commander, comms, ops). Check provider status for 5xx/529 patterns and ask "what changed" (deploy, prompt, model version, config, index update). These steps are practice (Interp); the provider status page itself was not fetched (Unverified).
- **Ý chính:** Triage trước: xác nhận và đo quy mô ảnh hưởng (ai, bao nhiêu, model/route/tenant nào, từ khi nào), phân loại (sự cố provider, deploy của bạn, quality regression, chi phí vượt kiểm soát, sự cố an toàn/riêng tư), đặt mức nghiêm trọng và phân vai (commander, comms, ops). Kiểm tra trạng thái provider với mẫu 5xx/529 và hỏi "cái gì đã đổi" (deploy, prompt, phiên bản model, config, cập nhật index). Các bước này là thực hành (Interp); trang status của provider chưa được đọc (Unverified).

- **Core idea:** Mitigate before root cause. Take the least risky reversible action: roll back the last change (prompt, model, config, index), fail over to a fallback model, degrade gracefully (cached or simple answers, disable a feature or tool), shed load, use a kill switch for runaway loops or cost, or pause a bad batch job. Rollback works best when prompts, tool definitions, model IDs and retrieval config are versioned and revertible independently; pinning model versions gives you control over when behavior changes. Verify recovery with the same SLIs and a canary eval (Interp).
- **Ý chính:** Giảm thiểu trước, tìm nguyên nhân gốc sau. Chọn hành động ít rủi ro nhất và đảo ngược được: rollback thay đổi cuối (prompt, model, config, index), failover sang model dự phòng, suy giảm có kiểm soát (trả lời cache hoặc đơn giản, tắt một tính năng hay tool), giảm tải, dùng kill switch cho loop/chi phí chạy mất kiểm soát, hoặc tạm dừng batch job lỗi. Rollback hiệu quả nhất khi prompt, định nghĩa tool, model ID và cấu hình retrieval được version hóa và hoàn tác độc lập; pin phiên bản model giúp bạn kiểm soát lúc hành vi thay đổi. Xác nhận phục hồi bằng cùng các SLI và một canary eval (Interp).

- **Core idea:** Communicate with a regular cadence and honest scope: impact, what you are doing, next update time; do not speculate on root cause publicly. For provider-side outages include request IDs for support; for data/privacy incidents involve security/legal (Interp).
- **Ý chính:** Truyền thông theo nhịp đều và phạm vi trung thực: ảnh hưởng, đang làm gì, lúc nào cập nhật tiếp; không suy đoán công khai về nguyên nhân gốc. Với sự cố phía provider, kèm request ID cho support; với sự cố dữ liệu/riêng tư, huy động security/legal (Interp).

- **Core idea:** Close the learning loop. After mitigation, produce (1) a blameless postmortem (impact, timeline, mitigation, root and contributing causes, follow-ups), (2) regression eval case(s) with the failing input and expected behavior added to the golden suite and CI gate, (3) monitoring coverage (the SLI/alert that would have caught it sooner), and (4) systemic fixes (runbook, guardrail, canary/staged rollout). A hotfix without these will recur.
- **Ý chính:** Khép vòng lặp học hỏi. Sau khi giảm thiểu, tạo ra (1) postmortem không đổ lỗi (ảnh hưởng, timeline, giảm thiểu, nguyên nhân gốc và đóng góp, việc theo dõi), (2) regression eval case gồm input lỗi và hành vi mong đợi, thêm vào golden suite và CI gate, (3) độ phủ monitoring (SLI/alert giúp phát hiện sớm hơn) và (4) sửa mang tính hệ thống (runbook, guardrail, canary/staged rollout). Hotfix thiếu các thứ này sẽ tái diễn.

- **Must-know facts:** Blameless postmortem principles (focus on systems not people; written record of impact, mitigation, root causes, follow-ups; triggers such as user-visible degradation, data loss, on-call intervention like rollback, long resolution time, or monitoring failure; action items are the point) come from the Google SRE book, a third-party supplement (Doc). Error semantics for triage: 529 `overloaded_error` can arise from high traffic across all users; 500 `api_error` means retry with exponential backoff then contact support with the request ID; 429 includes a tier spend cap (no `retry-after`, persists until access resumes) and ramp limits; 402 `billing_error`; a spend limit you set returns 400 when reached (Doc). SDK default 2 retries with backoff honoring `retry-after` (Doc); retry amplification under overload is a risk (Interp). Server-side refusal `fallbacks` can reroute declined requests, but an overloaded fallback returns the refusal, so size fallback capacity (Doc). Your workspace spend limit works as a cost-runaway circuit breaker (Doc for 400 behavior, Interp for the use). Postmortem data: `request-id`, OTel traces (`session.id`, `prompt.id`), usage/cost by key/workspace/model (Doc). Claude Code/Agent SDK events (`tool_decision`, `tool_result`, `mcp_server_connection`) can feed a SIEM as an audit trail for security incidents (Doc). Leaked-key investigation: Usage and Cost Analytics API grouped by `api_key_id` (Doc). Anthropic status/incident feeds and incident-comms guidance are (Unverified).
- **Kiến thức phải nhớ:** Nguyên tắc postmortem không đổ lỗi (tập trung hệ thống không phải con người; hồ sơ viết về ảnh hưởng, giảm thiểu, nguyên nhân gốc, việc theo dõi; điều kiện kích hoạt như suy giảm user thấy được, mất dữ liệu, can thiệp on-call như rollback, thời gian xử lý dài, hay monitoring thất bại; action item là trọng tâm) lấy từ sách Google SRE, nguồn bên thứ ba bổ trợ (Doc). Ngữ nghĩa lỗi cho triage: 529 `overloaded_error` có thể do lưu lượng cao toàn bộ user; 500 `api_error` thì retry exponential backoff rồi liên hệ support kèm request ID; 429 gồm tier spend cap (không có `retry-after`, kéo dài đến khi được cấp lại quyền truy cập) và ramp limit; 402 `billing_error`; spend limit do bạn đặt trả 400 khi chạm (Doc). SDK mặc định 2 retry với backoff tôn trọng `retry-after` (Doc); retry khuếch đại khi quá tải là rủi ro (Interp). `fallbacks` phía server cho refusal có thể chuyển hướng request bị từ chối, nhưng fallback quá tải thì refusal được trả về, nên phải tính dung lượng fallback (Doc). Spend limit của workspace đóng vai circuit breaker chống chi phí mất kiểm soát (Doc cho hành vi 400, Interp cho cách dùng). Dữ liệu cho postmortem: `request-id`, trace OTel (`session.id`, `prompt.id`), usage/cost theo key/workspace/model (Doc). Event của Claude Code/Agent SDK (`tool_decision`, `tool_result`, `mcp_server_connection`) có thể đưa vào SIEM làm audit trail cho sự cố bảo mật (Doc). Điều tra lộ key: Usage and Cost Analytics API nhóm theo `api_key_id` (Doc). Feed status/sự cố của Anthropic và hướng dẫn truyền thông sự cố là (Unverified).

- **Decision rule:** When a quality regression follows a deploy that changed prompt or model → roll back that single change first (fast, reversible), then investigate with replay and cohort analysis, because users are still being hurt. Trap: debugging live, rolling forward with an unverified fix, or root-cause-first before mitigation. For a provider-side 529/5xx spike with nothing changed on your side → backoff with jitter, fail over to an alternate model/path, degrade gracefully, notify users, open a ticket with request IDs. Trap: removing retries, hammering retries, or rolling back unrelated code.
- **Quy tắc quyết định:** Khi quality regression xuất hiện ngay sau deploy đổi prompt hoặc model → rollback đúng thay đổi đó trước (nhanh, đảo ngược được), rồi mới điều tra bằng replay và cohort analysis, vì user vẫn đang bị ảnh hưởng. Bẫy: debug trực tiếp, roll forward bằng bản sửa chưa kiểm chứng, hoặc tìm nguyên nhân gốc trước khi giảm thiểu. Với đợt tăng 529/5xx phía provider mà bên bạn không đổi gì → backoff có jitter, failover sang model/đường khác, suy giảm có kiểm soát, thông báo user, mở ticket kèm request ID. Bẫy: bỏ retry, retry dồn dập, hoặc rollback code không liên quan.

- **Decision rule:** For a cost runaway from an agent loop → kill switch or iteration cap, then workspace spend limit; identify via tool-call counts and tokens per task. Trap: waiting for next day's cost report (admin data is delayed). For a refusal surge after a new feature → add refusal handling and a fallback model, compare categories; do not retry the same model. For a model update that changed behavior → canary eval pinned old vs new, roll back to the pinned version while fixing prompts.
- **Quy tắc quyết định:** Với chi phí vượt kiểm soát do loop của agent → kill switch hoặc giới hạn số vòng, rồi spend limit của workspace; nhận diện qua số tool call và token mỗi task. Bẫy: chờ báo cáo chi phí ngày hôm sau (dữ liệu admin bị trễ). Với đợt refusal tăng sau tính năng mới → thêm xử lý refusal và model fallback, so sánh category; không retry cùng model. Với model update làm đổi hành vi → canary eval so phiên bản pin cũ và mới, rollback về phiên bản pin trong lúc sửa prompt.

- **Decision rule:** When the incident is resolved → the best answer closes the loop: regression eval into the CI gate, new alert/SLI or dashboard if detection was late, runbook update, owner and date on every action item. Trap: action items like "be more careful" or naming a person as the cause; distractors "restart the service" with no evidence, "ask the model to be more careful" as the only fix, and "disable observability to reduce load".
- **Quy tắc quyết định:** Khi sự cố đã xử lý xong → đáp án tốt nhất là khép vòng lặp: regression eval vào CI gate, alert/SLI hoặc dashboard mới nếu phát hiện muộn, cập nhật runbook, mỗi action item có owner và ngày. Bẫy: action item kiểu "cẩn thận hơn" hoặc nêu tên một người là nguyên nhân; mồi nhử "restart service" không có bằng chứng, "bảo model cẩn thận hơn" là cách sửa duy nhất, và "tắt observability để giảm tải".

### Self-check / Tự kiểm tra

1. Q: HTTP status and field of a classifier refusal? A: 200 with `stop_reason: "refusal"`; the policy area is in `stop_details.category` (may be null).
   Hỏi: HTTP status và trường của refusal do classifier? Đáp: 200 với `stop_reason: "refusal"`; lĩnh vực chính sách nằm ở `stop_details.category` (có thể null).
2. Q: Retrieved docs lack the answer; which origin bucket? A: Data/retrieval.
   Hỏi: Tài liệu retrieve không có đáp án; thuộc nhóm nguồn gốc nào? Đáp: Data/retrieval.
3. Q: First step for "works in playground, fails in prod"? A: Diff the actual assembled request and replay it.
   Hỏi: Bước đầu cho "chạy ở playground, lỗi ở prod"? Đáp: So sánh request thực tế đã lắp ghép và replay nó.
4. Q: How do you verify a fix for a 5% intermittent failure? A: Repeat many runs and compare pass rate/cohort rates, not one success.
   Hỏi: Kiểm chứng bản sửa cho lỗi chập chờn 5% thế nào? Đáp: Chạy lặp nhiều lần và so pass rate/tỷ lệ theo cohort, không dựa vào một lần thành công.
5. Q: What does `pause_turn` require from the harness, and which edit to a thinking block causes a 400? A: Send assistant content back unchanged; any modification of `thinking`/`redacted_thinking` in the latest assistant message.
   Hỏi: `pause_turn` đòi hỏi gì ở harness, và sửa thinking block thế nào gây 400? Đáp: Gửi lại assistant content nguyên vẹn; mọi sửa đổi `thinking`/`redacted_thinking` trong tin assistant mới nhất.
6. Q: In a multi-turn failure, which turn do you look for first? A: The first bad turn, not the last.
   Hỏi: Lỗi multi-turn thì tìm turn nào trước? Đáp: Turn sai đầu tiên, không phải turn cuối.
7. Q: First priority in an active user-impacting regression, and best first move after a prompt change? A: Mitigate before diagnosing; roll back the prompt change.
   Hỏi: Ưu tiên đầu tiên khi regression đang ảnh hưởng user, và nước đi đầu sau thay đổi prompt? Đáp: Giảm thiểu trước khi chẩn đoán; rollback thay đổi prompt.
8. Q: What three artifacts should every LLM incident produce beyond the fix? A: Regression eval case(s), monitoring/alert coverage, a blameless postmortem with owned action items.
   Hỏi: Ngoài bản sửa, mỗi sự cố LLM cần tạo ba sản phẩm nào? Đáp: Regression eval case, độ phủ monitoring/alert, postmortem không đổ lỗi với action item có owner.

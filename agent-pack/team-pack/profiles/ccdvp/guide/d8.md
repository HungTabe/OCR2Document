## 8. Agent Fleet Operations for Software Delivery (10%)
## 8. Vận hành fleet agent cho phân phối phần mềm (10%)

**What this domain tests.** Whether you can run many coding agents as an operated fleet: isolate parallel work, put verification in front of human review without breaking merges, let agents run unattended with hard limits, and configure the whole organization from one policy layer. Scenario questions ask you to pick the right primitive, the right rollout order, and the right enforcement point.
**Domain này kiểm tra gì.** Khả năng vận hành nhiều coding agent như một fleet: cô lập công việc song song, đặt lớp verification trước human review mà không làm hỏng merge, cho agent chạy không người giám sát với giới hạn cứng, và cấu hình toàn tổ chức từ một lớp policy. Đề tình huống yêu cầu chọn đúng primitive, đúng thứ tự rollout và đúng điểm enforcement.

### [8.1] Parallel Agent Orchestration for Engineering Work
### [8.1] Điều phối agent song song cho công việc kỹ thuật

- **Core idea:** Isolation comes first. Parallel agents editing the same checkout overwrite each other. A git worktree gives each agent its own files and branch while sharing history and remote; subagents can get a temporary worktree via `isolation: worktree`. Example: two agents refactoring overlapping modules each get one worktree, then integrate via PRs like any other branch.
- **Ý chính:** Cô lập là bước đầu tiên. Nhiều agent sửa cùng một checkout sẽ ghi đè nhau. Git worktree cho mỗi agent file và branch riêng nhưng dùng chung history và remote; subagent có thể có worktree tạm qua `isolation: worktree`. Ví dụ: hai agent refactor các module chồng lấn mỗi bên một worktree, rồi tích hợp bằng PR như mọi branch khác.
- **Core idea:** Choose the parallelism primitive by who coordinates and whether workers touch the same files: subagents (Claude delegates inside one session, summaries return), background sessions/agent view (you dispatch, check later), agent teams (lead plus teammates, shared task list, messaging), dynamic workflows (a script holds the plan), and `/batch` (one large change split into 5 to 30 worktree-isolated units, each opening a PR).
- **Ý chính:** Chọn primitive song song theo ai điều phối và worker có đụng cùng file không: subagent (Claude giao việc trong một session, trả về bản tóm tắt), background session/agent view (bạn giao, xem sau), agent teams (lead + teammate, task list chung, nhắn tin), dynamic workflows (script giữ kế hoạch) và `/batch` (một thay đổi lớn chia thành 5–30 đơn vị có worktree riêng, mỗi đơn vị mở một PR).
- **Core idea:** Decompose into self-contained units with a clear deliverable (a function, a test file, a review). Too small means coordination overhead; too large means long unchecked runs. Docs suggest starting with 3-5 teammates and 5-6 tasks per teammate. Merge strategy beyond "isolate and PR" (ordering, merge queue) is not prescribed by docs.
- **Ý chính:** Chia thành đơn vị tự chứa, có deliverable rõ (một hàm, một file test, một lần review). Quá nhỏ thì tốn chi phí điều phối; quá lớn thì chạy lâu không ai kiểm. Docs gợi ý bắt đầu 3–5 teammate và 5–6 task mỗi teammate. Chiến lược merge ngoài "cô lập rồi PR" (thứ tự, merge queue) docs không quy định.
- **Core idea:** Fleet failure modes show up in telemetry: cost multiplication (each session or teammate has its own context), runaway loops, API errors/retries/refusals, tool rejections, hitting concurrency limits, stuck tasks. OpenTelemetry gives per-model cost and tokens plus `api_error`, `api_refusal`, `tool_decision`, `tool_result` events. Mapping a symptom to a cause is your judgment, not a documented table.
- **Ý chính:** Lỗi cấp fleet hiện ra trong telemetry: chi phí nhân lên (mỗi session/teammate có context riêng), vòng lặp mất kiểm soát, lỗi API/retry/refusal, tool bị từ chối, chạm giới hạn concurrency, task bị kẹt. OpenTelemetry cung cấp cost/token theo model và các event `api_error`, `api_refusal`, `tool_decision`, `tool_result`. Việc ánh xạ triệu chứng sang nguyên nhân là phán đoán của bạn, không có bảng trong docs.
- **Core idea:** Reviewer independence: a fresh reviewer who did not see how the code was written helps; handing the same task to another subagent does not make the answer better. A reviewer told to "find problems" always finds something, so bound its scope (for example "skip style").
- **Ý chính:** Tính độc lập của reviewer: reviewer mới, chưa thấy quá trình viết code thì có ích; giao cùng task cho subagent khác không làm đáp án tốt hơn. Reviewer được bảo "tìm lỗi" sẽ luôn tìm ra thứ gì đó, nên phải giới hạn phạm vi (ví dụ "bỏ qua style").
- **Must-know facts:** `claude --worktree <name>` (`-w`) creates `.claude/worktrees/<name>/` on branch `worktree-<name>`; gitignore `.claude/worktrees/` (Doc). `worktree.baseRef`: `"fresh"` (default, remote default branch) or `"head"` (local HEAD, carries unpushed commits) (Doc). `.worktreeinclude` (gitignore syntax) copies gitignored files such as `.env`; it copies, so use `worktree.symlinkDirectories` for big dirs (Doc). `claude --worktree "#1234"` branches from a PR head; `claude -p --worktree` leaves cleanup to you (Doc). Subagent worktree is auto-removed if unchanged (Doc). Worktree checks block edits redirected into the main checkout, but `cp` and shell redirects are not tracked (Doc). Subagents: 20 concurrent by default (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), nesting depth 3 (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `1` disables), `maxTurns` frontmatter (Doc). Agent teams: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`, experimental, interactive only (not in `-p`), no worktree isolation, one team per session; hooks `TeammateIdle`/`TaskCreated`/`TaskCompleted` (exit 2 blocks and returns feedback) (Doc). `/batch` shows its plan first, then opens one PR per unit (Doc). Parallel sessions multiply token usage (Doc). Scripted fan-out: `claude --bare -p ... --allowedTools ... --permission-mode dontAsk --max-turns 20` in a loop (Doc). Sequencing and merge-queue choice (Interp).
- **Kiến thức phải nhớ:** `claude --worktree <name>` (`-w`) tạo `.claude/worktrees/<name>/` trên branch `worktree-<name>`; thêm `.claude/worktrees/` vào gitignore (Doc). `worktree.baseRef`: `"fresh"` (mặc định, default branch của remote) hoặc `"head"` (HEAD local, mang theo commit chưa push) (Doc). `.worktreeinclude` (cú pháp gitignore) copy các file bị ignore như `.env`; là copy nên thư mục lớn dùng `worktree.symlinkDirectories` (Doc). `claude --worktree "#1234"` rẽ nhánh từ head của PR; `claude -p --worktree` để bạn tự dọn (Doc). Worktree của subagent tự xóa nếu không có thay đổi (Doc). Cơ chế kiểm tra chặn edit bị chuyển hướng vào main checkout, nhưng `cp` và shell redirect không bị theo dõi (Doc). Subagent: mặc định 20 đồng thời (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), độ sâu lồng 3 (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `1` là tắt), frontmatter `maxTurns` (Doc). Agent teams: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`, experimental, chỉ interactive (không chạy trong `-p`), teammate không có worktree riêng, một team mỗi session; hook `TeammateIdle`/`TaskCreated`/`TaskCompleted` (exit 2 chặn và trả feedback) (Doc). `/batch` hiển thị plan trước rồi mở một PR cho mỗi đơn vị (Doc). Chạy song song nhân token usage (Doc). Fan-out bằng script: vòng lặp `claude --bare -p ... --allowedTools ... --permission-mode dontAsk --max-turns 20` (Doc). Thứ tự và lựa chọn merge queue (Interp).
- **Decision rule:** When many agents edit overlapping code → give each its own worktree (or `isolation: worktree`) because separate checkouts and branches prevent overwrites; if using agent teams, partition files so each teammate owns distinct files. Trap: "worktrees isolate everything" is wrong (they isolate files, not shared `.git`, external side effects or approvals saved to the main checkout); "add more teammates to go faster" gives diminishing returns; "give the subagent the same task for a better answer" does not help, a fresh reviewer does (Doc). For cost spikes, check `cost.usage`/`token.usage` by model, session count and `api_error` retries before rewriting prompts (Interp ordering).
- **Quy tắc quyết định:** Khi nhiều agent sửa code chồng lấn → cho mỗi agent một worktree riêng (hoặc `isolation: worktree`) vì checkout và branch tách biệt ngăn ghi đè; nếu dùng agent teams, chia file để mỗi teammate sở hữu tập file riêng. Bẫy: "worktree cô lập mọi thứ" là sai (chỉ cô lập file, không cô lập `.git` chung, side effect bên ngoài, hay approval lưu vào main checkout); "thêm teammate cho nhanh" bị lợi suất giảm dần; "giao cùng task cho subagent để đáp án tốt hơn" không có tác dụng, reviewer mới mới có (Doc). Khi chi phí tăng vọt, xem `cost.usage`/`token.usage` theo model, số session và retry `api_error` trước khi sửa prompt (thứ tự là Interp).

### [8.2] Verification and AI Code Review Operations
### [8.2] Vận hành verification và AI code review

- **Core idea:** When generation outpaces human review, verification becomes the bottleneck. Add automated verification layers, but introduce them non-blocking first, because a noisy gate trains people to bypass it.
- **Ý chính:** Khi tốc độ sinh code vượt khả năng review của người, verification thành nút cổ chai. Thêm các lớp verification tự động, nhưng ban đầu để ở chế độ không chặn, vì gate nhiễu sẽ khiến mọi người tìm cách lách.
- **Core idea:** The official Code Review service runs several agents over the diff in parallel, filters false positives with a verification step, deduplicates and ranks, then posts inline comments, a summary and a check run named "Claude Code Review". It never approves or blocks a PR and the check never concludes as failure. Gating is your own CI's job: read the severity line and enforce via CI plus branch protection.
- **Ý chính:** Dịch vụ Code Review chính thức chạy nhiều agent song song trên diff, lọc false positive bằng bước verification, loại trùng, xếp hạng, rồi đăng inline comment, summary và một check run tên "Claude Code Review". Nó không bao giờ approve hay chặn PR và check không bao giờ kết thúc là failure. Gating là việc của CI của bạn: đọc dòng severity và enforce bằng CI cùng branch protection.
- **Core idea:** "Shadow mode, then gate" is a rollout sequence: observe, measure, calibrate against human review, then gate. The docs supply the building blocks (Review runs setting, pilot cost estimate, REVIEW.md tuning, analytics); the sequence itself is inferred, supported by Uber's uReview write-up (phased rollout, precision tracking, per-category confidence thresholds).
- **Ý chính:** "Shadow mode rồi mới gate" là trình tự rollout: quan sát, đo, hiệu chỉnh so với review của người, rồi mới gate. Docs cung cấp các thành phần (setting Review runs, pilot ước lượng chi phí, REVIEW.md, analytics); bản thân trình tự là suy ra, được củng cố bởi bài của Uber về uReview (rollout theo pha, theo dõi precision, ngưỡng confidence theo category).
- **Core idea:** Calibration levers: review level, REVIEW.md (redefine Important, cap nits, skip generated paths, require `file:line` evidence), CLAUDE.md rules, resolving a thread to dismiss, and adding a REVIEW.md rule when the same finding repeats. Human oversight: "the decision to merge stays with your team"; REVIEW.md is read from the base/default branch, so an author cannot weaken the reviewer inside their own PR. A clean review is not proof of correctness, since review reads code without building or running it.
- **Ý chính:** Đòn bẩy hiệu chỉnh: review level, REVIEW.md (định nghĩa lại Important, giới hạn nit, bỏ qua path sinh tự động, yêu cầu bằng chứng `file:line`), luật trong CLAUDE.md, resolve thread để bỏ qua, và thêm luật REVIEW.md khi một finding lặp lại. Giám sát của người: "quyết định merge vẫn thuộc về team"; REVIEW.md được đọc từ base/default branch nên tác giả không thể làm yếu reviewer ngay trong PR của mình. Review sạch không chứng minh code đúng, vì review chỉ đọc code, không build hay chạy.
- **Must-know facts:** Code Review needs Team/Enterprise and GitHub (incl. GHES); unavailable with Zero Data Retention, HIPAA configuration or CMEK; read-only, does not build or run code (Doc). Levels Quick / Standard (default) / Deep; Review runs: Once after PR creation, After every push (default for newly added repos, most expensive), Manual (Doc). Commands: `@claude review`, `@claude review always|once|stop|off|pause`; needs write access; drafts and fork PRs skipped by automatic reviews (Doc). Severity: Important (red), Nit (yellow), Pre-existing (purple) (Doc). Last line of Details is `<!-- bughunter-severity: {"nit":1,"normal":2,"pre_existing":0} -->`, `normal` = count of Important; a missing line means no verdict, not zero findings (Doc). REVIEW.md at repo root, honored severity lowering and exclusions need a protected default branch; `@file` includes max 8 files and 150,000 bytes; local `/code-review` reads CLAUDE.md but not REVIEW.md (Doc). Billing via usage credits to the org; pilot with a monthly spend limit, few repos, Once or Manual; reviews are skipped when the limit runs out; analytics at claude.ai/analytics/code-review (Doc). Own-CI option: `anthropics/claude-code-action@v1` with `plugins: "code-review@claude-plugins-official"` (Doc). The term "shadow mode" is not in the official docs read (Interp). Uber uReview: 75% of comments useful, over 65% addressed vs 51% of human comments addressed (3rd party).
- **Kiến thức phải nhớ:** Code Review cần Team/Enterprise và GitHub (gồm GHES); không có với Zero Data Retention, cấu hình HIPAA hay CMEK; chỉ đọc, không build/chạy code (Doc). Level Quick / Standard (mặc định) / Deep; Review runs: Once after PR creation, After every push (mặc định cho repo mới thêm, đắt nhất), Manual (Doc). Lệnh: `@claude review`, `@claude review always|once|stop|off|pause`; cần quyền write; draft và PR từ fork bị bỏ qua khi review tự động (Doc). Severity: Important (đỏ), Nit (vàng), Pre-existing (tím) (Doc). Dòng cuối của Details là `<!-- bughunter-severity: {"nit":1,"normal":2,"pre_existing":0} -->`, `normal` = số Important; thiếu dòng này nghĩa là không có verdict, không phải 0 finding (Doc). REVIEW.md ở root repo, việc hạ severity và loại trừ chỉ được tôn trọng khi default branch được bảo vệ; `@file` include tối đa 8 file và 150,000 byte; `/code-review` local đọc CLAUDE.md nhưng không đọc REVIEW.md (Doc). Tính phí qua usage credits của org; pilot với spend limit hàng tháng, ít repo, Once hoặc Manual; hết limit thì review bị bỏ qua; analytics ở claude.ai/analytics/code-review (Doc). Phương án CI riêng: `anthropics/claude-code-action@v1` với `plugins: "code-review@claude-plugins-official"` (Doc). Thuật ngữ "shadow mode" không có trong docs chính thức đã đọc (Interp). Uber uReview: 75% comment hữu ích, hơn 65% được xử lý so với 51% comment của người (3rd party).
- **Decision rule:** When generation outpaces review → run AI review advisory first (Manual or Once-per-PR, few repos, spend limit), compare with human outcomes, tune REVIEW.md, and only then fail CI on `normal > 0` because a noisy gate blocks merges and gets bypassed (Interp, building blocks Doc). To make Claude's review block merges → build the gate in your CI from the severity line, since the service never blocks (Doc). Trap: "a clean review means safe to merge"; editing REVIEW.md in the PR under review (ignored); judging success by comment count instead of useful/addressed rate; ZDR/HIPAA/CMEK orgs expecting the managed service (use own-CI or local review) (Doc).
- **Quy tắc quyết định:** Khi sinh code vượt review → chạy AI review ở chế độ tham khảo trước (Manual hoặc Once-per-PR, ít repo, có spend limit), so với kết quả của người, chỉnh REVIEW.md, rồi mới cho CI fail khi `normal > 0` vì gate nhiễu sẽ chặn merge và bị lách (Interp, thành phần là Doc). Muốn review của Claude chặn merge → dựng gate trong CI của bạn từ dòng severity, vì dịch vụ không bao giờ chặn (Doc). Bẫy: "review sạch nghĩa là merge an toàn"; sửa REVIEW.md ngay trong PR đang bị review (bị bỏ qua); đo thành công bằng số comment thay vì tỷ lệ hữu ích/được xử lý; org ZDR/HIPAA/CMEK mong dùng dịch vụ managed (phải dùng CI riêng hoặc review local) (Doc).

### [8.3] Unattended and Event-Driven Agent Operations
### [8.3] Vận hành agent không giám sát và theo sự kiện

- **Core idea:** Pick the scheduling surface by where it must run: cloud scheduled tasks (Anthropic cloud, schedule/API/GitHub triggers, no machine needed, minimum 1 hour), Desktop scheduled tasks (your machine, local files), GitHub Actions/GitLab CI (your CI, event or cron), and `/loop` (session-scoped, needs an open session).
- **Ý chính:** Chọn bề mặt lập lịch theo nơi nó phải chạy: cloud scheduled task (cloud của Anthropic, trigger schedule/API/GitHub, không cần máy bật, tối thiểu 1 giờ), Desktop scheduled task (máy của bạn, file local), GitHub Actions/GitLab CI (CI của bạn, theo event hoặc cron) và `/loop` (gắn với session, cần session đang mở).
- **Core idea:** Goal-driven versus time-driven: `/goal <condition>` keeps working until a separate small fast evaluator model judges the condition met. That evaluator only sees what appears in the transcript; it cannot run tests itself. Bound it with "or stop after N turns". Use `/loop` for time-based polling.
- **Ý chính:** Hướng mục tiêu và hướng thời gian: `/goal <condition>` tiếp tục làm việc cho đến khi một model evaluator nhỏ, nhanh, tách biệt đánh giá điều kiện đã đạt. Evaluator chỉ thấy nội dung trong transcript, không tự chạy test. Giới hạn bằng "or stop after N turns". Dùng `/loop` cho polling theo thời gian.
- **Core idea:** Event-driven responders: a GitHub Action in automation mode (`prompt` set), a cloud task API trigger (HTTP POST to `/fire` with a bearer token and optional `text` such as an alert body), or GitHub-event triggers. The fire text is untrusted input. Example: an alert fires, the task reads the payload, diagnoses read-only, and pushes a `claude/` branch for a human to approve.
- **Ý chính:** Responder theo sự kiện: GitHub Action ở automation mode (có `prompt`), API trigger của cloud task (HTTP POST tới `/fire` với bearer token và `text` tùy chọn như nội dung alert), hoặc trigger theo GitHub event. Text của fire là input không tin cậy. Ví dụ: alert nổ, task đọc payload, chẩn đoán chỉ-đọc, rồi đẩy branch `claude/` cho người duyệt.
- **Core idea:** Unattended safety checklist: (1) knows what done looks like, (2) can check its own work, (3) limited scope (permission rules, `dontAsk`, sandbox, worktree, one pushable branch), (4) a stopper (`--max-turns`, `--max-budget-usd`, spend limit), (5) results go somewhere and a person signs off on irreversible steps. Docs give the mechanisms for checkpointing and escalation; the overall escalation design is your own. There is no documented "CI incident first response" page, only the pieces.
- **Ý chính:** Checklist an toàn khi không giám sát: (1) biết thế nào là xong, (2) tự kiểm được kết quả, (3) phạm vi hẹp (permission rule, `dontAsk`, sandbox, worktree, một branch được push), (4) có bộ dừng (`--max-turns`, `--max-budget-usd`, spend limit), (5) kết quả có nơi đến và người ký duyệt bước không hoàn tác được. Docs cho cơ chế checkpoint và escalation; thiết kế escalation tổng thể là của bạn. Không có trang docs nào tên "CI incident first response", chỉ có các mảnh ghép.
- **Must-know facts:** `claude -p` exits 0 on success, non-zero on failure, SIGTERM gives 143; `--output-format` text/json/stream-json; `--json-schema` fills `structured_output`; `stream-json` needs `--verbose` (Doc). `--bare` skips hooks, skills, plugins, MCP, auto memory, CLAUDE.md and uses `ANTHROPIC_API_KEY`/`apiKeyHelper`; without it, `-p` runs project hooks and `.mcp.json` servers without a trust dialog (Doc). `--permission-mode dontAsk` denies anything that would prompt; `--permission-prompts none` (v2.1.259+) and `permissions.denyInsteadOfPrompting` deny rather than wait (Doc). `system/init` carries `plugin_errors` and `mcp_server_errors`; load failures are otherwise silent (Doc). Cloud tasks: minimum 1 hour, branches prefixed `claude/`, limits 100 scheduled runs/hour per account, belong to an individual account and act as you (Doc). API trigger token is shown once; beta header `experimental-cc-routine-2026-04-01`; the saved prompt must opt in to act on the fire text (Doc). `/loop 5m <prompt>`, self-paced if omitted, `.claude/loop.md`, recurring tasks expire after 7 days, up to 50 tasks per session, 1-minute minimum (Doc). `/goal`: condition up to 4,000 characters, `CLAUDE_CODE_GOAL_CHECKIN_MINUTES` default 30, works with `-p`, unavailable when `allowManagedHooksOnly` or `disableAllHooks` (Doc). GitHub Action: scheduled workflows run only from the default branch, public-repo schedules disable after 60 days of inactivity, commits via default `GITHUB_TOKEN` do not trigger CI, bot actors rejected unless `allowed_bots` (Doc). GitLab CI/CD is beta (Doc). Hooks: `Stop`/`SubagentStop` (exit 2 keeps working), `Notification` cannot block, `TaskCompleted` (Doc).
- **Kiến thức phải nhớ:** `claude -p` thoát 0 khi thành công, khác 0 khi lỗi, SIGTERM cho 143; `--output-format` text/json/stream-json; `--json-schema` điền `structured_output`; `stream-json` cần `--verbose` (Doc). `--bare` bỏ qua hooks, skills, plugins, MCP, auto memory, CLAUDE.md và dùng `ANTHROPIC_API_KEY`/`apiKeyHelper`; nếu không có, `-p` chạy hook dự án và server `.mcp.json` mà không hỏi trust (Doc). `--permission-mode dontAsk` từ chối mọi thứ cần hỏi; `--permission-prompts none` (v2.1.259+) và `permissions.denyInsteadOfPrompting` từ chối thay vì chờ (Doc). `system/init` có `plugin_errors` và `mcp_server_errors`; lỗi nạp nếu không kiểm sẽ im lặng (Doc). Cloud task: tối thiểu 1 giờ, branch tiền tố `claude/`, giới hạn 100 lần chạy theo lịch/giờ mỗi account, thuộc về account cá nhân và hành động như bạn (Doc). Token API trigger chỉ hiện một lần; beta header `experimental-cc-routine-2026-04-01`; prompt đã lưu phải chủ động cho phép xử lý text của fire (Doc). `/loop 5m <prompt>`, tự điều nhịp nếu bỏ interval, `.claude/loop.md`, task định kỳ hết hạn sau 7 ngày, tối đa 50 task/session, tối thiểu 1 phút (Doc). `/goal`: điều kiện tối đa 4,000 ký tự, `CLAUDE_CODE_GOAL_CHECKIN_MINUTES` mặc định 30, chạy được với `-p`, không dùng được khi có `allowManagedHooksOnly` hoặc `disableAllHooks` (Doc). GitHub Action: workflow theo lịch chỉ chạy từ default branch, lịch của repo public tự tắt sau 60 ngày không hoạt động, commit bằng `GITHUB_TOKEN` mặc định không kích hoạt CI, bot bị từ chối trừ khi có `allowed_bots` (Doc). GitLab CI/CD đang beta (Doc). Hook: `Stop`/`SubagentStop` (exit 2 tiếp tục làm), `Notification` không chặn được, `TaskCompleted` (Doc).
- **Decision rule:** When work must run with the laptop off, on a schedule or on an alert → cloud scheduled task (at least 1 hour) or CI cron, because `/loop` dies with the session and expires in 7 days (Doc). When completion is condition-based → `/goal` with a measurable end state plus a turn cap. With no human to answer prompts → `--permission-mode dontAsk` plus `--allowedTools`, with caps. Alert response → `/fire` with a prompt that handles the payload as untrusted, output to a `claude/` branch, branch protection as the hard stop. Trap: expecting CI to run on commits made with the default `GITHUB_TOKEN`; a scheduled workflow on a non-default branch; believing the `/goal` evaluator runs tests; omitting `--max-turns`/budget/timeout caps; `--bare` combined with hooks passed via `--settings` (hooks do not run) (Doc). Using dedicated service identity for fleets is a recommendation (Interp).
- **Quy tắc quyết định:** Khi việc phải chạy lúc tắt laptop, theo lịch hoặc theo alert → cloud scheduled task (tối thiểu 1 giờ) hoặc CI cron, vì `/loop` chết cùng session và hết hạn sau 7 ngày (Doc). Khi hoàn thành dựa trên điều kiện → `/goal` với trạng thái kết thúc đo được cộng giới hạn turn. Không có người trả lời prompt → `--permission-mode dontAsk` cộng `--allowedTools`, kèm các giới hạn. Phản ứng alert → `/fire` với prompt coi payload là không tin cậy, output ra branch `claude/`, branch protection là điểm dừng cứng. Bẫy: mong CI chạy trên commit tạo bằng `GITHUB_TOKEN` mặc định; workflow theo lịch ở branch không phải default; tin rằng evaluator của `/goal` tự chạy test; bỏ quên giới hạn `--max-turns`/budget/timeout; `--bare` kèm hook truyền qua `--settings` (hook không chạy) (Doc). Dùng service identity riêng cho fleet là khuyến nghị (Interp).

### [8.4] Organization-Wide Coding Agent Configuration
### [8.4] Cấu hình coding agent toàn tổ chức

- **Core idea:** Managed settings sit above everything: managed, then `--settings`, then project local, shared project, user. Delivery channels are server-managed (polled hourly), MDM/OS policy (checked every 30 minutes), or a file (`managed-settings.json` plus `managed-settings.d/`). Lists merge, so developers can extend but not remove managed `permissions.deny`. CLAUDE.md is guidance, not enforcement; use managed settings or a PreToolUse hook to enforce.
- **Ý chính:** Managed settings đứng trên mọi thứ: managed, rồi `--settings`, project local, shared project, user. Kênh phân phối gồm server-managed (poll mỗi giờ), MDM/policy OS (kiểm tra mỗi 30 phút) hoặc file (`managed-settings.json` cùng `managed-settings.d/`). Danh sách được merge nên developer có thể thêm nhưng không gỡ được `permissions.deny` của managed. CLAUDE.md chỉ là hướng dẫn, không phải enforcement; muốn enforce hãy dùng managed settings hoặc hook PreToolUse.
- **Core idea:** MCP governance: `managed-mcp.json` gives exclusive control, `managedMcpServers` provides servers while users keep theirs, `allowedMcpServers`/`deniedMcpServers` with `allowManagedMcpServersOnly` restrict. The denylist always wins. A `serverName` match is not a security control because the label is user-chosen; match on `serverUrl` or `serverCommand`.
- **Ý chính:** Quản trị MCP: `managed-mcp.json` kiểm soát độc quyền, `managedMcpServers` cấp server nhưng user vẫn giữ server của họ, `allowedMcpServers`/`deniedMcpServers` cùng `allowManagedMcpServersOnly` để hạn chế. Denylist luôn thắng. So khớp `serverName` không phải kiểm soát bảo mật vì tên do user tự đặt; hãy so khớp `serverUrl` hoặc `serverCommand`.
- **Core idea:** Plugin and Skill governance: package internal Skills as plugins in a private marketplace, force them with `extraKnownMarketplaces` plus `enabledPlugins`, restrict sources with `strictKnownMarketplaces`/`blockedMarketplaces`/`disableSideloadFlags`. Staged release channels are two marketplaces on different refs for different groups. Review `allowed-tools` and `!` commands in shared skills because they apply even in `-p` runs in untrusted folders. A formal promotion process (owner, pinning, checklist) is your design.
- **Ý chính:** Quản trị plugin và Skill: đóng gói Skill nội bộ thành plugin trong marketplace riêng, ép dùng bằng `extraKnownMarketplaces` cộng `enabledPlugins`, hạn chế nguồn bằng `strictKnownMarketplaces`/`blockedMarketplaces`/`disableSideloadFlags`. Kênh release theo giai đoạn là hai marketplace trên các ref khác nhau cho các nhóm khác nhau. Phải review `allowed-tools` và lệnh `!` trong skill dùng chung vì chúng áp dụng cả khi chạy `-p` trong thư mục không tin cậy. Quy trình promote chính thức (owner, pin version, checklist) là thiết kế của bạn.
- **Core idea:** Telemetry and gateway: OpenTelemetry is opt-in and pushed fleet-wide through managed `env`; a repo's `.claude/settings.json` cannot set exporter variables. A gateway centralizes credentials, usage attribution, budgets, audit logging and provider switching, at the cost of operating it and keeping it current. Pin traffic to it with `allowedProviders: ["customEndpoint"]`.
- **Ý chính:** Telemetry và gateway: OpenTelemetry là opt-in và đẩy toàn fleet qua `env` của managed settings; `.claude/settings.json` của repo không đặt được biến exporter. Gateway tập trung credential, gán usage, budget, audit log và chuyển provider, đổi lại bạn phải vận hành và cập nhật nó. Ghim traffic vào gateway bằng `allowedProviders: ["customEndpoint"]`.
- **Must-know facts:** Paths: macOS `/Library/Application Support/ClaudeCode/managed-settings.json`, Linux/WSL `/etc/claude-code/managed-settings.json`, Windows `C:\Program Files\ClaudeCode\managed-settings.json`; Windows HKLM `HKLM\SOFTWARE\Policies\ClaudeCode`; HKCU is user-writable so not enforcement (Doc). Server-managed needs Teams/Enterprise, polled hourly; only server-managed settings reach Anthropic-hosted cloud sessions (Doc). Source priority remote > MDM > file > HKCU; first source with a policy key wins unless `managedSourcesBehavior: "merge"` (Doc). Enforcement keys: `allowManagedPermissionRulesOnly`, `permissions.disableBypassPermissionsMode`, `allowManagedHooksOnly`, `forceLoginOrgUUID`, `allowedProviders`, `availableModels`, `minimumVersion`, `sandbox.enabled`, `sandbox.network.allowedDomains` (Doc). Denying WebFetch does not stop `curl` via Bash; the sandbox network allowlist closes that gap (Doc). `managed-mcp.json` cannot be delivered via server-managed settings; empty `{"mcpServers": {}}` disables MCP; allowlist unset = all allowed, `[]` = none (Doc). MCP scope precedence: `managedMcpServers` > local > project > user > plugin > claude.ai connectors (Doc). `strictKnownMarketplaces: []` blocks all including official; `blockedMarketplaces` is checked first; `claude plugin validate` (Doc). Skills: enterprise > personal > project; `disable-model-invocation: true` for side-effecting skills (Doc). OTel: `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_METRICS_EXPORTER`, `OTEL_LOGS_EXPORTER`, `OTEL_EXPORTER_OTLP_ENDPOINT`; metrics such as `claude_code.cost.usage`, `token.usage`; prompts redacted unless `OTEL_LOG_USER_PROMPTS`; team attribution via `OTEL_RESOURCE_ATTRIBUTES` (Doc; that page was only partly read). Gateway: `ANTHROPIC_BASE_URL`; setting only the base URL keeps a saved claude.ai login as active credential; `allowedProviders: ["customEndpoint"]` needs v2.1.285+; third-party gateways are not endorsed and non-Claude models are unsupported; gateway sessions are not eligible for the HIPAA configuration (Doc). LiteLLM specifics (Unverified).
- **Kiến thức phải nhớ:** Đường dẫn: macOS `/Library/Application Support/ClaudeCode/managed-settings.json`, Linux/WSL `/etc/claude-code/managed-settings.json`, Windows `C:\Program Files\ClaudeCode\managed-settings.json`; Windows HKLM `HKLM\SOFTWARE\Policies\ClaudeCode`; HKCU user ghi được nên không phải enforcement (Doc). Server-managed cần Teams/Enterprise, poll mỗi giờ; chỉ server-managed settings tới được cloud session do Anthropic host (Doc). Ưu tiên nguồn remote > MDM > file > HKCU; nguồn đầu tiên có policy key thắng trừ khi `managedSourcesBehavior: "merge"` (Doc). Key enforcement: `allowManagedPermissionRulesOnly`, `permissions.disableBypassPermissionsMode`, `allowManagedHooksOnly`, `forceLoginOrgUUID`, `allowedProviders`, `availableModels`, `minimumVersion`, `sandbox.enabled`, `sandbox.network.allowedDomains` (Doc). Deny WebFetch không chặn được `curl` qua Bash; allowlist mạng của sandbox lấp lỗ hổng này (Doc). `managed-mcp.json` không phân phối được qua server-managed settings; `{"mcpServers": {}}` rỗng tắt MCP; allowlist không đặt = cho phép hết, `[]` = không cho gì (Doc). Ưu tiên scope MCP: `managedMcpServers` > local > project > user > plugin > claude.ai connectors (Doc). `strictKnownMarketplaces: []` chặn tất cả kể cả official; `blockedMarketplaces` được kiểm tra trước; `claude plugin validate` (Doc). Skill: enterprise > personal > project; `disable-model-invocation: true` cho skill có side effect (Doc). OTel: `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_METRICS_EXPORTER`, `OTEL_LOGS_EXPORTER`, `OTEL_EXPORTER_OTLP_ENDPOINT`; metric như `claude_code.cost.usage`, `token.usage`; prompt bị ẩn trừ khi có `OTEL_LOG_USER_PROMPTS`; gán team qua `OTEL_RESOURCE_ATTRIBUTES` (Doc; trang này mới đọc một phần). Gateway: `ANTHROPIC_BASE_URL`; chỉ đặt base URL thì login claude.ai đã lưu vẫn là credential đang dùng; `allowedProviders: ["customEndpoint"]` cần v2.1.285+; gateway bên thứ ba không được Anthropic bảo chứng và không hỗ trợ model non-Claude; session qua gateway không đủ điều kiện cấu hình HIPAA (Doc). Chi tiết LiteLLM (Unverified).
- **Decision rule:** When a policy must not be overridable → managed settings (server-managed, MDM or file), not `.claude/settings.json` or CLAUDE.md, because those are guidance or developer-editable (Doc). Only approved MCP servers → `allowedMcpServers` with `serverUrl`/`serverCommand` plus `allowManagedMcpServersOnly: true`, or `managed-mcp.json` for a fixed set. Route everything through a gateway → `ANTHROPIC_BASE_URL` in managed `env` plus `allowedProviders: ["customEndpoint"]` plus per-developer credentials. Cloud sessions must obey policy → server-managed settings only. Trap: `serverName` allowlists; HKCU or user-writable files as enforcement; OTel exporter variables in repo settings (ignored); an OAuth token as org-wide Action secret (tied to one person, use an API key or workload identity federation); forgetting that `allowManagedHooksOnly` also disables `/goal` (Doc).
- **Quy tắc quyết định:** Khi policy không được phép bị ghi đè → dùng managed settings (server-managed, MDM hoặc file), không dùng `.claude/settings.json` hay CLAUDE.md vì chúng chỉ là hướng dẫn hoặc developer sửa được (Doc). Chỉ cho MCP server đã duyệt → `allowedMcpServers` với `serverUrl`/`serverCommand` cộng `allowManagedMcpServersOnly: true`, hoặc `managed-mcp.json` cho tập cố định. Định tuyến mọi thứ qua gateway → `ANTHROPIC_BASE_URL` trong `env` managed cộng `allowedProviders: ["customEndpoint"]` cộng credential theo từng developer. Cloud session phải tuân policy → chỉ server-managed settings. Bẫy: allowlist theo `serverName`; HKCU hay file user ghi được làm enforcement; biến exporter OTel trong settings của repo (bị bỏ qua); dùng OAuth token làm secret Action cho cả org (gắn với một người, hãy dùng API key hoặc workload identity federation); quên rằng `allowManagedHooksOnly` cũng tắt `/goal` (Doc).

### Self-check / Tự kiểm tra

1. Q: Why can't Code Review gate merges by itself? A: It never approves or blocks and its check never fails; your CI must read the `bughunter-severity` line.
   Q: Vì sao Code Review không tự gate merge được? Đ: Nó không bao giờ approve/chặn và check không fail; CI của bạn phải đọc dòng `bughunter-severity`.
2. Q: Safest first step for AI review when generation outpaces human review? A: Run it advisory (Manual/Once-per-PR, few repos, spend cap), calibrate against humans, then gate (Interp).
   Q: Bước đầu an toàn nhất cho AI review khi sinh code vượt review? Đ: Chạy chế độ tham khảo (Manual/Once-per-PR, ít repo, có spend cap), hiệu chỉnh so với người, rồi mới gate (Interp).
3. Q: Where must REVIEW.md live to be honored? A: Root of a protected default branch; it is read from base, never from the PR.
   Q: REVIEW.md phải ở đâu để được tôn trọng? Đ: Root của default branch được bảo vệ; được đọc từ base, không bao giờ từ PR.
4. Q: A missing severity line in the check run means what? A: No verdict, not zero findings.
   Q: Thiếu dòng severity trong check run nghĩa là gì? Đ: Không có verdict, không phải 0 finding.
5. Q: Two agents edit overlapping modules in parallel; what isolates them? A: One worktree each (`claude -w name` or `isolation: worktree`).
   Q: Hai agent sửa module chồng lấn song song, cái gì cô lập chúng? Đ: Mỗi agent một worktree (`claude -w name` hoặc `isolation: worktree`).
6. Q: Agent teams and file conflicts? A: Teammates are not worktree-isolated, so assign disjoint file sets.
   Q: Agent teams và xung đột file? Đ: Teammate không có worktree riêng nên phải giao tập file không giao nhau.
7. Q: Nightly job must run with the laptop off; which option and minimum interval? A: Cloud scheduled task or CI cron; 1 hour minimum.
   Q: Job hằng đêm phải chạy khi tắt laptop; chọn gì và interval tối thiểu? Đ: Cloud scheduled task hoặc CI cron; tối thiểu 1 giờ.
8. Q: Which flags make a CI `claude -p` run non-interactive, bounded and locked down? A: `--bare`, `--allowedTools`, `--permission-mode dontAsk`, `--max-turns` (plus `--max-budget-usd`, job timeout).
   Q: Cờ nào làm `claude -p` trong CI không tương tác, có giới hạn và bị khóa chặt? Đ: `--bare`, `--allowedTools`, `--permission-mode dontAsk`, `--max-turns` (cộng `--max-budget-usd`, timeout của job).
9. Q: Can a repo's `.claude/settings.json` enable org telemetry? A: No, exporter variables there are ignored; use managed `env`.
   Q: `.claude/settings.json` của repo có bật được telemetry cho org không? Đ: Không, biến exporter ở đó bị bỏ qua; dùng `env` của managed settings.
10. Q: Does a local managed-settings.json govern Anthropic-hosted cloud sessions? A: No, only server-managed settings do.
    Q: managed-settings.json trên máy có chi phối cloud session do Anthropic host không? Đ: Không, chỉ server-managed settings làm được.

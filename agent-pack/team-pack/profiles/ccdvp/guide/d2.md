## 2. Production Integration, Reliability, and Knowledge Grounding (20%)
## 2. Tích hợp production, độ tin cậy và knowledge grounding (20%)

**What this domain tests.** It tests whether you can run Claude in production without surprises: classify a failure before reacting, find the real bottleneck in throughput, change models/prompts/MCP servers safely, and ground answers in retrieved knowledge with diagnosable quality. It is the heaviest domain, and almost every scenario question hides a "same symptom, different cause" trap.
**Domain này kiểm tra gì.** Domain này kiểm tra khả năng vận hành Claude trên production mà không bị bất ngờ: phân loại lỗi trước khi phản ứng, tìm đúng nút thắt về throughput, thay đổi model/prompt/MCP server một cách an toàn, và grounding câu trả lời vào tri thức truy xuất được với chất lượng có thể chẩn đoán. Đây là domain nặng nhất; gần như mọi câu tình huống đều có bẫy "cùng triệu chứng, khác nguyên nhân".

### [2.1] Reliability Engineering for Claude Services
### [2.1] Kỹ thuật độ tin cậy cho dịch vụ Claude

- **Core idea:** Classify the failure first, then pick the remedy. "No normal answer" can be a rate limit (429), platform overload (529), a safety refusal (HTTP 200 with `stop_reason: "refusal"`), an output cap (`max_tokens`) or a full context window (`model_context_window_exceeded`). Each has a different fix, and only some are retryable.
- **Ý chính:** Phân loại lỗi trước, rồi mới chọn cách xử lý. "Không có câu trả lời bình thường" có thể là rate limit (429), quá tải nền tảng (529), safety refusal (HTTP 200 kèm `stop_reason: "refusal"`), chạm trần output (`max_tokens`) hoặc đầy context window (`model_context_window_exceeded`). Mỗi loại có cách sửa khác nhau, chỉ một số loại nên retry.
- **Core idea:** Refusals are not exceptions. They arrive as a successful 200 response, so code that only catches `RateLimitError` misses them. Check `stop_details.category`, discard any partial streamed output, and retry on a different model, because the same model usually refuses again.
- **Ý chính:** Refusal không phải exception. Nó đến dưới dạng response 200 thành công, nên code chỉ bắt `RateLimitError` sẽ bỏ sót. Hãy xem `stop_details.category`, bỏ output stream dở dang, rồi retry bằng model khác vì cùng model thường sẽ từ chối lại.
- **Core idea:** Retry design: retry only transient classes (connection errors, 408, 409, 429, 5xx including 529) with exponential backoff plus jitter, capped attempts/total time, and prefer `retry-after` over your own clock. Never blind-retry 400/401/403/404/413 or refusals.
- **Ý chính:** Thiết kế retry: chỉ retry lớp lỗi tạm thời (lỗi kết nối, 408, 409, 429, 5xx gồm 529), dùng exponential backoff có jitter, giới hạn số lần/tổng thời gian, ưu tiên `retry-after` thay vì đồng hồ của bạn. Không retry mù 400/401/403/404/413 hay refusal.
- **Core idea:** Layered retries multiply: SDK retries 2x and app retries 3x can turn one logical call into 9 requests, amplifying 429/529 storms. Give one layer ownership of retries, and add a circuit breaker (stop calling a failing dependency for a cool-down, then half-open probe) and graceful degradation (cache, smaller model, queue, "try later" UX). The docs read do not define these patterns.
- **Ý chính:** Retry nhiều tầng nhân lên: SDK retry 2 lần và app retry 3 lần biến một lệnh gọi thành 9 request, làm trầm trọng bão 429/529. Hãy để một tầng sở hữu retry, thêm circuit breaker (ngừng gọi dependency đang lỗi trong thời gian nghỉ, rồi thử half-open) và graceful degradation (cache, model nhỏ hơn, hàng đợi, UX "thử lại sau"). Docs đã đọc không định nghĩa các pattern này.
- **Core idea:** Fallbacks come in three layers: cross-model (refusal fallback, smaller model on overload), cross-region (Bedrock global vs regional endpoints/inference profiles) and cross-platform (Claude API to Bedrock/Google Cloud/Foundry). The cross-platform trap is feature parity: the failover target may silently lack a feature your prompt depends on.
- **Ý chính:** Fallback có ba tầng: cross-model (fallback khi refusal, model nhỏ hơn khi quá tải), cross-region (endpoint global/regional, inference profile của Bedrock) và cross-platform (Claude API sang Bedrock/Google Cloud/Foundry). Bẫy của cross-platform là feature parity: đích failover có thể âm thầm thiếu tính năng mà prompt của bạn phụ thuộc.

- **Must-know facts:**
  - Error codes: 400 `invalid_request_error`, 401 `authentication_error`, 402 `billing_error`, 403 `permission_error`, 404 `not_found_error`, 409 `conflict_error`, 413 `request_too_large`, 429 `rate_limit_error`, 500 `api_error`, 504 `timeout_error`, 529 `overloaded_error`. (Doc)
  - 529 can occur from high traffic across all users, so it is platform capacity, not your quota. (Doc)
  - Hitting your own org/workspace spend limit returns 400 `invalid_request_error`, not 429 (Claude Code workspace can be 429). (Doc)
  - The tier monthly spend-cap 429 (`error.details.error_code = enforced_spend_limit_reached`) has no `retry-after` and keeps failing until access resumes. (Doc)
  - SDK auto-retries connection errors, rate limits and 5xx twice by default with exponential backoff, honoring `retry-after`; configurable via `max_retries`. Python SDK default timeout is 10 minutes and timeouts also retry twice. (Doc)
  - The SDK raises `ValueError` for non-streaming requests expected to exceed about 10 minutes; use streaming or Batches for long jobs. (Doc)
  - Max request size: Messages 128 MB, Token Counting 128 MB, Batch 256 MB, Files 500 MB; over the limit gives 413. (Doc)
  - Every response has a `request-id` header (also in the error body); log it for support. Foundry also adds `apim-request-id`. (Doc)
  - Errors can occur mid-stream after a 200 (SSE `error` event with `overloaded_error`); streams can contain `ping` events. (Doc)
  - Within one `anthropic-version`, Anthropic may add optional inputs, output values and new enum-like variants (e.g. new streaming event types), so clients must tolerate unknown fields/events. (Doc)
  - `stop_reason` values: `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, `refusal`, `model_context_window_exceeded`. (Doc)
  - `pause_turn`: a server-tool loop hit its iteration limit (default 10); append the content unchanged as an assistant message (no user message) and resend with the same tools, with a retry cap. It is never produced by client tools. (Doc)
  - `model_context_window_exceeded` is returned without a beta header on Sonnet 4.5 and newer; older models need beta header `model-context-window-exceeded-2025-08-26`. (Doc)
  - `end_turn` can occasionally be an empty 2-3 token response, especially after tool results; do not add text right after `tool_result` blocks and do not resend unchanged. (Doc)
  - Refusal: HTTP 200, `stop_details` has `category` (`cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms`), `explanation`, optional `recommended_model`; `stop_details` is null for other stop reasons. (Doc)
  - Billing: pre-output refusals are billed for `bio`, `frontier_llm`, `reasoning_extraction` but not `cyber`, `general_harms`; mid-stream refusals bill input plus streamed output. (Doc)
  - Server-side fallback: `fallbacks: "default"` plus beta header `server-side-fallback-2026-07-01` (Claude API and Google Cloud Anthropic-managed). Not supported on Bedrock (bedrock-mantle) or Foundry, where you use client-side fallback via SDK middleware. (Doc)
  - `reasoning_extraction` has no recommended fallback model: change the prompt (do not ask the model to output its reasoning; use thinking blocks). (Doc)
  - Bedrock (bedrock-mantle) does not support: Message Batches, MCP connector, server-side tools, Files/URL sources, Agent Skills, programmatic tool calling, Managed Agents, server-side fallback; model IDs are prefixed `anthropic.`. (Doc)
  - Bedrock regional endpoints carry a 10% premium; the global endpoint has none; inference profiles route across regions in a geography. (Doc)
  - Foundry: `model` is your deployment name; no Batches or server-side fallback; no `anthropic-ratelimit-*` headers (use Azure monitoring). (Doc)
  - Google Cloud has two offerings: Anthropic-managed (Claude API shape, rate limits by Anthropic) and Google-managed (Vertex shape, `anthropic_version` in body, limits by Google). (Doc)
  - Circuit breaker and graceful-degradation patterns are standard practice, not defined in the docs read. (Interp)
- **Kiến thức phải nhớ:**
  - Mã lỗi: 400 `invalid_request_error`, 401 `authentication_error`, 402 `billing_error`, 403 `permission_error`, 404 `not_found_error`, 409 `conflict_error`, 413 `request_too_large`, 429 `rate_limit_error`, 500 `api_error`, 504 `timeout_error`, 529 `overloaded_error`. (Doc)
  - 529 xảy ra khi lưu lượng cao của toàn bộ người dùng, tức là năng lực nền tảng, không phải quota của bạn. (Doc)
  - Chạm spend limit của chính org/workspace bạn trả về 400 `invalid_request_error`, không phải 429 (workspace Claude Code có thể là 429). (Doc)
  - 429 do trần chi tiêu hằng tháng của tier (`error.details.error_code = enforced_spend_limit_reached`) không có `retry-after` và tiếp tục lỗi cho đến khi được cấp lại quyền truy cập. (Doc)
  - SDK tự retry lỗi kết nối, rate limit và 5xx mặc định 2 lần với exponential backoff, tôn trọng `retry-after`; chỉnh qua `max_retries`. Python SDK timeout mặc định 10 phút, timeout cũng retry 2 lần. (Doc)
  - SDK ném `ValueError` với request non-streaming dự kiến quá khoảng 10 phút; dùng streaming hoặc Batches cho job dài. (Doc)
  - Kích thước request tối đa: Messages 128 MB, Token Counting 128 MB, Batch 256 MB, Files 500 MB; vượt thì 413. (Doc)
  - Mọi response có header `request-id` (cũng có trong body lỗi); hãy log để gửi support. Foundry thêm `apim-request-id`. (Doc)
  - Lỗi có thể xảy ra giữa stream sau khi đã 200 (SSE event `error` với `overloaded_error`); stream có thể chứa event `ping`. (Doc)
  - Trong cùng một `anthropic-version`, Anthropic có thể thêm input tùy chọn, giá trị output và biến thể enum mới (vd. event streaming mới), nên client phải chịu được field/event lạ. (Doc)
  - Các giá trị `stop_reason`: `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, `refusal`, `model_context_window_exceeded`. (Doc)
  - `pause_turn`: vòng lặp server-tool chạm giới hạn lặp (mặc định 10); append nội dung nguyên vẹn thành assistant message (không thêm user message) và gửi lại với cùng tools, có giới hạn số lần. Client tool không bao giờ sinh ra nó. (Doc)
  - `model_context_window_exceeded` trả về không cần beta header trên Sonnet 4.5 trở lên; model cũ cần header `model-context-window-exceeded-2025-08-26`. (Doc)
  - `end_turn` đôi khi là response rỗng 2-3 token, nhất là sau tool result; không thêm text ngay sau block `tool_result` và không gửi lại y nguyên. (Doc)
  - Refusal: HTTP 200, `stop_details` gồm `category` (`cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms`), `explanation`, `recommended_model` tùy chọn; `stop_details` là null với stop reason khác. (Doc)
  - Tính phí: refusal trước khi có output bị tính phí với `bio`, `frontier_llm`, `reasoning_extraction` nhưng không với `cyber`, `general_harms`; refusal giữa stream tính input cộng output đã stream. (Doc)
  - Server-side fallback: `fallbacks: "default"` cộng beta header `server-side-fallback-2026-07-01` (Claude API và Google Cloud Anthropic-managed). Không hỗ trợ trên Bedrock (bedrock-mantle) hay Foundry, ở đó dùng client-side fallback qua SDK middleware. (Doc)
  - `reasoning_extraction` không có model fallback khuyến nghị: đổi prompt (đừng bảo model xuất reasoning; dùng thinking block). (Doc)
  - Bedrock (bedrock-mantle) không hỗ trợ: Message Batches, MCP connector, server-side tools, Files/URL source, Agent Skills, programmatic tool calling, Managed Agents, server-side fallback; model ID có tiền tố `anthropic.`. (Doc)
  - Endpoint regional của Bedrock phụ thu 10%; endpoint global không phụ thu; inference profile định tuyến qua các region trong một khu vực địa lý. (Doc)
  - Foundry: `model` là tên deployment của bạn; không có Batches hay server-side fallback; không có header `anthropic-ratelimit-*` (dùng Azure monitoring). (Doc)
  - Google Cloud có hai dạng: Anthropic-managed (dạng Claude API, rate limit do Anthropic) và Google-managed (dạng Vertex, `anthropic_version` trong body, limit do Google). (Doc)
  - Circuit breaker và graceful degradation là thực hành chuẩn, không được định nghĩa trong docs đã đọc. (Interp)

**Failure triage table / Bảng phân loại lỗi**

| Signal / Tín hiệu | Retry same request? / Retry cùng request? | Remedy / Cách xử lý |
|---|---|---|
| 429 `rate_limit_error` + `retry-after` | Yes, after wait / Có, sau khi chờ | Backoff honoring header, smooth traffic, cache, queue / Backoff theo header, làm mượt traffic, cache, queue |
| 429 `enforced_spend_limit_reached` (no `retry-after`) | No / Không | Raise tier/cap, alert humans / Nâng tier/cap, báo người |
| 400 "reached your specified API usage limits" | No / Không | Raise or remove own limit / Nâng hoặc bỏ limit của mình |
| 529 `overloaded_error` | Yes, backoff / Có, backoff | Backoff, fallback model/region/platform |
| 500 / 504 | Yes, backoff / Có, backoff | Stream long requests, log `request-id` / Stream request dài, log `request-id` |
| 200 + `refusal` | No (same model) / Không (cùng model) | Fallback to another model; `reasoning_extraction`: rewrite prompt / Fallback model khác; `reasoning_extraction`: sửa prompt |
| 200 + `max_tokens` | No / Không | Raise `max_tokens` or continue / Tăng `max_tokens` hoặc tiếp tục |
| 200 + `model_context_window_exceeded` | No / Không | Compact/trim context; treat as truncated / Nén/cắt context; coi là bị cắt |
| 400 validation / 413 | No / Không | Fix request / split or Files API / Sửa request / tách hoặc dùng Files API |

- **Decision rule:** When you see intermittent 529 at peak traffic → choose exponential backoff with jitter plus a fallback model/region because 529 is platform capacity, not your quota. Trap: "request a rate limit increase". Likewise, `stop_reason: "refusal"` → fall back to a different model (server-side `fallbacks` where supported, client-side otherwise); trap: catching only `RateLimitError` or retrying the same model with backoff. For a failover to Bedrock/Foundry → check feature parity first; trap: assuming "same API".
- **Quy tắc quyết định:** Khi thấy 529 ngắt quãng lúc cao điểm → chọn exponential backoff có jitter cộng fallback model/region vì 529 là năng lực nền tảng, không phải quota của bạn. Bẫy: "xin tăng rate limit". Tương tự, `stop_reason: "refusal"` → fallback sang model khác (`fallbacks` phía server nếu được hỗ trợ, nếu không thì client-side); bẫy: chỉ bắt `RateLimitError` hoặc retry cùng model với backoff. Khi failover sang Bedrock/Foundry → kiểm tra feature parity trước; bẫy: tưởng "cùng API".
- **Decision rule:** `max_tokens` → continue or raise the limit; `model_context_window_exceeded` → compact/trim the input, because raising `max_tokens` will not help. `pause_turn` → resend the assistant content as-is with a loop cap. Trap: confusing the two stop reasons, or adding a "continue" user message.
- **Quy tắc quyết định:** `max_tokens` → tiếp tục hoặc tăng giới hạn; `model_context_window_exceeded` → nén/cắt input vì tăng `max_tokens` không giúp gì. `pause_turn` → gửi lại nội dung assistant nguyên vẹn, có giới hạn vòng lặp. Bẫy: nhầm hai stop reason, hoặc thêm user message "continue".

### [2.2] Scale and Throughput Management
### [2.2] Quản lý quy mô và throughput

- **Core idea:** Identify the binding constraint before choosing a fix. RPM-bound (many small requests): batch work, higher tier, Message Batches. ITPM-bound (big prompts): prompt caching. OTPM-bound: shorter output, spread load. Ramp-limit-bound (sudden growth): ramp gradually. Spend-cap-bound: it is a policy problem, not a retry problem.
- **Ý chính:** Xác định nút thắt thực sự trước khi chọn giải pháp. Bị RPM (nhiều request nhỏ): gộp việc, tier cao hơn, Message Batches. Bị ITPM (prompt lớn): prompt caching. Bị OTPM: output ngắn hơn, dàn tải. Bị ramp limit (tăng đột ngột): tăng dần. Bị spend cap: là vấn đề chính sách, không phải retry.
- **Core idea:** Rate limits use a token bucket (continuously replenished), so short bursts can trip a limit even when the per-minute average is fine (60 RPM may be enforced as 1 per second). Smooth the traffic instead of sending spikes.
- **Ý chính:** Rate limit dùng token bucket (nạp lại liên tục), nên burst ngắn có thể vượt limit dù trung bình theo phút vẫn ổn (60 RPM có thể bị áp như 1 request/giây). Hãy làm mượt traffic thay vì gửi dồn.
- **Core idea:** Prompt caching is a throughput lever: cache reads are excluded from ITPM, so a large repeated prefix costs little limit. Example: 2M ITPM at an 80% hit rate handles roughly 10M total input tokens per minute.
- **Ý chính:** Prompt caching là đòn bẩy throughput: cache read không tính vào ITPM, nên prefix lớn lặp lại tốn rất ít limit. Ví dụ: 2M ITPM với hit rate 80% xử lý khoảng 10M tổng input token mỗi phút.
- **Core idea:** Message Batches suit work with no latency requirement (nightly evals, bulk classification, backfills): 50% cheaper, separate rate limits, but up to 24 hours and no streaming. Multi-tenant isolation uses workspace limits so one tenant cannot starve others; backpressure means a bounded queue, a concurrency cap, and shedding or deferring low-priority work.
- **Ý chính:** Message Batches hợp với việc không cần độ trễ thấp (eval hằng đêm, phân loại hàng loạt, backfill): rẻ hơn 50%, rate limit riêng, nhưng tới 24 giờ và không streaming. Cô lập multi-tenant dùng workspace limit để một tenant không làm đói tenant khác; backpressure nghĩa là hàng đợi có giới hạn, trần concurrency, và loại bỏ/hoãn việc ưu tiên thấp.

- **Must-know facts:**
  - Limits are RPM, ITPM, OTPM per model class, using a token bucket. (Doc)
  - Only `input_tokens` + `cache_creation_input_tokens` count toward ITPM; `cache_read_input_tokens` do not. (Doc)
  - OTPM counts actual generated tokens; `max_tokens` does not count toward OTPM. (Doc)
  - Example limits, Sonnet 5.5: Start 4,000 RPM / 2M ITPM / 400K OTPM; Build 10,000 / 5M / 1M; Scale 13,000 / 10M / 2M. (Doc)
  - Monthly spend caps: Start $500, Build $1,000, Scale $200,000, Custom none; at the cap usage pauses until 00:00 UTC on the 1st. (Doc)
  - Ramp limit: 429 with `error.details.error_code = ramp_limit_exceeded`; wait `retry-after`, grow by at most one step per minute; Batches are exempt and cached reads do not count. (Doc)
  - Headers: `retry-after`, `anthropic-ratelimit-{requests,tokens,input-tokens,output-tokens}-{limit,remaining,reset}` (reset in RFC 3339), `anthropic-priority-*` for Priority Tier; `tokens-*` reflects the most restrictive limit; not every 429 has `retry-after`. (Doc)
  - Workspace limits: set per limiter type; if unset they equal the org limit; org limits always apply; unused share stays available to other workspaces; the Rate Limits API reads/sets them. (Doc)
  - Rate limits are shared across `inference_geo` values (`us` and `global` share one pool). Fast mode has separate dedicated limits and `anthropic-fast-*` headers. (Doc)
  - Batch: up to 100,000 requests or 256 MB per batch (whichever first); most finish within 1 hour; expire at 24 hours; results available 29 days after creation. (Doc)
  - Batch price is 50% of standard; result types include `succeeded`, `errored`, `canceled`, `expired` (expired is not billed); `custom_id` matches `^[a-zA-Z0-9_-]{1,64}$`. (Doc)
  - Match batch results by `custom_id`, not order. (Interp)
  - Batch rate limits are separate and shared across models: Start 1,000 RPM / 200,000 queued; Build 2,000 / 300,000; Scale 4,000 / 500,000. (Doc)
  - With batches use the 1-hour cache TTL (processing can exceed 5 minutes); `max_tokens: 0` pre-warming is not supported inside a batch. (Doc)
  - Batches are not ZDR-eligible (29-day retention); not supported on Foundry or Bedrock. (Doc)
  - Cache: TTL 5 min default (refreshed on use), 1 hour optional (`"ttl":"1h"`); write multipliers 1.25x (5m) and 2x (1h); read 0.1x (0.05x on Opus 5.5/Sonnet 5.5; 0.025x on Fable/Mythos 5.1/5.2); up to 4 explicit breakpoints; order tools, system, messages, and a change invalidates that level and later ones. (Doc)
  - Minimum cacheable length varies by model (512/1,024/2,048/4,096 tokens); shorter prompts run uncached without error. (Doc)
  - Caches are isolated per workspace on Claude API/Platform on AWS/Foundry but per organization on Google-managed and Bedrock. (Doc)
  - Queueing by estimated tokens rather than request count is sound practice. (Interp)
- **Kiến thức phải nhớ:**
  - Limit gồm RPM, ITPM, OTPM theo nhóm model, dùng token bucket. (Doc)
  - Chỉ `input_tokens` + `cache_creation_input_tokens` tính vào ITPM; `cache_read_input_tokens` không tính. (Doc)
  - OTPM tính token thực tế sinh ra; `max_tokens` không tính vào OTPM. (Doc)
  - Limit ví dụ, Sonnet 5.5: Start 4.000 RPM / 2M ITPM / 400K OTPM; Build 10.000 / 5M / 1M; Scale 13.000 / 10M / 2M. (Doc)
  - Trần chi tiêu tháng: Start $500, Build $1.000, Scale $200.000, Custom không giới hạn; chạm trần thì tạm dừng đến 00:00 UTC ngày 1. (Doc)
  - Ramp limit: 429 với `error.details.error_code = ramp_limit_exceeded`; chờ `retry-after`, tăng tối đa một bước mỗi phút; Batches được miễn và cached read không tính. (Doc)
  - Header: `retry-after`, `anthropic-ratelimit-{requests,tokens,input-tokens,output-tokens}-{limit,remaining,reset}` (reset theo RFC 3339), `anthropic-priority-*` cho Priority Tier; `tokens-*` phản ánh limit chặt nhất; không phải 429 nào cũng có `retry-after`. (Doc)
  - Workspace limit: đặt theo từng loại limiter; nếu không đặt thì bằng limit của org; limit org luôn áp dụng; phần chưa dùng vẫn dành cho workspace khác; Rate Limits API đọc/đặt được. (Doc)
  - Rate limit dùng chung giữa các giá trị `inference_geo` (`us` và `global` chung một pool). Fast mode có limit riêng và header `anthropic-fast-*`. (Doc)
  - Batch: tối đa 100.000 request hoặc 256 MB mỗi batch (cái nào tới trước); đa số xong trong 1 giờ; hết hạn sau 24 giờ; kết quả có sẵn 29 ngày kể từ lúc tạo. (Doc)
  - Giá batch bằng 50% giá chuẩn; các loại kết quả gồm `succeeded`, `errored`, `canceled`, `expired` (expired không bị tính phí); `custom_id` khớp `^[a-zA-Z0-9_-]{1,64}$`. (Doc)
  - Khớp kết quả batch bằng `custom_id`, không theo thứ tự. (Interp)
  - Rate limit của batch riêng và dùng chung giữa các model: Start 1.000 RPM / 200.000 queued; Build 2.000 / 300.000; Scale 4.000 / 500.000. (Doc)
  - Với batch dùng cache TTL 1 giờ (xử lý có thể quá 5 phút); pre-warm `max_tokens: 0` không được hỗ trợ trong batch. (Doc)
  - Batch không đủ điều kiện ZDR (lưu 29 ngày); không hỗ trợ trên Foundry hay Bedrock. (Doc)
  - Cache: TTL mặc định 5 phút (làm mới khi dùng), tùy chọn 1 giờ (`"ttl":"1h"`); hệ số ghi 1,25x (5m) và 2x (1h); đọc 0,1x (0,05x trên Opus 5.5/Sonnet 5.5; 0,025x trên Fable/Mythos 5.1/5.2); tối đa 4 breakpoint tường minh; thứ tự tools, system, messages, thay đổi làm mất hiệu lực cấp đó và các cấp sau. (Doc)
  - Độ dài tối thiểu để cache tùy model (512/1.024/2.048/4.096 token); prompt ngắn hơn chạy không cache và không báo lỗi. (Doc)
  - Cache cô lập theo workspace trên Claude API/Platform on AWS/Foundry nhưng theo organization trên Google-managed và Bedrock. (Doc)
  - Xếp hàng theo ước lượng token thay vì số request là thực hành hợp lý. (Interp)

- **Decision rule:** When nightly bulk work has no latency SLA → choose Message Batches (50% cheaper, own limits, up to 24h). Trap: using Batches for interactive UX, or assuming ordered results or a guaranteed under-1-hour finish. When ITPM-bound with a large repeated prefix → prompt caching; trap: buying more RPM. When 429s appear right after launch while under limits → ramp limit, so ramp gradually; trap: tier upgrade only. One tenant starving others → workspace limits and per-tenant quotas.
- **Quy tắc quyết định:** Khi việc bulk ban đêm không có SLA độ trễ → chọn Message Batches (rẻ 50%, limit riêng, tới 24h). Bẫy: dùng Batches cho UX tương tác, hoặc giả định kết quả theo thứ tự hay chắc chắn xong dưới 1 giờ. Khi bị ITPM với prefix lớn lặp lại → prompt caching; bẫy: mua thêm RPM. Khi 429 xuất hiện ngay sau launch dù chưa chạm limit → ramp limit, hãy tăng dần; bẫy: chỉ nâng tier. Một tenant làm đói tenant khác → workspace limit và quota theo tenant.

### [2.3] Production MCP and Change Management
### [2.3] MCP production và quản lý thay đổi

- **Core idea:** Claude's MCP connector lets the Messages API reach a remote MCP server with no client code: you pass `mcp_servers` plus a matching `mcp_toolset` entry in `tools`. It only supports tool calls (not resources/prompts) and needs a public HTTP server (Streamable HTTP or SSE); local STDIO servers need your own client (or an MCP tunnel on private networks).
- **Ý chính:** MCP connector của Claude cho phép Messages API gọi tới MCP server từ xa mà không cần code client: bạn truyền `mcp_servers` cùng mục `mcp_toolset` tương ứng trong `tools`. Nó chỉ hỗ trợ tool call (không có resources/prompts) và cần server HTTP công khai (Streamable HTTP hoặc SSE); server STDIO cục bộ cần client của bạn (hoặc MCP tunnel cho mạng riêng).
- **Core idea:** Remote MCP authentication follows OAuth 2.1: the MCP server is a resource server that publishes Protected Resource Metadata and validates token audience. It must never pass the client's token through to upstream APIs (confused-deputy).
- **Ý chính:** Xác thực MCP từ xa theo OAuth 2.1: MCP server là resource server, công bố Protected Resource Metadata và kiểm tra audience của token. Tuyệt đối không chuyển tiếp token của client sang API upstream (confused-deputy).
- **Core idea:** Treat tool names, descriptions and input schemas as a public contract. Additive optional parameters are safe; renames, removals and type changes are breaking, so ship a new versioned tool, run both during a deprecation window, and remember that tool-definition changes invalidate the prompt cache.
- **Ý chính:** Coi tên tool, mô tả và input schema như hợp đồng công khai. Thêm tham số tùy chọn là an toàn; đổi tên, xóa, đổi kiểu là breaking, nên phát hành tool mới có version, chạy song song trong thời gian deprecation, và nhớ rằng đổi tool definition làm mất cache prompt.
- **Core idea:** Model migration is a lifecycle (Active, Legacy, Deprecated, Retired) and retired models fail. Migration testing must cover request shape, not just quality: newer models reject old parameters with 400s. Prompts need the same discipline: versioned artifacts, golden-set regression eval, canary rollout, instant rollback, pinned model IDs.
- **Ý chính:** Migration model là một vòng đời (Active, Legacy, Deprecated, Retired) và model đã retired sẽ lỗi. Test migration phải bao gồm cả dạng request, không chỉ chất lượng: model mới từ chối tham số cũ bằng 400. Prompt cũng cần kỷ luật tương tự: artifact có version, regression eval trên golden set, canary rollout, rollback tức thì, ghim model ID.

- **Must-know facts:**
  - MCP connector is beta; headers `mcp-client-2026-09-15` / `mcp-client-2025-11-20` (older `mcp-client-2025-04-04` deprecated). `mcp_servers` items: type url, url, name, `authorization_token`; supports allowlist/denylist, per-tool config, multiple servers, OAuth Bearer tokens; not ZDR-eligible. (Doc)
  - `stop_reason: "tool_use"` may include `mcp_tool_use`/`server_tool_use` blocks awaiting results; resend with the same `tools` and `mcp_servers`; text mixed with `tool_result` blocks gives 400. (Doc)
  - MCP auth spec (2025-06-18): optional; HTTP transports SHOULD follow it, STDIO SHOULD NOT (use env credentials). Server is an OAuth 2.1 resource server and MUST implement Protected Resource Metadata (RFC 9728) with `authorization_servers`. (Doc)
  - A 401 MUST carry `WWW-Authenticate` pointing to the metadata; clients use AS metadata (RFC 8414); Dynamic Client Registration (RFC 7591) SHOULD be supported. (Doc)
  - Client MUST send `resource` (RFC 8707) in authorization and token requests and MUST use PKCE; token goes in the `Authorization: Bearer` header on every request, never in the query string. (Doc)
  - Server MUST validate audience and MUST NOT accept or pass through tokens meant for other resources; 401 invalid/expired token, 403 insufficient scope, 400 malformed. (Doc)
  - Lifecycle states Active, Legacy, Deprecated, Retired; at least 60 days notice for publicly released models; audit usage via Console Usage, Export CSV by key and model. (Doc)
  - Example: `claude-sonnet-4-5-20250929` deprecated 2026-09-30, retirement 2026-11-30, replacement `claude-sonnet-5-5`; `claude-haiku-4-5-20251001` retirement not sooner than 2026-10-15; `claude-opus-4-5-20251101` not sooner than 2026-11-24. (Doc)
  - Those dates apply to Anthropic-operated platforms; Bedrock and Google-managed set their own schedules. (Doc)
  - Breaking changes on newer models: no assistant prefill (400) on Claude 4.6+; `thinking:{type:"enabled"}` 400 on 4.7+ (use adaptive + effort); forced `tool_choice` any/tool 400 on Fable 5.2/5.1, Mythos, Opus 5.5, Sonnet 5.5 (auto/none accepted); Sonnet 5.5 rejects `thinking:disabled`. (Doc)
  - API version 2026-10-21 removes `temperature`/`top_p`/`top_k` (400); a `text` block with non-empty `citations` in a user message returns 400. (Doc)
  - Google Cloud Anthropic-managed lacks API keys and MCP tunnels but has the MCP connector (beta). (Doc)
  - Prompt versioning, canary rollout, rollback by flag, pinning explicit model IDs, additive-only tool schema changes, and gateway centralisation (auth, limits, routing, fallback, logging, still honoring platform differences) are practice, with no official doc read. (Interp)
- **Kiến thức phải nhớ:**
  - MCP connector đang beta; header `mcp-client-2026-09-15` / `mcp-client-2025-11-20` (`mcp-client-2025-04-04` cũ đã deprecated). Mục `mcp_servers`: type url, url, name, `authorization_token`; hỗ trợ allowlist/denylist, cấu hình theo tool, nhiều server, OAuth Bearer token; không đủ điều kiện ZDR. (Doc)
  - `stop_reason: "tool_use"` có thể chứa block `mcp_tool_use`/`server_tool_use` đang chờ kết quả; gửi lại với cùng `tools` và `mcp_servers`; trộn text với block `tool_result` gây 400. (Doc)
  - MCP auth spec (2025-06-18): tùy chọn; transport HTTP NÊN theo, STDIO KHÔNG NÊN (dùng credential qua env). Server là OAuth 2.1 resource server và PHẢI cài Protected Resource Metadata (RFC 9728) có `authorization_servers`. (Doc)
  - 401 PHẢI kèm `WWW-Authenticate` trỏ tới metadata; client dùng AS metadata (RFC 8414); NÊN hỗ trợ Dynamic Client Registration (RFC 7591). (Doc)
  - Client PHẢI gửi `resource` (RFC 8707) trong request authorization và token, PHẢI dùng PKCE; token đặt trong header `Authorization: Bearer` ở mọi request, không bao giờ trong query string. (Doc)
  - Server PHẢI kiểm tra audience và KHÔNG ĐƯỢC nhận hay chuyển tiếp token dành cho resource khác; 401 token sai/hết hạn, 403 thiếu scope, 400 request sai dạng. (Doc)
  - Vòng đời Active, Legacy, Deprecated, Retired; thông báo trước ít nhất 60 ngày với model phát hành công khai; kiểm tra mức dùng qua Console Usage, Export CSV theo key và model. (Doc)
  - Ví dụ: `claude-sonnet-4-5-20250929` deprecated 2026-09-30, retire 2026-11-30, thay thế `claude-sonnet-5-5`; `claude-haiku-4-5-20251001` retire không sớm hơn 2026-10-15; `claude-opus-4-5-20251101` không sớm hơn 2026-11-24. (Doc)
  - Các mốc này áp dụng cho nền tảng do Anthropic vận hành; Bedrock và Google-managed tự đặt lịch. (Doc)
  - Thay đổi breaking trên model mới: không còn assistant prefill (400) từ Claude 4.6+; `thinking:{type:"enabled"}` 400 từ 4.7+ (dùng adaptive + effort); `tool_choice` ép buộc any/tool 400 trên Fable 5.2/5.1, Mythos, Opus 5.5, Sonnet 5.5 (auto/none vẫn nhận); Sonnet 5.5 từ chối `thinking:disabled`. (Doc)
  - API version 2026-10-21 bỏ `temperature`/`top_p`/`top_k` (400); block `text` có `citations` khác rỗng trong user message trả 400. (Doc)
  - Google Cloud Anthropic-managed không có API key và MCP tunnel nhưng có MCP connector (beta). (Doc)
  - Versioning prompt, canary rollout, rollback bằng flag, ghim model ID tường minh, chỉ thay đổi tool schema theo hướng additive, và gateway tập trung (auth, limit, routing, fallback, logging, vẫn phải tôn trọng khác biệt nền tảng) là thực hành chung, chưa đọc doc chính thức. (Interp)

- **Decision rule:** When Claude must reach a remote tool server from the API without client code → use the MCP connector (`mcp_servers` + `mcp_toolset`, beta header) because it is the built-in path; trap: expecting resources/prompts, local STDIO servers, or using it on Bedrock. For remote MCP auth → OAuth 2.1 resource server with RFC 9728 metadata, audience-validated tokens, PKCE and `resource`; trap: forwarding the client's token upstream, tokens in query strings, a shared static key. When a model retirement is announced → test the candidate on an eval set including request-shape breakage (prefill, thinking, `tool_choice`, sampling params), canary, keep rollback, pin explicit IDs; trap: swapping the model string in prod and watching. Prompt change → version, regression eval, progressive rollout; trap: editing in place.
- **Quy tắc quyết định:** Khi Claude cần chạm tới tool server từ xa qua API mà không có code client → dùng MCP connector (`mcp_servers` + `mcp_toolset`, beta header) vì đây là đường có sẵn; bẫy: mong có resources/prompts, server STDIO cục bộ, hoặc dùng trên Bedrock. Với auth MCP từ xa → OAuth 2.1 resource server có metadata RFC 9728, token kiểm tra audience, PKCE và `resource`; bẫy: chuyển token của client lên upstream, token trong query string, key tĩnh dùng chung. Khi có thông báo model retire → test ứng viên trên eval set gồm cả lỗi dạng request (prefill, thinking, `tool_choice`, tham số sampling), canary, giữ rollback, ghim ID tường minh; bẫy: đổi chuỗi model trên prod rồi quan sát. Đổi prompt → version, regression eval, rollout dần; bẫy: sửa tại chỗ.

### [2.4] Retrieval and Knowledge Grounding at Scale
### [2.4] Truy xuất và knowledge grounding ở quy mô lớn

- **Core idea:** Classic RAG (embed, retrieve top-k, stuff into the prompt) is cheap, fast and predictable, good for large stable corpora and single-hop questions. Agentic search (the model issues repeated tool queries, reads, reformulates) handles multi-hop, ambiguous, code/structured and fresh data, at higher latency, token cost and variance. Anthropic notes that under about 200,000 tokens (about 500 pages) you can skip RAG and put the whole knowledge base in the prompt with caching.
- **Ý chính:** RAG cổ điển (embed, lấy top-k, nhét vào prompt) rẻ, nhanh, dễ dự đoán, hợp kho tri thức lớn ổn định và câu hỏi một bước. Agentic search (model gọi tool truy vấn lặp lại, đọc, đặt lại truy vấn) xử lý tốt câu multi-hop, mơ hồ, code/dữ liệu có cấu trúc và dữ liệu mới, đổi lại độ trễ, chi phí token và độ biến thiên cao hơn. Anthropic lưu ý dưới khoảng 200.000 token (khoảng 500 trang) có thể bỏ RAG, đưa cả kho vào prompt kèm caching.
- **Core idea:** Quality comes from a pipeline: hybrid search (dense vectors for meaning plus BM25 for exact IDs, error codes, names), then reranking (retrieve wide, e.g. top-150, keep narrow, e.g. top-20), plus Contextual Retrieval (prepend LLM-generated chunk context before embedding and BM25), so chunks like "revenue grew 3%" stay interpretable.
- **Ý chính:** Chất lượng đến từ cả pipeline: hybrid search (vector dense cho ngữ nghĩa cộng BM25 cho ID chính xác, mã lỗi, tên), rồi rerank (lấy rộng, vd. top-150, giữ hẹp, vd. top-20), cộng Contextual Retrieval (thêm ngữ cảnh chunk do LLM sinh trước khi embed và BM25), để những chunk như "doanh thu tăng 3%" vẫn hiểu được.
- **Core idea:** Grounding means verifiable output: use the Citations feature or `search_result` blocks (API-validated pointers) rather than asking in prose to "quote sources"; give Claude permission to say "I don't know"; restrict to provided documents; for long documents extract quotes first; add a verification pass. These reduce but do not eliminate hallucination.
- **Ý chính:** Grounding nghĩa là output kiểm chứng được: dùng tính năng Citations hoặc block `search_result` (con trỏ được API kiểm tra) thay vì xin trong prompt "hãy trích nguồn"; cho phép Claude nói "tôi không biết"; giới hạn trong tài liệu được cung cấp; với tài liệu dài hãy trích dẫn nguyên văn trước; thêm bước verify. Các cách này giảm nhưng không loại bỏ hallucination.
- **Core idea:** Diagnose retrieval failures by stage and fix the first failing one: (1) ingestion/parsing, (2) chunking, (3) indexing/embedding, (4) first-stage retrieval (recall@k), (5) fusion/rerank, (6) context assembly, (7) generation (faithfulness), (8) citation. Do not tune the prompt for a retrieval miss.
- **Ý chính:** Chẩn đoán lỗi truy xuất theo giai đoạn và sửa giai đoạn lỗi đầu tiên: (1) ingestion/parsing, (2) chunking, (3) indexing/embedding, (4) truy xuất tầng một (recall@k), (5) fusion/rerank, (6) lắp ráp context, (7) generation (faithfulness), (8) citation. Đừng chỉnh prompt cho lỗi retrieval miss.

- **Must-know facts:**
  - Contextual Retrieval: contextual embeddings cut top-20 retrieval failures by 35% (5.7% to 3.7%); plus contextual BM25 49% (to 2.9%); plus reranking 67% (to 1.9%). Top-20 beats top-10 and top-5; rerank from top-150 to top-20. (Doc)
  - One-time cost about $1.02 per million document tokens (800-token chunks, 8k-token docs); prompt caching cuts latency over 2x and cost up to 90%. (Doc)
  - Anthropic offers no embedding model; Voyage AI is recommended (`voyage-4-large`/`voyage-4`/`voyage-4-lite`, `voyage-code-4`, `voyage-law-2`, `voyage-finance-2`, `voyage-context-4`; rerankers `rerank-3`, `rerank-3-lite`). Set `input_type` to `query` or `document` and never omit it; embeddings are normalized so cosine equals dot product. (Doc)
  - Citations: enable with `citations: {enabled: true}` on each document; you cannot mix enabled and disabled docs in one request. (Doc)
  - Plain text and PDF are chunked into sentences; custom content documents are not chunked further. Locations: char indices (plain text, 0-indexed), page numbers (PDF, 1-indexed), content block indices (custom content). Claude cannot cite images in PDFs. (Doc)
  - `cited_text` does not count toward output tokens; citation pointers are guaranteed valid; toggling citations invalidates the cached tools level. (Doc)
  - Citations are incompatible with structured outputs (`output_config.format`): combining returns 400. (Doc)
  - To cite your own RAG chunks: use plain text documents (sentence-level) or custom content documents (no re-chunking), or `search_result` blocks (`type`, `source`, `title`, `content` array, optional `citations.enabled`) returned from a custom tool or placed top-level in a user message; all search results in a request share the same citations setting; `source` can be a URL or an identifier like `kb://article-1234`. (Doc)
  - Hallucination reduction: allow "I don't know"; for long docs (over 20k tokens) extract word-for-word quotes first; verify each claim with a supporting quote and retract if none; best-of-N consistency; restrict to provided documents. (Doc)
  - Chunk size is a recall/precision trade-off; Anthropic's example uses chunks of a few hundred tokens. (Doc)
  - No official statement was found on the hybrid fusion method (RRF etc.), a "best" chunk size, or an agentic-search-vs-RAG decision table. (Unverified)
  - The agentic-search-vs-RAG split, the eight-stage diagnostic framework, and confidence signals (cited vs uncited, retrieval score margin, self-consistency across N samples) are engineering interpretation. (Interp)
- **Kiến thức phải nhớ:**
  - Contextual Retrieval: contextual embeddings giảm 35% lỗi retrieval top-20 (5,7% xuống 3,7%); thêm contextual BM25 giảm 49% (xuống 2,9%); thêm reranking giảm 67% (xuống 1,9%). Top-20 tốt hơn top-10 và top-5; rerank từ top-150 xuống top-20. (Doc)
  - Chi phí một lần khoảng $1,02 cho mỗi triệu token tài liệu (chunk 800 token, tài liệu 8k token); prompt caching giảm độ trễ hơn 2 lần và chi phí tới 90%. (Doc)
  - Anthropic không có model embedding; khuyên dùng Voyage AI (`voyage-4-large`/`voyage-4`/`voyage-4-lite`, `voyage-code-4`, `voyage-law-2`, `voyage-finance-2`, `voyage-context-4`; reranker `rerank-3`, `rerank-3-lite`). Đặt `input_type` là `query` hoặc `document` và không bao giờ bỏ trống; embedding đã chuẩn hóa nên cosine bằng dot product. (Doc)
  - Citations: bật bằng `citations: {enabled: true}` trên từng document; không trộn document bật và tắt trong một request. (Doc)
  - Plain text và PDF được chia thành câu; custom content document không bị chia thêm. Vị trí: chỉ số ký tự (plain text, từ 0), số trang (PDF, từ 1), chỉ số content block (custom content). Claude không cite được ảnh trong PDF. (Doc)
  - `cited_text` không tính vào output token; con trỏ citation đảm bảo hợp lệ; bật/tắt citations làm mất cache ở cấp tools. (Doc)
  - Citations không tương thích với structured outputs (`output_config.format`): kết hợp trả 400. (Doc)
  - Để cite chunk RAG của bạn: dùng plain text document (cấp câu) hoặc custom content document (không chia lại), hoặc block `search_result` (`type`, `source`, `title`, mảng `content`, `citations.enabled` tùy chọn) trả về từ custom tool hoặc đặt ở top-level trong user message; mọi search result trong một request dùng chung cài đặt citations; `source` có thể là URL hoặc định danh như `kb://article-1234`. (Doc)
  - Giảm hallucination: cho phép "I don't know"; với tài liệu dài (trên 20k token) trích nguyên văn trước; verify từng claim bằng trích dẫn hỗ trợ và rút lại nếu không có; best-of-N consistency; giới hạn trong tài liệu được cung cấp. (Doc)
  - Kích thước chunk là đánh đổi recall/precision; ví dụ của Anthropic dùng chunk vài trăm token. (Doc)
  - Không tìm thấy phát biểu chính thức về phương pháp fusion của hybrid (RRF...), kích thước chunk "tốt nhất", hay bảng quyết định agentic-search-vs-RAG. (Unverified)
  - Cách chia agentic search vs RAG, khung chẩn đoán tám giai đoạn, và tín hiệu độ tin cậy (có/không citation, chênh lệch retrieval score, self-consistency qua N mẫu) là suy luận kỹ thuật. (Interp)

- **Decision rule:** When exact identifiers/error codes/SKUs are missing from results → add BM25/lexical (hybrid) because dense vectors blur exact tokens. Trap: a bigger embedding model. When the gold chunk is retrieved but falls outside the final top-k → add or tune a reranker (retrieve about 150, keep about 20). Trap: re-chunking. When you need verifiable sources → Citations or `search_result` blocks. Trap: pairing citations with structured outputs (400), mixing enabled/disabled docs, expecting image citations. When you need JSON plus citations → post-process or run a second pass (Interp). A silent recall loss with no errors → check `input_type` omitted or different models for index and query.
- **Quy tắc quyết định:** Khi ID/mã lỗi/SKU chính xác không xuất hiện trong kết quả → thêm BM25/lexical (hybrid) vì vector dense làm mờ token chính xác. Bẫy: dùng embedding model lớn hơn. Khi chunk đúng đã được lấy nhưng rơi ra ngoài top-k cuối → thêm hoặc tinh chỉnh reranker (lấy khoảng 150, giữ khoảng 20). Bẫy: chunk lại. Khi cần nguồn kiểm chứng được → Citations hoặc block `search_result`. Bẫy: ghép citations với structured outputs (400), trộn document bật/tắt, mong cite ảnh. Khi cần JSON kèm citations → hậu xử lý hoặc chạy lượt thứ hai (Interp). Recall tụt âm thầm không báo lỗi → kiểm tra `input_type` bị bỏ hoặc dùng khác model giữa index và query.

### Self-check / Tự kiểm tra

1. Q: A 200 response has `stop_reason: refusal`. What now? A: Inspect `stop_details.category`, discard partial output, retry on a different model (fallback), not the same one.
   Q: Một response 200 có `stop_reason: refusal`. Làm gì? Đ: Xem `stop_details.category`, bỏ output dở, retry bằng model khác (fallback), không dùng lại cùng model.
2. Q: Which 429 has no `retry-after` and must not be retried blindly? A: The tier spend-cap 429 (`enforced_spend_limit_reached`).
   Q: 429 nào không có `retry-after` và không được retry mù? Đ: 429 do trần chi tiêu của tier (`enforced_spend_limit_reached`).
3. Q: What does hitting your own workspace spend limit return? A: 400 `invalid_request_error`.
   Q: Chạm spend limit của workspace mình trả về gì? Đ: 400 `invalid_request_error`.
4. Q: Why does prompt caching raise effective throughput? A: `cache_read_input_tokens` are excluded from ITPM; only uncached input and cache writes count.
   Q: Vì sao prompt caching tăng throughput hiệu dụng? Đ: `cache_read_input_tokens` không tính vào ITPM; chỉ input không cache và cache write được tính.
5. Q: Batch limits, price, expiry? A: 100,000 requests or 256 MB; 50% price; expires at 24h (expired items not billed); results kept 29 days.
   Q: Giới hạn, giá, hết hạn của Batch? Đ: 100.000 request hoặc 256 MB; giá 50%; hết hạn sau 24h (mục expired không tính phí); kết quả giữ 29 ngày.
6. Q: Which stop reason means the context window filled, and the fix? A: `model_context_window_exceeded`; reduce/compact input, not just raise `max_tokens`.
   Q: Stop reason nào nghĩa là context window đầy, và cách sửa? Đ: `model_context_window_exceeded`; giảm/nén input, không chỉ tăng `max_tokens`.
7. Q: Can citations combine with `output_config.format`? A: No, the API returns an error (400).
   Q: Citations có dùng chung với `output_config.format` được không? Đ: Không, API trả lỗi (400).
8. Q: Three things a remote MCP server must do under the auth spec? A: Publish Protected Resource Metadata (RFC 9728), return 401 with `WWW-Authenticate`, validate token audience and never pass tokens through upstream.
   Q: Ba việc MCP server từ xa phải làm theo auth spec? Đ: Công bố Protected Resource Metadata (RFC 9728), trả 401 kèm `WWW-Authenticate`, kiểm tra audience của token và không chuyển tiếp token lên upstream.
9. Q: Retrieval-failure reduction from contextual embeddings + BM25 + reranking? A: 67% (5.7% to 1.9%) for top-20 chunks.
   Q: Mức giảm lỗi retrieval khi dùng contextual embeddings + BM25 + reranking? Đ: 67% (5,7% xuống 1,9%) với top-20 chunk.
10. Q: Failing over from the Claude API to Bedrock: name two things that may break. A: Message Batches and MCP connector are unsupported; `fallbacks` unsupported; model IDs and auth differ.
    Q: Failover từ Claude API sang Bedrock: nêu hai thứ có thể hỏng. Đ: Message Batches và MCP connector không được hỗ trợ; `fallbacks` không hỗ trợ; model ID và auth khác.

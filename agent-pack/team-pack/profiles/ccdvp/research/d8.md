## (a) Key concepts per skill

### Skill 1 – Parallel Agent Orchestration for Engineering Work

- **Isolation first.** Parallel agents that edit the same checkout collide. Git worktrees give each session its own files and branch while sharing history and remote. Subagents can each get a temporary worktree (`isolation: worktree`). **[doc]**
- **Pick the parallelism primitive by who coordinates and whether workers touch the same files.** Subagents (Claude delegates inside one session, results return as summary); agent view / background sessions (you dispatch, check later); agent teams (lead + teammates, shared task list, messaging; experimental, off by default); dynamic workflows (a script holds the plan); `/batch` (splits one large change into 5 to 30 worktree-isolated subagents, each opening a PR). **[doc]**
- **Task decomposition rule of thumb.** Self-contained units with a clear deliverable (a function, a test file, a review). Too small means coordination overhead; too large means long unchecked runs and wasted effort. Docs suggest 3-5 teammates to start and 5-6 tasks per teammate. **[doc]**
- **Merge and conflict strategy.** Docs only say: isolate with worktrees; for agent teams (no worktree isolation) partition work so each teammate owns different files; two teammates editing one file leads to overwrites. Each worktree has its own branch, so integration is done via PRs/merges like any other branch. The docs do not prescribe a rebase/merge-queue algorithm; sequencing, dependency ordering and merge-queue choice below are **[interp]**.
- **Fleet failure modes visible in telemetry.** Token/cost multiplication (every parallel session or teammate has its own context), runaway loops (`--max-turns` / budget caps), API errors/retries/refusals, tool rejections, concurrency limits (20 concurrent subagents by default), stuck tasks and lagging task status in agent teams. OTel gives per-model cost/tokens, `api_error`, `api_refusal`, `tool_decision`, `tool_result` events. **[doc]** Mapping symptoms to causes is **[interp]**.
- **Reviewer independence.** A fresh reviewer that has not seen how code was written helps; delegating the same task to a subagent does not make the answer smarter. A reviewer asked to find problems will always find something, so bound it ("skip style"). **[doc best-practices]**

### Skill 2 – Verification and AI Code Review Operations

- **Premise:** generation speed outpaces human review, so verification becomes the bottleneck. Add automated verification layers, but roll them out as non-blocking first. **[interp, consistent with docs]**
- **Official Code Review service** (Team/Enterprise, GitHub only): several agents examine the diff in parallel, a verification step filters false positives, findings are deduplicated and ranked, then posted as inline comments + summary + a check run named "Claude Code Review". **It never approves or blocks a PR and the check run never concludes as failure.** **[doc]**
- **Severity:** Important (red, a bug to fix before merge), Nit (yellow), Pre-existing (purple). **[doc]**
- **Gating is your own CI's job.** The check run's last Details line is an HTML comment `<!-- bughunter-severity: {"nit":1,"normal":2,"pre_existing":0} -->`; `normal` = count of Important. Missing line = no verdict, not zero findings. Titles "Code review not repeated" / "no new changes" need special handling. **[doc]**
- **Shadow-mode-then-gate pattern.** Docs give the building blocks: repository-level "Review runs" setting (Once after PR creation / After every push / Manual `@claude review`), a pilot to estimate cost, REVIEW.md to tune severity and nit caps, analytics for "Code Review feedback" (auto-resolved comments) and findings by severity. The explicit phrase "shadow mode" is **not** used in the official docs I read; the sequence observe → measure → calibrate vs. humans → gate is **[interp]** supported by **[3P]** Uber uReview (phased rollout, precision tracking, per-category confidence thresholds, human baseline of 51% of human comments addressed).
- **Calibration levers [doc]:** review level (Quick/Standard/Deep), REVIEW.md (redefine what Important means, cap nits, skip generated paths, require `file:line` evidence), CLAUDE.md rules, resolve thread = dismiss, repeated same finding → add a REVIEW.md rule.
- **Human oversight design [interp + doc]:** Docs state "the decision to merge stays with your team"; branch protection can require conversation resolution; REVIEW.md is read from the base/default branch, never from the PR, so an author cannot weaken the reviewer in the same PR.
- **Caveat [doc]:** "A review with no findings doesn't mean your code is error-free or secure." Review reads code, does not build or run it.

### Skill 3 – Unattended and Event-Driven Agent Operations

- **Four scheduling surfaces [doc]:** cloud scheduled tasks (formerly routines; Anthropic cloud, schedule/API/GitHub triggers, research preview, min interval 1 hour); Desktop scheduled tasks (your machine, local files); GitHub Actions / GitLab CI (your CI, event or cron); `/loop` (session-scoped, needs open session, 1-minute minimum, recurring tasks expire after 7 days).
- **Goal-driven:** `/goal <condition>` keeps working until a separate small fast evaluator model judges the condition met/impossible; one goal per session; evaluator judges only what appears in the transcript (cannot run commands); bound it with "or stop after N turns"; works with `-p`. **[doc]**
- **Event-driven responders [doc]:** GitHub Action in automation mode (`prompt` input) on any event; cloud task API trigger (HTTP POST to `/fire` with bearer token, optional `text` payload e.g. alert body); GitHub-event triggers (PR/release filters).
- **Unattended safety checklist [doc best-practices]:** (1) knows what done looks like, (2) can check its own work, (3) limited scope (permission rules, `dontAsk`, sandbox, worktree, single pushable branch), (4) stopper (`--max-turns`, `--max-budget-usd`, spend limit), (5) result goes somewhere and a person signs off on the irreversible step.
- **Checkpointing / notification / escalation:** Docs give mechanisms (session `--resume`/`--continue`, stream-json events, `permission_denials`, hooks `Notification`/`Stop`/`TaskCompleted`, `/goal` check-ins, cloud run history, PR comments). The overall escalation-design pattern (when to page a human, how to checkpoint partial progress) is **[interp]**.
- **CI incident first response [interp]:** docs don't have a page titled "CI/CD incident first response"; the pieces are an alert-triggered API fire or CI-failure event, read-only/diagnostic tools, a `claude/` branch or PR as the output, human approval for remediation.

### Skill 4 – Organization-Wide Coding Agent Configuration

- **Managed settings sit above everything** (managed > `--settings` > project local > shared project > user). Delivery: server-managed (claude.ai console, polled hourly), MDM/OS policy (macOS plist, Windows HKLM, checked every 30 min), file (`managed-settings.json` + `managed-settings.d/`). Lists merge across scopes; developers can extend but not remove managed `permissions.deny`. **[doc]**
- **MCP governance:** `managed-mcp.json` (exclusive control), `managedMcpServers` (provide servers, users keep theirs), `allowedMcpServers` / `deniedMcpServers` with `allowManagedMcpServersOnly`. Denylist always wins. `serverName` matching is not a security control; use `serverUrl`/`serverCommand`. **[doc]**
- **Plugin/Skill governance:** plugin marketplaces (`.claude-plugin/marketplace.json`), `extraKnownMarketplaces` + `enabledPlugins` to require, `strictKnownMarketplaces` / `blockedMarketplaces` to restrict, `disableSideloadFlags`, `strictPluginOnlyCustomization`. Skills: enterprise > personal > project; plugin skills namespaced. **[doc]**
- **Telemetry:** OpenTelemetry opt-in (`CLAUDE_CODE_ENABLE_TELEMETRY=1`), pushed fleet-wide via managed `env`; endpoint/credential locking from managed settings; content logging off by default. **[doc]**
- **Gateway routing:** any gateway exposing a supported API format works; gives central credentials, usage attribution, budgets, audit logging, provider switching; tradeoff: you operate infrastructure and must keep it current with Claude Code. Pin with `allowedProviders: ["customEndpoint"]`. **[doc]**
- **Quality/safety bar for sharing prompts/Skills/MCP servers across teams:** Docs supply controls (allowlists, marketplace restrictions, `Skill(...)` deny rules, validate command, security review of `allowed-tools` and `!` commands). A formal review/promotion process (owner, version pinning, review checklist, staged release channels) is **[interp]**, though release channels via two marketplaces are **[doc]**.

## (b) Concrete facts with sources

### Headless / CI
- `claude -p "prompt"` runs non-interactively; exit 0 on success, non-zero on failure; SIGTERM gives exit 143. https://code.claude.com/docs/en/headless
- `--output-format`: `text` (default), `json`, `stream-json`; `--json-schema` returns `structured_output` field; json output includes `total_cost_usd` (client-side estimate). https://code.claude.com/docs/en/headless
- `stream-json` needs `--verbose` (and `--include-partial-messages` for token deltas); `system/api_retry` event has `attempt`, `max_retries`, `retry_delay_ms`, `error_status`, `error`. https://code.claude.com/docs/en/headless
- `--bare` skips hooks, skills, plugins, MCP servers, auto memory, CLAUDE.md; recommended for scripted/CI calls; uses `ANTHROPIC_API_KEY`/`apiKeyHelper`, never OAuth/keychain. https://code.claude.com/docs/en/headless
- Without `--bare`, `-p` runs project hooks and `.mcp.json` servers with no trust dialog. https://code.claude.com/docs/en/headless
- `--allowedTools` pre-approves tools using permission-rule syntax, e.g. `Bash(git diff *)` (space before `*` matters). `--permission-mode` accepts `auto`, `dontAsk` (denies anything that would prompt; good for locked-down CI), `acceptEdits`. https://code.claude.com/docs/en/headless
- `--permission-prompts none` (v2.1.259+) and setting `permissions.denyInsteadOfPrompting` deny rather than wait for a permission host. https://code.claude.com/docs/en/headless
- Piped stdin capped at 10MB. `--max-turns 20` and `--max-budget-usd` are the run caps; `--max-budget-usd` stops background work. https://code.claude.com/docs/en/best-practices ; https://code.claude.com/docs/en/headless
- CI gate on plugin/MCP load: `system/init` has `plugin_errors` and `mcp_server_errors`; failures are otherwise silent (run exits cleanly). https://code.claude.com/docs/en/headless
- Fan-out loop pattern: `for file in ...; do claude --bare -p "..." --allowedTools ... --permission-mode dontAsk --max-turns 20; done`. https://code.claude.com/docs/en/best-practices

### Worktrees / parallelism
- `claude --worktree <name>` (`-w`): worktree at `.claude/worktrees/<name>/`, branch `worktree-<name>`; add `.claude/worktrees/` to `.gitignore`. https://code.claude.com/docs/en/worktrees
- Base branch: `worktree.baseRef` = `"fresh"` (default, remote default branch) or `"head"` (current local HEAD, carries unpushed commits). https://code.claude.com/docs/en/worktrees
- `.worktreeinclude` (gitignore syntax) copies gitignored files such as `.env` into new worktrees; copies rather than links, so use `worktree.symlinkDirectories` for big dirs. https://code.claude.com/docs/en/worktrees ; https://code.claude.com/docs/en/best-practices
- `claude --worktree "#1234"` branches from a PR head. `claude -p --worktree` leaves the worktree for you to clean (`git worktree remove`, `git worktree unlock`). https://code.claude.com/docs/en/worktrees
- Subagent frontmatter `isolation: worktree`; worktree auto-removed if no changes; sweep removes old subagent worktrees per `cleanupPeriodDays`. https://code.claude.com/docs/en/worktrees ; https://code.claude.com/docs/en/sub-agents
- Worktree isolation checks block edits/git redirects into the main checkout, but `cp`/shell redirects are not tracked. https://code.claude.com/docs/en/worktrees
- Subagents: 20 concurrent by default (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), nesting depth 3 (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`; `1` disables), `maxTurns` frontmatter, `tools`/`disallowedTools`, model resolution order includes `CLAUDE_CODE_SUBAGENT_MODEL`. Subagent file precedence: managed > `--agents` > `.claude/agents/` > `~/.claude/agents/` > plugin. https://code.claude.com/docs/en/sub-agents
- Agent teams: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`, experimental, interactive only (not in `-p`), no worktree isolation of teammates, one team per session, hooks `TeammateIdle`/`TaskCreated`/`TaskCompleted` (exit 2 blocks and sends feedback). https://code.claude.com/docs/en/agent-teams
- `/batch` splits one change into 5 to 30 worktree-isolated units, shows plan, each opens a PR. https://code.claude.com/docs/en/agents ; https://code.claude.com/docs/en/best-practices
- Running several sessions/subagents multiplies token usage. https://code.claude.com/docs/en/agents

### Code review
- Code Review: Team/Enterprise, GitHub repos (incl. GHES); not available with Zero Data Retention, HIPAA configuration or CMEK; runs on Anthropic infrastructure; read-only access; does not build/run code. https://code.claude.com/docs/en/code-review
- Review levels Quick / Standard (default) / Deep; "Review runs": Once after PR creation, After every push (default for newly added repos, most expensive), Manual (`@claude review`). https://code.claude.com/docs/en/code-review-setup
- Comment commands: `@claude review`, `@claude review always`, `@claude review once`, `@claude review stop|off|pause`; needs write access; drafts and fork PRs skipped by automatic reviews. https://code.claude.com/docs/en/code-review-pull-requests
- Check run "Claude Code Review" concludes neutral/skipped, never failure; machine-readable `bughunter-severity` line. https://code.claude.com/docs/en/code-review-pull-requests
- `REVIEW.md` at repo root (+ subdirectory files on protected branches); read from base/default branch, never PR changes; honored severity-lowering/exclusions/nit caps need protected default branch; `@file` includes (max 8 files, 150,000 bytes combined); skill files includable via `@.claude/skills/<folder>/SKILL.md` (30,000 byte cap; Code Review does not run skills). `/code-review` (local) reads CLAUDE.md but not REVIEW.md. https://code.claude.com/docs/en/code-review-customize
- Billing: token usage via usage credits, billed to the org; pilot guidance (set monthly spend limit, few repos, Once-per-PR or Manual, read "Average cost" column); reviews skipped when spend limit/credits run out; analytics at claude.ai/analytics/code-review. https://code.claude.com/docs/en/code-review-costs
- Other review options: `/code-review` local, Ultrareview (cloud sandbox), Claude in your own CI (Actions/GitLab), custom reviewer subagent/skill. https://code.claude.com/docs/en/code-review
- Action-based review: `anthropics/claude-code-action@v1`, `plugins: "code-review@claude-plugins-official"`, `--comment`, and `--allowedTools "mcp__github_inline_comment__create_inline_comment"` in `claude_args`. https://code.claude.com/docs/en/github-actions
- Uber uReview (**[3P]**): multi-stage pipeline, confidence thresholds per assistant/language/category, 75% of comments marked useful, over 65% addressed, only 51% of human-written comments addressed in the same changeset, phased rollout per team/assistant with precision-recall dashboards. https://www.uber.com/en-GB/blog/ureview/

### Unattended / event-driven
- Cloud scheduled tasks (formerly routines): triggers schedule/API/GitHub; min interval 1 hour; runs start in auto mode; branches prefixed `claude/` unless told otherwise; control pushes with GitHub branch protection; belong to your individual account and act as you; limits 100 scheduled runs/hour per account, 30/hour per task for Run now + API fires; GitHub events have hourly caps (dropped beyond). https://code.claude.com/docs/en/routines
- API trigger: POST to `/fire` with `Authorization: Bearer`, optional `text`; token shown once; beta header `experimental-cc-routine-2026-04-01`; the saved prompt must opt in to act on the fire text (treat as untrusted input). https://code.claude.com/docs/en/routines
- `/loop`: `/loop 5m <prompt>`; self-paced when interval omitted (1 minute to 1 hour); `.claude/loop.md` default prompt; recurring tasks expire after 7 days; session holds up to 50 tasks; jitter on recurring runs; `CLAUDE_CODE_DISABLE_CRON=1` disables. https://code.claude.com/docs/en/scheduled-tasks
- Comparison table: Cloud min 1 hour, no machine needed; Desktop needs machine on; `/loop` needs open session. https://code.claude.com/docs/en/scheduled-tasks
- `/goal`: condition up to 4,000 characters; evaluator = small fast model (`ANTHROPIC_DEFAULT_HAIKU_MODEL` changes it); `CLAUDE_CODE_GOAL_CHECKIN_MINUTES` (default 30) controls check-ins; unavailable when `allowManagedHooksOnly` is set or `disableAllHooks` true; `/goal` is a session-scoped prompt-based Stop hook. https://code.claude.com/docs/en/goal
- GitHub Action: interactive mode (no `prompt`, trigger `@claude`) vs automation mode (`prompt` set); `--max-turns`, workflow timeouts and concurrency controls to cap cost; requires write access of actor and rejects bot actors unless `allowed_bots`; scheduled workflows run only from the default branch and public-repo schedules disable after 60 days of inactivity; commits made with default `GITHUB_TOKEN` do not trigger CI. https://code.claude.com/docs/en/github-actions
- Action auth: `ANTHROPIC_API_KEY` secret or `CLAUDE_CODE_OAUTH_TOKEN`; org-wide use API key (OAuth token tied to a person); workload identity federation inputs `anthropic_federation_rule_id`, `anthropic_organization_id` with `id-token: write`; Bedrock/Vertex/Foundry via `use_bedrock`/`use_vertex`/`use_foundry` with OIDC. https://code.claude.com/docs/en/github-actions
- GitLab CI/CD: beta, maintained by GitLab; masked `ANTHROPIC_API_KEY`; job runs `claude -p ... --permission-mode acceptEdits --allowedTools "Bash Read Edit Write mcp__gitlab"`; OIDC for Bedrock / WIF for Vertex; use `--max-turns` and job `timeout`. https://code.claude.com/docs/en/gitlab-ci-cd
- Hooks relevant to unattended ops: `Stop`/`SubagentStop` (exit 2 keeps working), `Notification` (cannot block; `permission_prompt`, `idle_prompt` matchers), `TaskCompleted`, `PermissionRequest`, `WorktreeCreate/Remove`, `SessionEnd`; exit 2 = blocking error, other non-zero = non-blocking unless `onFailure: "block"`; PreToolUse exit 2 blocks. https://code.claude.com/docs/en/hooks

## (c) Decision rules and traps

Format: **When X → choose Y because Z.** Source tags as above.

**Parallel orchestration**
1. Many agents edit overlapping code → one worktree (or subagent `isolation: worktree`) per agent → separate checkout/branch prevents overwrites. [doc]
2. Agent teams in use (no worktree isolation) → partition so each teammate owns distinct files → same-file edits overwrite. [doc]
3. One mechanical change across hundreds of files → `/batch` or a scripted `claude -p` loop with `--allowedTools`, `--permission-mode dontAsk`, `--max-turns` → bounded, independent, reviewable units (each its own PR). [doc]
4. Work is sequential or tightly coupled → single session or subagents, not a team → coordination overhead and token cost exceed benefit. [doc]
5. Subagents spawned from `-p` or CI → agent teams do not spawn in `-p`; named subagents run as ordinary subagents. [doc]
6. Fleet cost spike → look at `claude_code.cost.usage`/`token.usage` by model, `agent.name`/`skill.name` attributes, session count `start_type`, and `api_error` retries before changing prompts. [doc for the signals; ordering of diagnosis is interp]
- Trap: "give the subagent the same task for a better answer" – doc says it does not help; a fresh reviewer does. [doc]
- Trap: "worktrees isolate everything" – they isolate files, not shared `.git`, plugins, permission approvals saved to main checkout's `settings.local.json`, or external side effects. [doc]
- Trap: "add more teammates to go faster" – diminishing returns; start with 3-5. [doc]
- Trap: unbounded concurrency – 20 concurrent subagents is the default limit; beyond that spawn fails. [doc]

**Verification and review**
7. Generation outpaces review → add AI review, but run it non-blocking first (Manual or Once-per-PR on a few repos with a spend limit), compare findings with human review outcomes, tune with REVIEW.md, only then wire your CI to fail on `normal > 0` → a noisy gate blocks merges and trains people to bypass it. [interp, building blocks doc; uReview 3P]
8. Want Claude's review to block merges → build the gate in your own CI from the check-run severity line (and branch protection), because the service itself never blocks. [doc]
9. Too many nits → REVIEW.md cap ("at most five nits") and redefine Important, not more prompting in the PR. Put it on the protected default branch or it is ignored. [doc]
10. Review is too slow/expensive → drop level (Standard→Quick) or change Review runs from After every push to Once per PR/Manual; every-push multiplies cost by pushes. [doc]
11. ZDR/HIPAA/CMEK org → the managed Code Review service is unavailable; use own-CI review (Action/GitLab) or local `/code-review`, subject to the data-handling constraints. [doc]

## (d) Self-check questions

1. Q: Why can't Code Review gate merges by itself? A: The review never approves/blocks and its check run never fails; you gate via your CI reading the `bughunter-severity` line.
2. Q: Safest first step for introducing AI review where generation outpaces human review? A: Run it advisory (Manual/Once-per-PR, small repo set, spend cap), calibrate against human review and tune REVIEW.md, then gate. [interp]
3. Q: Where must REVIEW.md live to be honored for severity lowering and exclusions? A: Root of a protected default branch; read from base/default branch, never the PR.
4. Q: Two agents must edit overlapping modules in parallel – what isolates them? A: One git worktree per agent (`claude -w name` or `isolation: worktree`).
5. Q: Agent teams and file conflicts? A: Teammates are not worktree-isolated; assign each a disjoint file set.
6. Q: A nightly job must keep working when your laptop is off – which option, and min interval? A: Cloud scheduled task (or CI cron); minimum 1 hour.
7. Q: Which flags make a CI `claude -p` run non-interactive, bounded and locked down? A: `--bare`, `--allowedTools`, `--permission-mode dontAsk`, `--max-turns` (plus `--max-budget-usd`, job timeout).
8. Q: How do you stop developers adding arbitrary MCP servers fleet-wide? A: Managed `allowedMcpServers` (URL/command entries) with `allowManagedMcpServersOnly: true`, or a `managed-mcp.json`.
9. Q: Can a repo's `.claude/settings.json` turn on org telemetry? A: No; exporter variables there are ignored. Use managed settings `env`.
10. Q: Does a managed-settings.json on a laptop govern Anthropic-hosted cloud sessions? A: No; only server-managed settings do.

## (a) Key concepts per blueprint skill

### Skill 1 – Reliability Engineering for Claude Services

The blueprint says the skill is about retry/backoff, circuit breakers, graceful degradation, and cross-model / cross-region / cross-platform fallbacks that distinguish three different failure causes: rate limits vs safety refusals vs context-window stops, while respecting per-platform feature parity.

Core mental model: classify the failure first, then pick the remedy. The same "it did not return a normal answer" symptom has very different fixes.

| Signal | What it is | Retry same request? | Right remedy |
|---|---|---|---|
| HTTP 429 `rate_limit_error` with `retry-after` | RPM/ITPM/OTPM or ramp limit | Yes, after the wait | Backoff honoring `retry-after`, smooth traffic, caching, queue |
| HTTP 429 with `error.details.error_code = enforced_spend_limit_reached`, no `retry-after` | Tier monthly spend cap | No, fails until access resumes | Raise tier/cap, alert humans |
| HTTP 400 "reached your specified API usage limits" | Your own org/workspace spend limit | No | Raise or remove your limit |
| HTTP 529 `overloaded_error` | Platform-wide capacity | Yes, with backoff | Backoff, fallback model/region/platform |
| HTTP 500 `api_error` / 504 `timeout_error` | Server side or timeout | Yes, backoff | Stream long requests, log `request-id` |
| HTTP 200, `stop_reason: "refusal"` | Safety classifier decline | No (same model usually refuses again) | Fallback to a different model (server- or client-side), or reword the prompt |
| HTTP 200, `stop_reason: "max_tokens"` | Output cap hit | No | Raise `max_tokens` or continue the response |
| HTTP 200, `stop_reason: "model_context_window_exceeded"` | Context window filled | No | Truncate/compact/trim context, treat output as truncated |
| HTTP 400 `invalid_request_error` (validation) | Bad request | No | Fix the request |
| HTTP 413 `request_too_large` | Body too big | No | Split or use Files API |

Retry design [INTERP built on OFFICIAL SDK behaviour]: retry only transient classes (connection errors, 408, 409, 429, 5xx incl. 529), use exponential backoff with jitter, cap attempts and total time, prefer `retry-after` over your own clock, never blind-retry 400/401/403/404/413 or refusals. Layered retries multiply: if the SDK retries 2x and your app retries 3x, one logical call can fire 9 requests (amplifies 429/529 storms). A circuit breaker (stop calling a failing dependency for a cool-down, then half-open probe) and graceful degradation (cached answer, smaller model, queued/deferred processing, "try later" UX) are standard patterns; the docs I read do not define them [INTERP].

Fallback layers [OFFICIAL facts below, strategy INTERP]: cross-model (refusal fallback, smaller model on overload), cross-region (e.g. Bedrock global vs regional endpoints / inference profiles), cross-platform (Claude API <-> Bedrock/Google Cloud/Foundry). Cross-platform fallback is limited by feature parity: Batch, MCP connector, server-side tools, Files API, `fallbacks` parameter and others are missing on some platforms, so a "failover" target may silently lack a feature your prompt relies on.

### Skill 2 – Scale and Throughput Management

Identify the binding constraint before choosing a fix:
- RPM-bound (many small requests): batch work into fewer requests, request higher tier, Message Batches API.
- ITPM-bound (big prompts): prompt caching, because `cache_read_input_tokens` do not count toward ITPM; trim context.
- OTPM-bound: lower output (effort, shorter responses), spread load; note `max_tokens` is not counted toward OTPM.
- Ramp-limit-bound (sudden growth): ramp traffic gradually, at most one step per minute; Batches are exempt from ramp limits.
- Spend-cap-bound: tier cap/own limit, not a technical retry problem.
- Latency not required (nightly evals, bulk classification, backfills): Message Batches API = 50% price cut, separate rate limits, but up to 24h and no streaming.

Multi-tenant isolation: workspace-level rate and spend limits protect one tenant/team from starving others; org limits always apply; unset workspace limits equal org limits. Backpressure: bounded queue + concurrency limit + shed/defer low-priority work; queue by estimated tokens, not only request count [INTERP].

### Skill 3 – Production MCP and Change Management

- Remote MCP deployment: Streamable HTTP (and SSE) over public HTTPS; Claude's MCP connector cannot reach local STDIO servers; only tool calls (not resources/prompts) are supported by the connector. For private networks the docs list "MCP tunnels" (outbound-only connection).
- Authentication: MCP authorization (HTTP transports) is OAuth 2.1 based; the MCP server is an OAuth *resource server*; must publish Protected Resource Metadata (RFC 9728); client uses `resource` parameter (RFC 8707) and PKCE; server must validate token audience and must not pass the client's token through to upstream APIs (confused-deputy).
- Tool/schema versioning: treat tool names, descriptions and input schemas as a public contract. [INTERP] Additive optional parameters are safe; renames/removals/type changes are breaking; version via new tool name or server version, run both during deprecation, and note tool-definition changes invalidate the prompt cache.
- Model migration: states Active -> Legacy -> Deprecated -> Retired; retired models fail; Anthropic gives at least 60 days notice for publicly released models; test replacements well before retirement; audit usage via Console usage export. New models can reject old params (e.g. prefill, `thinking.type=enabled`, sampling params, forced tool_choice) with 400 errors, so migration testing must cover request shape, not only quality.
- Prompt versioning and rollout [INTERP, no official doc read]: store prompts as versioned artifacts, tie each production request to prompt version + model ID, golden-set regression eval before rollout, canary/progressive percentage rollout, instant rollback by flag. Pin dated/explicit model IDs rather than moving aliases.
- Gateway/routing: a gateway centralises auth, rate limiting, model routing, fallback, logging; it must still honor platform differences (model ID formats, auth, headers, missing features).

### Skill 4 – Retrieval and Knowledge Grounding at Scale

- Agentic search vs classic RAG: [INTERP] RAG (embed -> retrieve top-k -> stuff) is cheap, fast, predictable, good for large, stable corpora and single-hop questions. Agentic search (model issues repeated queries with tools such as grep/search/fetch, reads results, reformulates) handles multi-hop, ambiguous, structured/code corpora and fresh data, at higher latency/token cost and with more variance. Anthropic's contextual-retrieval post notes that for a knowledge base under ~200,000 tokens (~500 pages) you can skip RAG and put it all in the prompt (with prompt caching).
- Chunking: chunk size is a recall/precision trade-off; Anthropic's example uses chunks of "a few hundred tokens" (800-token chunks in the cost model). Citations feature chunks plain text/PDF into sentences automatically; custom-content documents let you control the unit.
- Embeddings: Anthropic does not offer its own embedding model; docs point to Voyage AI. Use `input_type` = `query` vs `document`.
- Hybrid search: combine dense vectors (semantic) with BM25/lexical (exact IDs, error codes, names) then merge; then rerank. Anthropic's measured gains: see facts.
- Reranking: retrieve wide (e.g. top-150), rerank, pass narrow (top-20).
- Contextual Retrieval: prepend LLM-generated chunk-specific context to each chunk before embedding and before BM25.
- Grounding practices: citations (API feature), `search_result` blocks, "allow I don't know", quote-first for long docs, claim-verification pass, restrict to provided documents, confidence/uncertainty signals (cited vs uncited, retrieval scores, self-consistency).
- Diagnosing retrieval failures by stage [INTERP framework]: (1) ingestion/parsing (text missing, tables broken), (2) chunking (answer split across chunks, no context), (3) indexing/embedding (wrong model, query/document `input_type` mismatch, stale index), (4) first-stage retrieval (recall: is the gold chunk in top-k at all?), (5) fusion/rerank (gold chunk retrieved but ranked out of the cut), (6) context assembly (too many chunks, lost-in-the-middle, truncated), (7) generation (ignored or misused context, hallucination), (8) citation/attribution (claim not supported). Measure recall@k at stage 4, then rank position after stage 5, then faithfulness at stage 7 to localise the fault.

## (b) Concrete facts (each with source URL)

### Errors, retries, request limits
1. Error codes: 400 `invalid_request_error`, 401 `authentication_error`, 402 `billing_error`, 403 `permission_error`, 404 `not_found_error`, 409 `conflict_error`, 413 `request_too_large`, 429 `rate_limit_error`, 500 `api_error`, 504 `timeout_error`, 529 `overloaded_error`. https://platform.claude.com/docs/en/api/errors
2. 529 can occur with high traffic across all users (platform-wide, not your quota). https://platform.claude.com/docs/en/api/errors
3. Hitting your own org/workspace spend limit returns 400 `invalid_request_error`, not 429 (Claude Code workspace excepted: can be 429). https://platform.claude.com/docs/en/api/errors
4. Tier monthly spend-cap 429 has no `retry-after` and keeps failing until access resumes; ramp limits can also 429 while under rate limits. https://platform.claude.com/docs/en/api/errors
5. SDK auto-retries connection errors, rate limits and 5xx with exponential backoff, 2 times by default, honoring `retry-after`; configurable via `max_retries`. https://platform.claude.com/docs/en/api/errors
6. Python SDK retries: connection errors, 408, 409, 429, >=500; default timeout 10 minutes; timeouts are also retried twice by default; `APITimeoutError` on timeout. https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/python
7. SDK raises `ValueError` for non-streaming requests expected to exceed ~10 minutes; use streaming (or override timeout). https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/python
8. Max request size: Messages 128 MB, Token Counting 128 MB, Batch 256 MB, Files 500 MB; exceeding -> 413. https://platform.claude.com/docs/en/api/errors
9. Every response has a `request-id` header (also `request_id` in error body); SDK exposes `_request_id`; give it to support. On Claude Platform on AWS there is also `x-amzn-requestid`; on Foundry also `apim-request-id`. https://platform.claude.com/docs/en/api/errors ; https://platform.claude.com/docs/en/build-with-claude/claude-in-microsoft-foundry
10. Errors can occur mid-stream after a 200; SSE sends `{"type":"error","error":{"type":"overloaded_error",...}}` (corresponds to 529); streams can contain `ping` events. https://platform.claude.com/docs/en/build-with-claude/streaming
11. Long requests: use streaming or Batches for long jobs (>10 min); idle connections may drop on some networks. https://platform.claude.com/docs/en/api/errors
12. Versioning: for a given `anthropic-version`, Anthropic preserves existing inputs/outputs but may add optional inputs, add output values, add new enum-like variants (e.g. new streaming event types), change conditions for specific errors. So clients must tolerate unknown fields/event types. Current version cited: `2026-10-21`. https://platform.claude.com/docs/en/api/versioning
13. API 2026-10-21 removes `temperature`/`top_p`/`top_k` (400); `text` block with non-empty `citations` in a user message returns 400. https://platform.claude.com/docs/en/api/versioning ; https://platform.claude.com/docs/en/about-claude/model-deprecations

### stop_reason handling
14. `stop_reason` values: `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, `refusal`, `model_context_window_exceeded`. https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons
15. `max_tokens`: raise it or continue; if last block is an incomplete `tool_use`, retry with higher `max_tokens`. https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons
16. `pause_turn`: server-tool sampling loop hit its iteration limit (default 10); append content unchanged as assistant message (no user message) and resend with same tools; repeat with a retry cap; never produced by client tools. https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons
17. `model_context_window_exceeded`: response filled the context window before `max_tokens`; treat as truncated. Returned without beta header on Sonnet 4.5 and newer; older models need beta header `model-context-window-exceeded-2025-08-26`. https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons
18. `end_turn` can occasionally be an empty (2-3 token) response, esp. after tool results; do not add text right after `tool_result` blocks; do not resend unchanged. https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons
19. Refusal is HTTP 200, `stop_reason:"refusal"`, with `stop_details` (`category`, `explanation`, optional `recommended_model`); `stop_details` is null for other stop reasons. Categories: `cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms`. https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback
20. Refusal can come mid-stream; discard partial output. Re-sending to the same model usually earns another refusal; retry on a different model. https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback
21. Billing: pre-output refusals are billed for `bio`, `frontier_llm`, `reasoning_extraction` (not for `cyber`, `general_harms`); mid-stream refusals bill input + streamed output; Fallback credit offsets the cache miss of the fallback request. https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback
22. Server-side fallback: `fallbacks: "default"` + beta header `server-side-fallback-2026-07-01` (beta on Claude API and Google Cloud Anthropic-managed). Not supported on Bedrock (bedrock-mantle) or Foundry; use client-side fallback (SDK middleware) there. `reasoning_extraction` has no recommended fallback: change the prompt (do not ask the model to output its reasoning; use thinking blocks). https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback ; https://platform.claude.com/docs/en/build-with-claude/claude-in-microsoft-foundry ; https://platform.claude.com/docs/en/build-with-claude/claude-in-amazon-bedrock

### Rate limits and throughput
23. Rate limits: RPM, ITPM, OTPM per model class; token-bucket algorithm (continuously replenished, not fixed reset); short bursts can trip limits (60 RPM may be enforced as 1/sec). https://platform.claude.com/docs/en/api/rate-limits
24. Cache-aware ITPM: only `input_tokens` + `cache_creation_input_tokens` count; `cache_read_input_tokens` do not. Example: 2M ITPM at 80% hit rate ~ 10M total input tokens/min. https://platform.claude.com/docs/en/api/rate-limits
25. OTPM counts actual generated tokens; `max_tokens` does not count toward OTPM. https://platform.claude.com/docs/en/api/rate-limits
26. Example limits: Start tier Sonnet 5.5: 4,000 RPM / 2,000,000 ITPM / 400,000 OTPM; Build: 10,000 / 5,000,000 / 1,000,000; Scale: 13,000 / 10,000,000 / 2,000,000. https://platform.claude.com/docs/en/api/rate-limits
27. Monthly spend caps: Start $500, Build $1,000, Scale $200,000; Custom none; at cap, usage pauses until 00:00 UTC on the 1st. https://platform.claude.com/docs/en/api/rate-limits
28. Ramp limits: cap on how fast usage can grow; 429 with `error.details.error_code = ramp_limit_exceeded`; wait `retry-after`, increase by at most one step per minute; Batches exempt; cached reads do not count. https://platform.claude.com/docs/en/api/rate-limits
29. Headers: `retry-after`, `anthropic-ratelimit-{requests,tokens,input-tokens,output-tokens}-{limit,remaining,reset}` (reset in RFC 3339), plus `anthropic-priority-*` for Priority Tier. `tokens-*` reflects the most restrictive limit. Not every 429 has `retry-after`. https://platform.claude.com/docs/en/api/rate-limits
30. Workspace limits: set per limiter type; if unset equal org limit; org limits always apply; unused share stays available to other workspaces. Rate Limits API can read/set them programmatically. https://platform.claude.com/docs/en/api/rate-limits
31. Rate limits are shared across `inference_geo` values (`us` and `global` draw from one pool). https://platform.claude.com/docs/en/api/rate-limits
32. Fast mode has separate dedicated limits and `anthropic-fast-*` headers. https://platform.claude.com/docs/en/api/rate-limits

### Message Batches
33. Batch limit: 100,000 requests or 256 MB, whichever first; most finish within 1 hour; expire if not complete in 24 hours; results available 29 days after creation. https://platform.claude.com/docs/en/build-with-claude/batch-processing
34. Price: 50% of standard price for all usage. https://platform.claude.com/docs/en/build-with-claude/batch-processing
35. Result types per request include `succeeded`, `errored`, `canceled`, `expired`; `expired` (24h reached) is not billed. `custom_id` matches `^[a-zA-Z0-9_-]{1,64}$`. Match results by `custom_id`, not order [INTERP: docs show custom_id as the identifier]. https://platform.claude.com/docs/en/build-with-claude/batch-processing
36. Batch rate limits are separate from Messages limits and shared across models: Start 1,000 RPM / 200,000 queued requests; Build 2,000 / 300,000; Scale 4,000 / 500,000; 100,000 per batch in all tiers. https://platform.claude.com/docs/en/api/rate-limits
37. Use the 1-hour cache TTL with batches since processing can exceed 5 minutes; `max_tokens: 0` cache pre-warming is not supported inside a batch (`max_tokens` >= 1). https://platform.claude.com/docs/en/build-with-claude/batch-processing
38. Batches are not ZDR-eligible (29-day retention). Supported platforms listed: Claude API, Claude Platform on AWS, Google Cloud (Anthropic managed). Not supported on Foundry or Bedrock. https://platform.claude.com/docs/en/build-with-claude/batch-processing ; https://platform.claude.com/docs/en/build-with-claude/claude-in-microsoft-foundry ; https://platform.claude.com/docs/en/build-with-claude/claude-in-amazon-bedrock

### Prompt caching (throughput lever)
39. TTL 5 min default (refreshed on use), optional 1 hour (`"ttl":"1h"`); write multipliers 1.25x (5m) and 2x (1h); read 0.1x (0.05x on Opus 5.5/Sonnet 5.5; 0.025x on Fable/Mythos 5.1/5.2). Up to 4 explicit breakpoints. Cache order tools -> system -> messages; changes invalidate that level and later ones. https://platform.claude.com/docs/en/build-with-claude/prompt-caching
40. Minimum cacheable length varies by model (512 / 1,024 / 2,048 / 4,096 tokens); shorter prompts are processed uncached without error. https://platform.claude.com/docs/en/build-with-claude/prompt-caching

### MCP in production
52. MCP connector: beta, headers `mcp-client-2026-09-15` / `mcp-client-2025-11-20` (older `mcp-client-2025-04-04` deprecated); Messages API takes `mcp_servers` (type url, url, name, `authorization_token`) plus a matching `{"type":"mcp_toolset","mcp_server_name":...}` in `tools`; supports allowlist/denylist and per-tool config; multiple servers; OAuth Bearer tokens; only tool calls from the MCP spec; server must be public over HTTP (Streamable HTTP or SSE), not local STDIO; not ZDR-eligible. https://platform.claude.com/docs/en/agents-and-tools/mcp-connector
53. `stop_reason: "tool_use"` may contain `mcp_tool_use`/`server_tool_use` blocks awaiting results; resend with same `tools` and same `mcp_servers`; text mixed with `tool_result` blocks gives 400. https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons
54. MCP authorization spec (2025-06-18): optional; for HTTP transports SHOULD follow it; STDIO SHOULD NOT (use env credentials). MCP server = OAuth 2.1 resource server, MUST implement Protected Resource Metadata (RFC 9728) with `authorization_servers`; 401 MUST carry `WWW-Authenticate` pointing to metadata; client MUST use AS metadata (RFC 8414); Dynamic Client Registration (RFC 7591) SHOULD be supported; client MUST send `resource` (RFC 8707) in authorization and token requests; MUST use PKCE; token in `Authorization: Bearer` header on every request, never in query string; server MUST validate audience; MUST NOT accept or pass through tokens for other resources; 401 invalid/expired token, 403 insufficient scope, 400 malformed. https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization

### Retrieval and grounding
55. Contextual Retrieval (Anthropic): contextual embeddings cut top-20 retrieval failures 35% (5.7% -> 3.7%); + contextual BM25 49% (-> 2.9%); + reranking 67% (-> 1.9%). Top-20 chunks beat top-10 and top-5; rerank from top-150 to top-20. One-time cost $1.02 per million document tokens (800-token chunks, 8k-token docs); prompt caching cuts latency >2x and cost up to 90%. Under ~200,000 tokens (~500 pages) include whole KB in prompt. https://www.anthropic.com/news/contextual-retrieval
56. Anthropic offers no embedding model; Voyage AI recommended: `voyage-4-large` / `voyage-4` / `voyage-4-lite`, `voyage-code-4`, `voyage-law-2`, `voyage-finance-2`, `voyage-context-4` (contextualized chunk embeddings), 32,000 context (120,000 for context models with auto-chunking); rerankers `rerank-3`, `rerank-3-lite`; set `input_type` `query`/`document` and never omit it; embeddings normalized so cosine = dot product. https://platform.claude.com/docs/en/build-with-claude/embeddings
57. Citations feature: enable with `citations: {enabled: true}` on each document (cannot mix enabled and disabled docs in one request); plain text and PDF are chunked into sentences; custom content documents are not chunked further; citation locations: char indices (plain text, 0-indexed), page numbers (PDF, 1-indexed), content block indices (custom content). Claude cannot cite images in PDFs. https://platform.claude.com/docs/en/build-with-claude/citations
58. `cited_text` does not count toward output tokens (nor input tokens when passed back); citations are parsed so pointers are guaranteed valid; slight input-token increase; toggling citations invalidates cached tools level. https://platform.claude.com/docs/en/build-with-claude/citations ; https://platform.claude.com/docs/en/build-with-claude/prompt-caching
59. Citations are incompatible with structured outputs (`output_config.format`): combining returns an error (400). https://platform.claude.com/docs/en/build-with-claude/citations
60. ## (c) Decision rules (exam style) and traps

Reliability
- Intermittent 529 during traffic peaks -> exponential backoff with jitter + fallback model/region, NOT raising your tier (529 is platform capacity, not your quota). Trap: "request a rate limit increase".
- 429 with `retry-after` -> wait at least that long, then retry. Trap: fixed 1-second retry loop.
- 429 with `enforced_spend_limit_reached`, no `retry-after` -> stop retrying, escalate (tier/cap). Trap: more backoff.
- 400 with "specified API usage limits" -> your own spend limit; raise/remove it. Trap: treating as malformed request.
- `stop_reason: "refusal"` on HTTP 200 -> do not retry same model, do not treat as an exception; use fallback model (server-side `fallbacks` where supported, else client-side). Trap: wrapping only `except RateLimitError` and missing it entirely; or retrying with backoff.
- `reasoning_extraction` category -> rewrite the prompt (remove "output your reasoning" fields), use thinking blocks. Trap: fallback model.
- `max_tokens` stop -> continue/raise limit; `model_context_window_exceeded` -> reduce/compact context (raising `max_tokens` will not help). Trap: confusing the two.
- `pause_turn` -> resend the assistant content as-is (no new user message) with loop cap. Trap: adding "continue".
- Failover Claude API -> Bedrock/Foundry: first check parity (no Batches, no MCP connector on Bedrock, no `fallbacks`, different model IDs/auth, no `anthropic-ratelimit-*` headers on Foundry). Trap: assuming "same API".
- Long generation with large `max_tokens` timing out -> stream (SDK `stream.get_final_message()`) or Batch. Trap: just raise timeout.
- Retry stacking: set one retry layer owner (SDK `max_retries` or app), add a circuit breaker when the dependency is down; blind retries amplify outages [INTERP].

Throughput
- Nightly bulk work with no latency SLA -> Message Batches (50% cheaper, own limits, up to 24h). Trap: using Batches for interactive UX, or assuming ordered results/ guaranteed <1h (expiry at 24h).
- ITPM-bound with big repeated prefix -> prompt caching (cache reads excluded from ITPM). Trap: buying more RPM.
- Sudden 429s right after launch while under limits -> ramp limit; ramp gradually. Trap: tier upgrade only.
- One tenant starving others -> workspace limits / per-tenant quotas and queue fairness.
- Batch + shared context -> 1-hour cache TTL (processing may exceed 5 min).

MCP and change management
- Need Claude to reach a remote tool server from API with no client code -> MCP connector (`mcp_servers` + `mcp_toolset`, beta header); STDIO/local servers need your own client or a tunnel; only tools supported. Trap: expecting resources/prompts, or using it on Bedrock.
- Remote MCP server auth -> OAuth 2.1 resource server, RFC 9728 metadata, audience-validated tokens, PKCE, `resource` parameter. Trap: forwarding the client's token to upstream APIs (token passthrough, forbidden), putting tokens in query string, or using a shared static key.
- Model retirement announced -> test candidate on eval set, check request-shape breakage (prefill, thinking, tool_choice, sampling params), canary, keep rollback; pin explicit model IDs. Trap: swapping the model string in prod and watching.
- Prompt change -> version, regression eval, progressive rollout, rollback [INTERP]. Trap: edit in place.
- Tool schema change -> additive and optional only; otherwise new versioned tool and deprecation window [INTERP]. Note a tool-definition change invalidates the whole prompt cache.

Retrieval and grounding
- Exact identifiers/error codes/SKUs missing from results -> add BM25/lexical (hybrid). Trap: bigger embedding model.
- Gold chunk retrieved but not in the final top-k -> add/tune reranker (retrieve ~150, keep ~20). Trap: re-chunking.
- Chunks lack context ("the company's revenue grew 3%") -> contextual retrieval (prepend chunk context before embedding and BM25), cache the doc to make it cheap.
- KB < ~200k tokens -> skip RAG, put it in prompt with caching.
- Multi-hop, ambiguous, or code/structured corpora -> agentic search; high-volume simple FAQ -> RAG [INTERP].
- Need verifiable sources -> citations feature or `search_result` blocks, not "please quote sources" prompt text (API citations have valid pointers, `cited_text` is free of output tokens). Trap: using citations together with structured outputs (error); mixing citation-enabled and disabled docs; expecting image citations in PDFs.
- Need JSON plus citations -> cannot use `output_config.format`; put citations in separate fields via post-processing or a second pass [INTERP].
- Model asserts unsupported facts -> allow "I don't know", restrict to documents, verification pass, lower reliance on parametric knowledge; confidence signals = presence/absence of citations, retrieval score margin, self-consistency across N samples [INTERP].
- Diagnose in order: recall@k (retrieval) -> rank after rerank -> context assembly -> faithfulness. Fix the first failing stage; do not tune the prompt for a retrieval miss.
- Query/document embedding mismatch (`input_type` omitted, or different models for index vs query) -> silent recall loss.

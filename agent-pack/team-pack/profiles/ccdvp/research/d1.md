## (a) Key concepts by skill

### 1. Multi-Agent Orchestration (supervisor/worker, parallel dispatch, isolation, communication, HITL)

- **Orchestrator-worker (supervisor/worker)**: a lead agent plans, delegates to subagents, synthesizes. Anthropic's research system: lead (Opus 4) + parallel subagents (Sonnet 4) + separate CitationAgent. Subagents act as *filters*: search iteratively, return condensed findings. [DOC]
- **Context isolation (cô lập ngữ cảnh)**: in the Agent SDK a subagent starts with a fresh context; the ONLY parent-to-child channel is the Agent tool's prompt string; only the subagent's final message returns to the parent. Intermediate tool calls stay inside. So the parent must put file paths, errors, decisions into the prompt. [DOC]
- **Inter-agent communication**: (i) return value of the Agent tool (final report, parent may paraphrase it); (ii) `SendMessage` between named agents in the SDK; (iii) Managed Agents "session threads": each agent has a context-isolated event stream, all share the same sandbox/filesystem/vault credentials; subagent threads are persistent (follow-ups possible). Research system: subagents write big outputs to external storage and pass lightweight references (avoids "telephone game"). [DOC]
- **Parallel dispatch**: independent subtasks finish in time of the slowest, not the sum. Research system: lead launches 3-5 subagents in parallel, each uses 3+ tools in parallel, cutting research time up to 90%. But parallelism buys thoroughness more than speed overall (3-10x tokens). [DOC]
- **When multi-agent pays off**: context pollution (>~1,000 irrelevant tokens from a subtask), parallelizable independent work, specialization (15-20+ tools, conflicting behaviours). Decompose by *context boundary*, not by job type (planner/implementer/tester/reviewer splits burned tokens on coordination). [DOC blog]
- **Human-in-the-loop (HITL)**: SDK `canUseTool` callback fires for tool approval and for `AskUserQuestion`; execution pauses until it returns; may allow, deny (with message Claude sees), allow with `updatedInput`, or "approve and remember" via `updatedPermissions`. Managed Agents: permission policy `always_ask` pauses the session -> `session.status_idle` with `stop_reason.type = requires_action` -> you send `user.tool_confirmation` (`allow`/`deny`). [DOC]

### 2. Durable Execution and State Management

- **Session persistence**: Agent SDK writes the conversation (not the filesystem) to JSONL under `~/.claude/projects/<encoded-cwd>/`. `continue` = most recent session in cwd; `resume` = by session ID; `fork` = new session with copy of history, original untouched. [DOC]
- **Checkpointing**: (i) conversation = session transcript; (ii) files = SDK file checkpointing (`enableFileCheckpointing`, rewind to user-message UUID; does NOT track Bash edits or subagent edits; does not rewind conversation); (iii) git commits + progress file for multi-session projects. [DOC]
- **Resumability across hosts**: transcripts are local; use a `SessionStore` adapter (`append`, `load` required) to mirror to S3/Redis/Postgres so another host can resume; resume from a matching cwd. [DOC]
- **Human wait that outlives the process**: return a `PreToolUse` hook `defer` decision so the process exits and resumes later from the persisted session (instead of a callback pending forever). [DOC user-input page; the hooks page detail on defer was not read -> mechanism details `[unverified]`]
- **Managed Agents** = hosted harness; session is a stateful resource (history, sandbox state, outputs stored server-side; resumes cleanly after pauses); statuses `idle`, `running`, `rescheduling` (transient error, auto-retry), `terminated`. Agent versions can be pinned per session. [DOC]
- **Survive model version change**: the agent's `model`/`system` are fixed for the life of a session; to run a different model you create a new session (optionally `agent_with_overrides`) or pin an agent version. Compaction/thinking caveat: on models with preserved thinking, reinserted earlier thinking blocks fail the prefix check after compaction (strip them or `prefix_mismatch_behavior: "drop_block"`). [DOC] Whether an existing SDK transcript can be resumed on a *different* model is `[unverified]` (not stated on pages read) -> design rule: keep durable state in external artifacts (memory files, feature list, git), not only in thinking/transcript.
- **Memory architecture**: client-side memory tool (files under `/memories`) + progress log + feature checklist (initializer/coding-agent pattern). [DOC]

### 3. Architecture Selection at Scale (workflow vs agent, harness, framework, patterns)

- Workflow = LLM + tools orchestrated by predefined code paths; agent = LLM dynamically directs its own process and tool use. Five workflow patterns: prompt chaining, routing, parallelization (sectioning/voting), orchestrator-workers, evaluator-optimizer. [DOC]
- Principle: simplest thing that works; add complexity only when it *demonstrably* improves outcomes. Workflows for predictable, well-defined tasks; agents for open-ended, unpredictable-step tasks (cost/latency/compounding-error trade-off). [DOC]
- Evolving a running system: use cost, reliability and quality data (eval scores, token use, failure cohorts) to decide to move a step from agentic to deterministic workflow (or the reverse). [INTERP of blueprint; supported by "demonstrably improves outcomes" [DOC]]
- Harness choices: raw Messages API loop (max control) vs Agent SDK (same loop as Claude Code, sessions, subagents, hooks) vs Managed Agents (hosted harness + sandbox; "best for long-running and asynchronous work"). Frameworks: abstractions can hide prompts/responses and hinder debugging; understand what's underneath. [DOC]
- Standardisation: reusable subagent definitions (`AgentDefinition`/`.claude/agents/`), Skills, MCP servers shared with a quality/safety bar (Domain 8 overlaps). [INTERP]

### 4. Context and Memory Architecture

Toolbox, from lightest to heaviest [DOC unless noted]:
1. **Tool-result clearing (context editing)**: server-side removal of old tool results by rule; client keeps full history.
2. **Compaction**: server-side summary replaces older turns; recommended primary strategy for long-running conversations.
3. **Memory tool / notes**: persist what must survive clearing/summarization outside context.
4. **Subagents**: fresh contexts, return 1,000-2,000-token summaries.
5. **Tool search (`defer_loading`)**: keep big tool catalogs out of context.
6. **Cache-safe mid-conversation instruction changes**: append, don't edit the prefix.
Context rot: recall accuracy declines as the window fills -> every token must earn its place.

## (b) Concrete facts (each with source URL)

**Orchestration / subagents**
- Research system: orchestrator-worker; beat single-agent Opus 4 by 90.2% on internal eval; multi-agent ~15x chat tokens, agents ~4x; token usage alone explained 80% of BrowseComp variance (3 factors = 95%). https://www.anthropic.com/engineering/multi-agent-research-system
- Effort-scaling rules: simple fact-find = 1 agent / 3-10 tool calls; comparison = 2-4 subagents / 10-15 calls each; complex = >10 subagents. Early versions over-spawned. Lead saves plan to memory because context beyond 200,000 tokens is truncated; lead runs subagents synchronously (bottleneck); rainbow deployments for stateful agents. Same URL.
- Multi-agent typically 3-10x tokens vs single agent; failure modes: lost context at handoffs, problem-type splits, tightly coupled components, misrouting, verifier "early victory". https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them
- SDK `AgentDefinition` fields: `description`, `prompt` (required); `tools`, `disallowedTools`, `model` (`sonnet`/`opus`/`haiku`/`inherit`/full ID), `skills`, `memory`, `mcpServers`, `maxTurns`, `background`, `effort`, `permissionMode`. Subagents are invoked through the `Agent` tool (shows as `Task` in `system:init`; match both). Listing a tool in `tools` does not pre-approve it. https://code.claude.com/docs/en/agent-sdk/subagents
- Subagent receives: own prompt + Agent tool prompt string + project CLAUDE.md + tool defs; does NOT receive parent history, parent system prompt, or skill content unless listed. Same URL.
- Subagents run in background by default in current docs (`status: "async_launched"`) and Claude waits when it needs the report. Same URL.
- Caps: `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` default 3; `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` default 20 (returns `Concurrent subagent limit reached`); `maxBudgetUsd`/`max_budget_usd` -> `Budget limit reached`, result subtype `error_max_budget_usd`. Same URL.
- Resume a subagent: capture `session_id` and `agentId`, then `resume: sessionId`; resumed subagent keeps full history. Same URL.
- `AskUserQuestion` is NOT available inside subagents; each call = 1-4 questions with 2-4 options; `header` max 12 chars. https://code.claude.com/docs/en/agent-sdk/user-input
- Managed Agents multiagent: delegation one level deep; max 25 child threads at a time (idle included); up to 20 predefined agents per list; `advisor` setting (`{"type":"enabled","model":...}`) lets primary thread consult a model mid-turn, advisor model must be at least as capable as the agent's model. https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration
- Managed Agents permission policies: `always_allow`, `always_ask`, `auto`; agent toolset defaults `always_allow`, MCP toolsets default `always_ask`; custom tools are not covered (they run in your app). https://platform.claude.com/docs/en/managed-agents/permission-policies
- `session.status_idle` stop reasons: `end_turn`, `requires_action` (with `stop_reason.event_ids`); answer with `user.tool_confirmation` (`result` allow/deny) or `user.custom_tool_result`; reconnect without missing events by combining new stream + event history. https://platform.claude.com/docs/en/managed-agents/events-and-streaming

**Durability**
- Managed Agents beta header `managed-agents-2026-04-01`; concepts Agent / Environment / Session / Events; not ZDR/HIPAA eligible (stateful; transcripts persist until deleted). https://platform.claude.com/docs/en/managed-agents/overview
- Session: agent can be pinned `{"type":"agent","id":...,"version":1}`; `agent_with_overrides` replaces model/system/tools wholesale for one session; `initial_events` max 50; `budget.max_list_cost` (amount in cents, string) -> session idles with `budget_reached`. https://platform.claude.com/docs/en/managed-agents/sessions
- Statuses `idle/running/rescheduling/terminated`; only `tools` and `mcp_servers` can change after creation (session must be `idle`); `system` fixed for session lifetime; `system.message` event can append guidance on supporting models. https://platform.claude.com/docs/en/managed-agents/session-operations
- Agent SDK sessions: persist conversation not filesystem; `persistSession: false` (TS only) for stateless; cross-host needs SessionStore or moved JSONL. https://code.claude.com/docs/en/agent-sdk/sessions
- `SessionStore`: required `append`/`load`; optional `listSessions`, `listSessionSummaries`, `delete`, `listSubkeys`; dual-write (local first, then mirror); `append` retried up to 3 attempts total, dedupe by `entry.uuid`; failed mirror emits `mirror_error`; `persistSession:false` and file checkpointing conflict with a store (SDK throws). https://code.claude.com/docs/en/agent-sdk/session-storage
- File checkpointing: needs `enableFileCheckpointing` + `replay-user-messages` extra arg; rewind via UUID of a user message; limits: Bash changes, subagent edits, directories, remote files not tracked; same-session only. https://code.claude.com/docs/en/agent-sdk/file-checkpointing
- Long-running harness pattern: initializer agent writes `init.sh`, `claude-progress.txt`, JSON feature list (200+ features, `passes` boolean, only `passes` editable) and first git commit; each later session: pwd, read git log + progress, pick one feature, e2e smoke test, work, commit. JSON chosen because models overwrite it less than Markdown. https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

**Context & memory**
- Context editing: beta `context-management-2025-06-27`; strategies `clear_tool_uses_20250919` and `clear_thinking_20251015`; `clear_tool_uses` params `trigger` (default 100,000 input tokens; also `tool_uses`), `keep` (default 3), `clear_at_least` (default none), `exclude_tools`, `clear_tool_inputs` (default false); cleared results replaced by placeholder; response `context_management.applied_edits`; clearing invalidates cached prefix, so use `clear_at_least`; `clear_thinking` default keeps last 1 thinking turn (`keep: {type:"thinking_turns", value:N}` or `"all"`); put `clear_thinking_20251015` first when combining. https://platform.claude.com/docs/en/build-with-claude/context-editing
- Context editing + memory: model gets an automatic warning near the clearing threshold to save to memory first. Same URL.
- Compaction overview: three ways (on demand, at a token threshold, own summarizer); on-demand preferred "wherever available"; on-demand beta header `compact-2026-09-04` + top-level `compaction` parameter, returns a single `compaction` block (summary + signature) that you put first in `messages`. https://platform.claude.com/docs/en/build-with-claude/compaction
- Threshold compaction: beta `compact-2026-01-12`, edit type `compact_20260112`; `trigger` default 150,000 input tokens, minimum 50,000, only `input_tokens`; `pause_after_compaction` (default false -> `stop_reason: "compaction"`); `instructions` REPLACES default summary prompt; `cache_control` allowed on the compaction block; also breakpoint at end of system prompt; billing: sum `usage.iterations`; API ignores everything before the compaction block; may fire more than once in a request with server tools. https://platform.claude.com/docs/en/build-with-claude/compaction-threshold
- Memory tool: type `memory_20250818`, name `memory`; CLIENT-side (you implement handler); commands `view`, `create`, `str_replace`, `insert`, `delete`, `rename`; paths under `/memories`; must defend against path traversal (`../`, `%2e%2e%2f`); API injects "ASSUME INTERRUPTION" protocol into system prompt; no beta header required; ZDR eligible; guidance: pair with compaction (compaction keeps context small, memory keeps what must survive). https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool
- Tool search: `tool_search_tool_regex_20251119` (Python `re.search`, pattern max 200 chars) and `tool_search_tool_bm25_20251119` (natural language, max 500 chars); `defer_loading: true` per tool; at least one tool non-deferred (never the search tool); all definitions still sent every request; up to 10,000 deferred tools; returns 5 matches by default (`limit` 1-10,000); ~55k-token multi-server setup cut >85%; accuracy degrades beyond 30-50 tools; use when >=10 tools or >10k tokens of definitions; keep 3-5 hot tools non-deferred; deferred tool cannot carry `cache_control` (400); for MCP set `defer_loading` in `mcp_toolset` `default_config`; custom client-side search returns `tool_reference` blocks. https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool
- Prompt cache order `tools -> system -> messages`; a change invalidates that level and later ones; changing tool definitions invalidates everything; editing top-level `system` invalidates system + messages caches. https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- Cache-safe mid-conversation change: append a `{"role":"system"}` message in `messages` (supported on listed models, NOT on Claude Sonnet 5); add/alter tools mid-conversation with beta `inline-tools-2026-09-15` via `tool_addition` block, leaving `tools` untouched; per-message effort change also via system message. Same URL.
- Cache mechanics: 20-block lookback; TTL 5 min default (write 1.25x) or 1 h (2x); read 0.1x (0.05x Opus/Sonnet 5.5; 0.025x Fable/Mythos 5.1/5.2); minimum cacheable 512/1,024/2,048/4,096 tokens depending on model. Same URL.
- Context engineering: compaction (recall first, then precision), structured note-taking, sub-agent summaries 1,000-2,000 tokens, just-in-time retrieval with lightweight references. https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

## (c) Decision rules and traps (exam-style)

1. **Subtasks are independent, large, and read-heavy (research, multi-file audit)** -> orchestrator + parallel subagents because each gets clean context and returns a summary. **Tightly coupled / shared-state work (most coding in one repo, feature + its tests)** -> keep in ONE agent; splitting causes telephone-game and coordination cost. Trap: "split by role planner/coder/tester/reviewer" sounds modular but wastes tokens.
2. **Subagent lacks info the parent has** -> put it in the Agent tool prompt string. Trap: "subagent inherits parent conversation" (false unless it is a fork). Trap: "give subagent the parent's system prompt" (false).
3. **Subagent returns huge raw output / lost fidelity** -> have it write to external storage and return a reference + short summary. Trap: raising parent context or compaction.
4. **Runaway delegation/cost** -> set depth/concurrency env caps and `max_budget_usd` (SDK) or session `budget` (Managed Agents); add effort-scaling rules in the prompt. Trap: "tell the model not to spawn too many" alone (prompt-only steering is not enforcement; docs say set limits as well).
5. **Need human approval for risky tool calls** -> `canUseTool` / `PreToolUse` hook (SDK) or `always_ask` (Managed Agents). Trap: relying on `allowedTools` list (that pre-approves). Trap: `canUseTool` inside a subagent for `AskUserQuestion` (not available there). Note evaluation order: deny rules, permission mode, allow rules run BEFORE `canUseTool`; use a `PreToolUse` hook to police calls that never reach the callback.
6. **Approval may take hours/days** -> `defer` via PreToolUse hook (process exits, resumes from persisted session) / Managed Agents `idle` + `requires_action`. Trap: keeping the callback pending (works, but process must stay alive).
7. **Worker restarts or runs on another host** -> `SessionStore` (S3/Redis/Postgres) + resume from matching cwd, or pass captured results into a fresh session. Trap: assuming session files are cluster-shared; assuming sessions snapshot the filesystem (they don't; use file checkpointing/git).
8. **Rewind bad file edits** -> file checkpointing, but it will not undo Bash `sed -i` or subagent edits -> use git. Trap: "rewindFiles also rewinds the conversation" (false).
9. **Multi-session project that keeps declaring "done" early or loses its place** -> initializer + coding-agent pattern with JSON feature list, progress file, git commits, e2e verification before `passes: true`.
10. **Model upgrade mid-project** -> don't rely on thinking blocks/transcript as sole state; persist decisions in memory/progress files; pin agent versions; roll out new versions via new sessions (rainbow-style) not in-place mutation. [INTERP + DOC for pinning/rainbow]
11. **Context near limit, long conversation, flow matters** -> compaction (server-side, preferred). **Mostly bloated old tool results (search/file reads)** -> context editing `clear_tool_uses` with `exclude_tools` and `clear_at_least`. **Must retain facts across compaction/clear** -> memory tool. Trap: custom `instructions` on compaction "add to" the default prompt (they REPLACE it). Trap: trigger of 20,000 for compaction (minimum 50,000).
12. **Context clearing causes cost spike** -> each clear invalidates cached prefix; raise `clear_at_least`, don't clear every turn; keep thinking blocks if cache hits matter.
13. **Need to change instructions mid-conversation without paying cache miss** -> append a system-role message (supported models; not Sonnet 5) or `inline-tools` addition. Trap: editing `system` or tool definitions (invalidates cache from that level down). Trap: "start a new conversation" (loses cached context).
14. **50+ tools, MCP aggregators, selection accuracy dropping** -> tool search with `defer_loading`, keep 3-5 hot tools loaded, consistent name prefixes, descriptive keywords. Trap: deferring ALL tools (400 error); dropping definitions from the `tools` array (still required); `cache_control` on deferred tool (400); using tool search for <10 small tools (not worth it); tool search not available in Managed Agents per its page.
15. **Choose workflow vs agent** -> fixed, known steps and need predictability -> workflow (chaining/routing/parallelization); unknown number of steps -> agent. Evolve with data: if agent traces show stable repetitive paths and cost/latency pain, harden into workflow; if workflow keeps failing on long-tail inputs, add agentic fallback. Trap: "always use a framework for production" (docs warn about obscured prompts); "multi-agent is always higher quality" (quality up on breadth tasks, 3-15x tokens).
16. **Harness choice** -> Managed Agents for long-running/async work with minimal infra; Agent SDK for programmatic control with hooks/sessions; raw Messages API loop for fine-grained control. Trap: Managed Agents for ZDR-bound workloads (not eligible, except self-hosted).
17. **Verifier subagent** -> give concrete criteria, include negative tests, mandatory language; otherwise "early victory".

## (d) Self-check questions

1. Q: What is the only channel from parent to a fresh (non-fork) SDK subagent? A: The Agent tool's prompt string (plus its own prompt/CLAUDE.md/tools).
2. Q: Default `trigger` for tool-result clearing, and why use `clear_at_least`? A: 100,000 input tokens; clearing invalidates the cache, so each clear must free enough tokens to justify it.
3. Q: Minimum and default `trigger` for `compact_20260112`? A: Minimum 50,000; default 150,000 input tokens.
4. Q: Does the memory tool run on Anthropic servers? A: No, it is client-side; your handler executes the six commands on `/memories` and must block path traversal.
5. Q: How do you add an instruction mid-conversation without invalidating the cache (non-Sonnet-5 supported models)? A: Append a `role: "system"` message to `messages` instead of editing `system`.
6. Q: Which tool-search field keeps a tool out of context, and what must remain non-deferred? A: `defer_loading: true`; at least one tool (not the search tool itself) must stay non-deferred.
7. Q: Session pauses for an `always_ask` tool in Managed Agents; what do you receive and send? A: `session.status_idle` with `requires_action` + `event_ids`; send `user.tool_confirmation` with allow/deny.
8. Q: What does SDK file checkpointing NOT undo? A: Bash-command file changes and subagent edits (and the conversation itself).

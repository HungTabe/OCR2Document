# DOMAIN 5: Evaluation Engineering and Quality Assurance (12%)

## 5A. Key concepts by blueprint skill

### Skill 1: Evaluation System Design (offline)

Vocabulary [official, Anthropic "Demystifying evals for AI agents"]:
- **Task** (test case) = one test with inputs and success criteria. **Trial** = one attempt at a task (outputs vary, so run several). **Outcome** = the final state in the environment (e.g. does the reservation actually exist in the DB), which can differ from what the agent claims. **Transcript** = full record of a trial (trace/trajectory).
- Grader types: code-based (fast, cheap, reproducible, but brittle), model-based (flexible, non-deterministic, needs calibration), human (gold standard, slow/expensive, used mainly to calibrate model graders).
- **Capability evals** start at a low pass rate ("what can this agent do well?"). **Regression evals** should sit near 100%; a drop signals breakage. High-pass capability evals graduate into the regression suite.
- **Saturation**: agent passes all solvable tasks, so no room to measure improvement; small score changes hide real capability gains.
- Good design: balanced sets (test where a behavior should AND should not occur), isolated trials from a clean environment (shared state causes correlated failures), grade outcomes not rigid tool-call paths, allow partial credit, read transcripts to check failures are "fair" (grader bug vs agent bug).
- Eval-driven development: build evals for planned capabilities before the agent can do them.

Success criteria and eval design [official, "Define success criteria and build evaluations"]:
- Criteria must be specific, measurable, achievable, relevant. Common dimensions: task fidelity, consistency, relevance/coherence, tone, privacy preservation, context utilization, latency, price. Most use cases are multidimensional.
- Eval principles: be task-specific (mirror real distribution, include edge cases: irrelevant/nonexistent input, overly long input, harmful input, ambiguous cases); automate when possible; prioritize volume over quality ("more questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals").
- Grading examples: exact match (classification), cosine similarity (consistency across paraphrases), ROUGE-L (summaries), LLM Likert (tone), LLM binary (e.g. PHI detection). Page recommends the LLM grader be a different model from the one that generated the output.

Concepts the blueprint names that the docs I read do NOT define in detail (treat as [interp]):
- **Golden set**: curated, human-verified inputs with reference outputs/labels; version-controlled; stratified by task type, difficulty, tenant, language; includes edge cases and known past failures.
- **Regression suite**: a subset that must not degrade; every production incident becomes a new case.
- **Behavioral checks**: assertions on properties (refusal when it should, format validity, no PII leakage, tool-call policy) rather than exact text.
- **CI/CD eval gate**: pipeline step that runs the suite on every change to prompt/model/tool/retrieval config and blocks merge/deploy if thresholds fail.
- **Release criteria**: explicit, pre-registered thresholds (e.g. overall score no worse than baseline within a confidence interval; zero regressions on critical/safety slices; latency and cost budgets; per-slice floors). Because outputs are non-deterministic, use multiple trials and compare with variance in mind.
- **Retrieval metrics**: context precision (share of retrieved chunks that are relevant), context recall (share of needed evidence retrieved), **groundedness/faithfulness** (claims in the answer supported by retrieved context; citations verify). Evaluate retrieval and generation separately to localize failure.
- **Suite validity over time**: *contamination* (eval items leak into prompts, few-shot examples, fine-tuning/optimization data, or are tuned against), *saturation* (above), *coverage gaps* (production inputs drift away from what the suite represents). Mitigations: held-out/rotating items, refresh from sampled production traffic, track slice coverage, retire solved tasks into regression set, add harder capability tasks.

### Skill 2: LLM-as-Judge Engineering

[official] Anthropic: "LLM-as-judge graders should be closely calibrated with human experts"; give the judge an "Unknown" option to reduce hallucinated verdicts; model-based graders are non-deterministic and need calibration against human judgment; use a different model from the generator (develop-tests page).

[3rd] Zheng et al. 2023 "Judging LLM-as-a-Judge" (arXiv 2306.05685) examined position, verbosity, and self-enhancement bias plus limited reasoning ability. Newer preprints (2026, not verified by me against primary PDFs) report that chance-corrected agreement (Cohen's kappa) is materially lower than raw exact-match agreement, and that bias magnitudes vary by judge and rubric. Takeaway: always measure these on YOUR judge and YOUR data.

Engineering practice [interp, standard methodology; not stated verbatim in the Anthropic pages I read]:
- **Calibration**: build a human-labeled set (ideally multiple annotators), run the judge, compute agreement. Prefer chance-corrected metrics (Cohen's kappa for 2 raters; Krippendorff's alpha/Fleiss for more) over raw % agreement, especially with imbalanced labels (high raw agreement can coexist with low kappa). Also look at per-class precision/recall of the judge against human labels, not just overall.
- **Inter-rater reliability among humans** sets the ceiling: if humans disagree (low kappa), fix the rubric before blaming the judge.
- **Rubric design**: narrow, one criterion per judge call, explicit anchors per score level, binary or small scales preferred over fine-grained scales, ask for reasoning before the verdict, include an "Unknown/insufficient info" option, give reference answers where possible.
- **Bias checks**: *position bias* (swap order of A/B in pairwise and require consistency or average), *verbosity/length bias* (check score vs length correlation, control length), *self-preference* (judge favors its own family's outputs; use a different model or panel), style bias.
- **Judge drift**: judge model version changes (or silent updates) shift scores. Pin the judge model version, keep a frozen human-labeled anchor set, re-run calibration whenever the judge model, rubric, or judged model changes, and never compare scores across judge versions without re-baselining.

### Skill 3: Online Quality Measurement

[official, Anthropic "Demystifying evals"]: automated evals are reproducible but can create false confidence if they don't match real usage; production monitoring shows real behavior and ground truth but is reactive (problems reach users first); A/B testing measures real user outcomes and controls for confounds but is slow and needs substantial traffic. "Swiss Cheese" model: combine layers because no single layer catches everything. Develop-tests page lists implicit user feedback (task completion rates), A/B vs baseline, and % of edge cases handled without errors as quantitative methods.

[interp] Techniques:
- **Live-traffic sampling**: sample a fixed percentage (stratified by tenant/intent, oversample low-confidence, long-tail, negative-feedback, and high-risk traffic), run automated judges asynchronously (not in the request path), human-review a smaller slice, respect privacy/retention.
- **A/B testing**: randomize by user/session, define primary metric and guardrail metrics (latency, cost, safety) up front, run to adequate power, watch novelty effects; use shadow mode (run candidate on live inputs without serving) before exposing users.
- **Feedback loops**: thumbs, edits, regenerations, escalations to humans, task completion; implicit signals are biased (only vocal users) so calibrate against sampled labels. Failures flow back into the golden/regression set.
- **Metric by task type**: extraction = exact/field-level F1, schema validity; generation = rubric-based LLM/human grading, tone/factuality (n-gram metrics like ROUGE are weak proxies); agentic = outcome/state-based success, plus pass@k / pass^k, cost and steps per task, tool-error rate; retrieval-grounded = context precision/recall, groundedness/citation accuracy, abstention correctness.
- **pass@k vs pass^k** [official]: pass@k = probability of at least one success in k attempts (fits "one success is enough" like code generation with verification). pass^k = probability all k trials succeed (fits customer-facing agents needing consistency); it falls as k rises. If pass rate per trial is p and trials independent, pass^k = p^k [interp: arithmetic; independence rarely holds exactly].

## 5C. Decision rules and traps

- Prompt change looks better on 5 hand-picked examples -> run the full golden set plus regression suite in CI with an eval gate, because anecdotes miss regressions and variance. Trap: "ship, monitor and roll back if complaints."
- Regression suite score drops 3 points after model upgrade -> investigate by slice and transcripts (grader bug vs real regression) before blocking or approving. Trap: averaging hides critical-slice failure.
- Suite pass rate is 98% and flat across candidates -> saturated; add harder/fresh tasks from production, graduate old ones to regression. Trap: "the model is perfect."
- Eval items were used as few-shot examples or tuned against -> contamination; build a held-out set. Trap: adding more of the same items.
- Production users ask things the suite never covers -> coverage gap; sample live traffic, cluster, add cases. Trap: increasing suite size randomly.
- Customer-facing agent must behave consistently -> report pass^k, not pass@k. Pass@k is for "one success suffices." Trap: choosing pass@k because it looks higher.
- Judge agrees 90% with humans but labels are 90% "pass" -> compute kappa/per-class metrics; raw agreement is inflated by imbalance.
- Pairwise judge prefers whichever answer is first or longer -> swap order and average/require consistency; control length; try rubric-based absolute scoring. Trap: just switching to a bigger judge without measuring bias.
- Judge model version updated, scores jump -> judge drift; re-run calibration on frozen human-labeled anchor set, pin judge versions, re-baseline. Trap: comparing new-judge scores with last month's.
- Judge and generator are same model family and scores seem inflated -> self-preference; use a different model/panel and validate with humans.
- RAG answers wrong -> separate retrieval metrics (context precision/recall) from groundedness of generation; fix the stage that failed. Trap: tuning the prompt when recall is the problem.
- Need to validate a change on live users -> shadow mode / canary then A/B with guardrail metrics; offline eval alone can give false confidence [official].
- Extraction task -> code-based exact/field-level grading; do not use an LLM judge where deterministic grading works (cheaper, reproducible).
- Agent task -> grade final outcome/state, not exact tool-call sequence (brittle).
- Multi-select tip: correct answers usually combine layers (offline gate + online sampling + human calibration), not one method.

## 5D. Self-check (Domain 5)

1. Q: Which metric for an agent that must succeed every time across 5 attempts? A: pass^k (k=5), not pass@k.
2. Q: A regression suite should sit near what pass rate? A: Near 100%; a drop signals breakage.
3. Q: Name three suite-validity threats. A: Contamination, saturation, coverage gaps.
4. Q: Why prefer Cohen's kappa to raw agreement when calibrating a judge? A: It corrects for chance agreement, which is high with imbalanced labels.
5. Q: How do you detect position bias in a pairwise judge? A: Swap A/B order and check verdict consistency.
6. Q: Judge model gets a new version; what do you do before trusting scores? A: Re-run calibration against the frozen human-labeled set and re-baseline.
7. Q: Why is offline eval alone insufficient? A: It can create false confidence if it doesn't match real usage; add production monitoring and A/B (Swiss Cheese).
8. Q: RAG quality dropped; which two metric families separate causes? A: Retrieval (context precision/recall) vs generation (groundedness).

# DOMAIN 6: Cost and Latency Optimization at Scale (8%)

## 6A. Key concepts by blueprint skill

### Skill 1: Cost Architecture at Scale

**Cost modeling and forecasting** [interp built on official price table]: cost per request = (uncached input x base) + (cache writes x 1.25 or 2x base) + (cache reads x read multiplier) + (output incl. thinking tokens x output price). Output costs 5x input on most current models (e.g. Sonnet 5.5 $2 in / $10 out; Opus 5.5 $4 / $20; Haiku 5.5 $0.10 / $0.50 for prompts up to 100k). Forecast from token histograms by request type/tenant (not averages), cache hit rate, batch share, retry rate, and growth. Use the Usage and Cost API to ground the model in real data. Note: Claude 4.7+ tokenizer produces ~30% more tokens for the same text (official pricing page), so migrating models can raise cost even at the same per-token price.

**Model routing and cascades** [official concept: routing workflow; details interp]: classify request difficulty/type and send easy/high-volume traffic to a smaller model (Haiku-class), hard cases to a bigger one. A *cascade* tries a cheap model first and escalates on low confidence/verification failure. Route by measured eval results per slice, not by gut feel; include the cost of escalations and the eval cost of the router. Effort is a second axis: same model at lower effort. Haiku 5.5 is positioned for "high-volume, latency-sensitive tasks such as classification, extraction, and routing."

**Caching strategy and diagnostics** (see facts). Key mental model: cache order is tools -> system -> messages; a prefix must be byte-identical up to the breakpoint; a change at level N invalidates N and everything after it.

**Batch vs realtime economics**: batch = 50% off input and output; most batches finish within 1 hour, max 24 hours; unsuitable for interactive paths. Stacks with caching discounts, but cache hits in batch are best-effort.

**Per-tenant budget enforcement** [official building blocks + interp design]: Anthropic gives org-level monthly spend caps, org/workspace spend limits and rate limits (workspace limits protect other workspaces), per-workspace attribution in the Usage and Cost API, `anthropic-workspace-id` response header. Per-end-customer (tenant) budgets inside your app are NOT a built-in API feature that I verified; you implement them in your gateway: meter usage from response `usage` fields, keep per-tenant counters, enforce soft (alert, downgrade model/effort, lower max_tokens) and hard limits (reject/queue) before sending requests. Map tenants to workspaces only if the number of tenants is small (workspace count practicality `[unverified]`).

### Skill 2: Latency Engineering

- **TTFT vs total latency** [official reduce-latency page]: TTFT = time from prompt sent to first token; matters when streaming for perceived responsiveness. Total latency depends on output length x output speed plus TTFT.
- **Streaming** improves perceived responsiveness; does not reduce total generation time [interp, implied].
- **Reduce output tokens**: concise prompt, ask for shorter responses (sentence/paragraph limits are more effective than word counts), `max_tokens` as a hard (blunt) cap that can truncate mid-sentence. Thinking tokens count toward `max_tokens` and are billed as output.
- **Choose a faster model**: docs name Claude Haiku 5.5 for speed-critical apps.
- **Effort** (`output_config.effort`): levels low/medium/high/xhigh/max; affects all output tokens including text, tool calls, and thinking; lower effort -> fewer, terser tool calls. Defaults: high on most models; medium on Opus 5.5 and Haiku 5.5.
- **Fast mode** (`speed: "fast"`): same model, up to 2.5x higher output tokens/second at premium price; gains are in OTPS, not TTFT.
- **Parallel tool use**: Claude can emit several `tool_use` blocks in one turn; you decide whether to execute concurrently. Independent read-only calls are safe to parallelize; side-effecting/ordered calls may need sequential execution.
- **Cache checkpointing** (blueprint phrase): place breakpoints at stable prefix boundaries so long shared context is read from cache (lower latency and cost). Pre-warming with `max_tokens: 0` exists (see batch/extended-thinking pages) `[details of pre-warming section not read]`.
- **Extended thinking budget** (legacy manual mode): `budget_tokens` min 1,024, must be < `max_tokens` (except interleaved), a target not a cap; higher budget = more latency; for budgets above 32k use batch to avoid timeouts. On Claude 4.7 and later, `type: "enabled"` returns 400; use adaptive thinking + effort.

## 6C. Decision rules and traps

- Large static prefix (system prompt/tools/documents) reused many times within minutes -> prompt caching with breakpoint on last stable block, because cache reads cost 0.1x (0.05x/0.025x on some models). Trap: breakpoint after a timestamp or per-user text; no cache will ever hit.
- Prefix is reused but with gaps >5 minutes (e.g. bursts every 10-30 min) -> 1-hour TTL (2x write) when expected reads before expiry justify it. Break-even [interp arithmetic, default 0.1x read]: 5m write costs 1.25x and saves 0.9x per hit; 1h write costs 2x. A 1h cache pays off when it avoids repeated 5m rewrites. Trap: using 1h for one-shot prompts (pure extra cost).
- Cache hit rate suddenly drops to 0 -> use cache diagnostics (`cache_miss_reason`) and check usage fields; typical causes: timestamp in system prompt, reordered/non-deterministically serialized tools, edited history, model/effort/thinking/speed changes, prompt under minimum length, TTL expiry. Trap: "increase TTL" before diagnosing.
- Parallel cold requests all show cache writes, no reads -> send the first request, wait until its response starts, then fan out.
- Nightly evals, bulk classification, back-fills, no user waiting -> Message Batches API (50% off). Trap: using batch for interactive chat or with fast mode (not available together); expecting guaranteed <1h completion (up to 24h).
- Batch with shared long context -> identical `cache_control` blocks + 1-hour TTL; cache hits are best-effort.
- 70% of traffic is simple FAQ/classification -> route to Haiku-class (optionally low effort), escalate hard/low-confidence cases; validate with per-slice evals. Trap: routing by guess, or using the largest model everywhere "for safety."
- Latency target is TTFT -> streaming, smaller/faster model, shorter prompt, cache the prefix, lower effort. Fast mode will NOT help TTFT (OTPS only). Trap: choosing fast mode for a TTFT problem.
- Latency target is total time on long outputs -> reduce output tokens (concise instructions, sentence/paragraph limits, structured output), lower effort, fast mode (accept ~2x price on Opus 5.5), parallelize independent tool calls, split work into parallel subtasks.
- Agent is slow due to many sequential tool calls -> parallel tool use for independent, read-only calls; keep results in one user message. Trap: parallelizing calls with side effects or ordering dependencies.
- Need cost control across tenants -> meter per-tenant tokens from `usage`, enforce soft then hard budgets in your gateway; use workspaces/spend limits for coarse isolation; use Usage and Cost API for attribution/forecast. Trap: relying on org-level spend cap (it pauses everyone with 429, no retry-after).
- Rate limit pressure (ITPM) -> raise cache hit rate (cache reads don't count toward ITPM). Trap: only requesting tier increase.
- Setting a very low `max_tokens` to save cost on a thinking model -> truncation (thinking counts toward `max_tokens`). Trap.
- Changing effort/thinking config per turn in a cached long conversation -> breaks cache; hold constant or use per-message effort on supported models.
- Migrating to a newer model "at the same price per token" -> re-forecast: tokenizer produces ~30% more tokens on 4.7+ [official]; also re-run evals.

## 6D. Self-check (Domain 6)

1. Q: Cache write multipliers for 5-minute and 1-hour TTL? A: 1.25x and 2x base input.
2. Q: Cache read multiplier? A: 0.1x by default; 0.05x on Opus 5.5/Sonnet 5.5; 0.025x on Fable/Mythos 5.1 and 5.2.
3. Q: What does a Batch API request cost and how long does it take? A: 50% off input and output; most finish within 1 hour, hard expiry at 24 hours.
4. Q: Which tool tells you why a cache miss occurred? A: Cache diagnostics (`diagnostics.previous_message_id` -> `cache_miss_reason`).
5. Q: Does fast mode reduce TTFT? A: No, it raises output tokens/second (up to 2.5x) at premium price.
6. Q: Which changes invalidate the cache's messages section? A: Thinking parameters, `output_config.effort`, `tool_choice`, images (and anything earlier in the prefix).
7. Q: Do cache-read tokens count toward ITPM limits? A: No; only `input_tokens` and `cache_creation_input_tokens` do.
8. Q: Where do you set `disable_parallel_tool_use`? A: Inside the `tool_choice` object, not top level.

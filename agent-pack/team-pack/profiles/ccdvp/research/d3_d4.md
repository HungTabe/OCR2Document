# DOMAIN 3: Observability and Production Monitoring (12%)

## 3.1 Telemetry and Instrumentation

### (a) Key concepts

- **Three layers of telemetry exist for Claude systems** and the exam likely tests choosing the right one:
  1. *Response-level data you already have*: the `usage` object, `stop_reason`, and the `request-id` header. Cheapest; log these on every call.
  2. *OpenTelemetry traces/metrics/events* from (a) Claude Code / Agent SDK (the CLI emits them), (b) the Anthropic SDK + Claude API "OpenTelemetry tracing" (beta), (c) your own app spans.
  3. *Admin-side usage/cost reporting* (Usage and Cost API / Analytics API): organization-wide, authoritative for billing, delayed.
- **Distributed traces for an agent loop**: one root span per user prompt/interaction; child spans per model request and per tool call; subagents nest under the parent's tool span so the whole delegation chain is one trace. This is what lets you answer "which step of the loop failed or was slow."
- **Token and cost metrics**: counters split by token type (input, output, cache read, cache creation) and attributed by model, agent, skill, tool. Cache-performance diagnostics rely on the cache read/creation split.
- **Grounding and reasoning traceability**: to debug a wrong answer you need retrieved chunk IDs/sources, the tool inputs/outputs, and the model's stop reason, joined by a stable ID (`request_id`, `tool_use_id`, conversation/session id). Capturing the full prompt/response is the strongest debugging aid but conflicts with privacy.
- **Structured log events**: one event per API request, error, tool result, refusal, carrying join keys (`request_id`, `prompt.id`, `tool_use_id`).
- **Content-capture under privacy constraints (ZDR)**: structural telemetry (timings, token counts, model, status, IDs) is safe by default; content (prompts, responses, tool I/O) is opt-in and must go only to an approved store. Design = metadata always on, content gated/sampled/short-retention.

### (b) Concrete facts (each with source)

**Response fields and request IDs**
- Every API response carries a `request-id` header (e.g. `req_018...`); the same value appears as `request_id` in error bodies. Include it in support tickets. Python/TS SDKs expose `_request_id` on response objects. [DOC] https://platform.claude.com/docs/en/api/errors
- Error body shape: `{"type":"error","error":{"type":...,"message":...},"request_id":...}`. [DOC] same URL.
- Error types: 400 `invalid_request_error`; 401 `authentication_error`; 402 `billing_error`; 403 `permission_error`; 404 `not_found_error`; 409 `conflict_error`; 413 `request_too_large`; 429 `rate_limit_error`; 500 `api_error`; 504 `timeout_error`; 529 `overloaded_error`. Spend-limit hits return 400 (Claude Code workspace limits may return 429); a tier spend-cap 429 has no `retry-after` and keeps failing. [DOC] same URL.
- SDK auto-retries transient failures (connection errors, rate limits, 5xx) with exponential backoff, 2 retries by default, honoring `retry-after`; configurable via `max_retries`. [DOC] same URL.
- In streaming, an error can occur *after* a 200 response; standard HTTP error handling does not apply (mid-stream error events). [DOC] same URL.
- Long requests: use streaming or Batch API, especially >10 minutes; SDK validates non-streaming requests are not expected to exceed 10 minutes. [DOC] same URL.
- On Claude Platform on AWS there are two request IDs: `x-amzn-requestid` (primary, for CloudTrail) and Anthropic `request-id` (for Anthropic support). [DOC] same URL.
- Other useful response headers via raw-response accessors: `anthropic-organization-id`, `anthropic-workspace-id`. [DOC] same URL.

**Usage fields and cache diagnostics**
- `usage` fields: `input_tokens` (uncached input, i.e. only tokens after the last cache breakpoint), `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`; `cache_creation` breaks writes into `ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens` (sum equals `cache_creation_input_tokens`). [DOC] https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- **Total input = `cache_read_input_tokens + cache_creation_input_tokens + input_tokens`**. [DOC] same URL.
- If both cache creation and cache read are 0, the prompt was not cached, usually because it is below the model's minimum cacheable length (examples: 512 / 1,024 / 2,048 / 4,096 tokens depending on model); no error is returned. [DOC] same URL.
- 5-minute cache write = 1.25x base input price; 1-hour (`"ttl": "1h"`) = 2x; hits refresh the 5-minute lifetime. [DOC] same URL.
- Cache-miss checklist: min length, identical prefix, breakpoint on a stable block (timestamps/per-request content change the hash), consistent `tool_choice`/images/thinking config/`output_config.effort`, stable JSON key order in `tool_use`, stay within TTL, do not fire parallel requests before the first response begins. [DOC] same URL.
- In OTel spans from the API, `gen_ai.usage.input_tokens` already includes cache read and write tokens, so do not add the cache attributes again. [DOC] https://platform.claude.com/docs/en/manage-claude/opentelemetry

**Claude Code / Agent SDK OpenTelemetry**
- Enable: `CLAUDE_CODE_ENABLE_TELEMETRY=1` plus exporters: `OTEL_METRICS_EXPORTER`, `OTEL_LOGS_EXPORTER` (otlp/console/none; metrics also prometheus), `OTEL_TRACES_EXPORTER` (beta; also needs `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`). Default export intervals: metrics 60 s, logs 5 s, traces 5 s. [DOC] https://code.claude.com/docs/en/monitoring-usage
- Metrics: `claude_code.session.count`, `claude_code.cost.usage` (USD), `claude_code.token.usage` with `type` = input/output/cacheRead/cacheCreation, `claude_code.lines_of_code.count`, `claude_code.commit.count`, `claude_code.pull_request.count`, `claude_code.code_edit_tool.decision`, `claude_code.active_time.total`. [DOC] same URL.
- Events (via the logs exporter): `claude_code.user_prompt`, `assistant_response`, `tool_result`, `api_request` (model, cost_usd, duration_ms, input/output/cache_read/cache_creation tokens, `request_id`), `api_error` (status_code, attempt), **`api_refusal`** (model, request_id, category), `tool_decision`, `api_request_body`/`api_response_body`. [DOC] same URL.
- Correlation attributes: `prompt.id` links all events for one prompt; `request_id`, `client_request_id`, `tool_use_id`, `message.uuid` are join keys. [DOC] same URL.
- Trace span hierarchy: `claude_code.interaction` (root per prompt) -> `claude_code.llm_request` (has `ttft_ms`, token counts, `stop_reason`, `error_class`, `attempt`), `claude_code.tool` -> `tool.blocked_on_user`, `tool.execution`; subagent spans nest under the Agent tool span; `claude_code.hook` only with detailed beta tracing. [DOC] same URL and https://code.claude.com/docs/en/agent-sdk/observability
- Trace-context propagation: SDK/`-p` sessions read inbound `TRACEPARENT`; Bash subprocesses inherit it; `CLAUDE_CODE_PROPAGATE_TRACEPARENT=1` for proxies. Interactive sessions ignore inbound `TRACEPARENT`. [DOC] same URLs.
- The Agent SDK produces no telemetry of its own: it runs the CLI as a child process which exports directly to the collector. In TypeScript `options.env` replaces the inherited env (spread `process.env`); in Python it is merged. Do not use the `console` exporter in the SDK (stdout is the message channel). Export failures are silent unless `CLAUDE_CODE_OTEL_DIAG_STDERR=1`. Short-lived processes can lose buffered telemetry, so lower export intervals. [DOC] https://code.claude.com/docs/en/agent-sdk/observability
- Tag telemetry with `OTEL_SERVICE_NAME` (default `claude-code`) and `OTEL_RESOURCE_ATTRIBUTES` (e.g. `enduser.id`, `tenant.id`, percent-encoded) to attribute actions to end users. [DOC] same URL.
- Cardinality knobs: `OTEL_METRICS_INCLUDE_SESSION_ID` (default true), `..._VERSION` (false), `..._ACCOUNT_UUID` (true). [DOC] https://code.claude.com/docs/en/monitoring-usage
- Managed settings: OTLP config belongs in managed settings; a repo's `.claude/settings.json` cannot enable telemetry or content capture (it can only disable a signal). [DOC] same URL.

**Privacy gates (Claude Code / Agent SDK), all default OFF**
- `OTEL_LOG_USER_PROMPTS=1` (prompt text); `OTEL_LOG_ASSISTANT_RESPONSES`; `OTEL_LOG_TOOL_DETAILS=1` (commands, file paths, tool inputs, real agent/skill/MCP names on metrics); `OTEL_LOG_TOOL_CONTENT=1` (tool output span event, needs tracing, truncated at 60 KB via `CLAUDE_CODE_OTEL_CONTENT_MAX_LENGTH`); `OTEL_LOG_RAW_API_BODIES=1` or `file:<dir>` (full request/response JSON incl. whole conversation, implies consent to all other gates). [DOC] https://code.claude.com/docs/en/monitoring-usage and https://code.claude.com/docs/en/agent-sdk/observability
- `user.id` is a random anonymous ID, not derived from the account. [DOC] https://code.claude.com/docs/en/monitoring-usage

**Claude API / SDK OpenTelemetry tracing (beta)**
- Two sources: *SDK tracing* (code, no permission needed, covers SDK clients, client-side tools) and *API tracing* (a "destination" added in Claude Console, needs Admin, covers any client, each model run, server tools, Managed Agents turns). Both together link into one trace. [DOC] https://platform.claude.com/docs/en/manage-claude/opentelemetry
- Uses GenAI semantic-conventions attributes. Spans include `anthropic.messages.create` (SDK = CLIENT kind, API = SERVER kind), `anthropic.model_request`, `anthropic.messages.tool_runner`, `anthropic.custom_tool_use`, `anthropic.session.turn`. [DOC] same URL.
- **Content modes**: `metadata_only` (default: IDs, timing, status, token counts) vs `content` (full prompts and responses in `gen_ai.system_instructions`, `gen_ai.input.messages`, `gen_ai.output.messages`). Per-span content limit 0.75 MB default; truncated spans set `anthropic.content.truncated=true`. [DOC] same URL.
- **ZDR interplay**: with zero data retention you can still use Full content for Messages API requests; the API holds exported content only in memory until delivered to your destination. Managed Agents are not ZDR-eligible. HIPAA/FERPA/K-12-restricted orgs export metadata only from destinations regardless of content mode (SDK spans unaffected). The *destination platform* then stores content under its own retention. [DOC] same URL and https://platform.claude.com/docs/en/manage-claude/api-and-data-retention
- Counting tokens from spans: sum only one source per request (SDK spans or API spans, not both), either `anthropic.messages.create` or `anthropic.model_request` on the API side, not both; dedupe retried deliveries by trace ID + span ID. Span export is best-effort and not a complete usage record; for authoritative per-key usage use the Usage and Cost Analytics API grouped by `api_key_id`. A caller can drop spans by turning off the sampled flag in `traceparent`. [DOC] same URL.
- Group Managed Agents spans by `gen_ai.conversation.id` (one thread) or `anthropic.session.id` (whole session across traces). [DOC] same URL.

**ZDR facts**
- ZDR: Anthropic does not store prompts/responses at rest after the API response is returned; enabled per organization via the account team. [DOC] https://platform.claude.com/docs/en/manage-claude/api-and-data-retention
- Features marked "No" for ZDR (e.g. Batch API, Files API, code execution) are not blocked; using one steps outside ZDR for that data. [DOC] same URL.
- Claude Code with API keys is ZDR-covered, but if Claude Code metrics logging is enabled, productivity/usage statistics are exempt from ZDR and may be retained. [DOC] same URL.
- Orgs with ZDR cannot call the API from a browser (CORS rejected with 401); call from your backend. [DOC] same URL and https://platform.claude.com/docs/en/api/errors
- Some models (Fable/Mythos families per the doc) require 30-day retention and are unavailable under ZDR unless authorized; a workspace can opt in to 30-day retention while other workspaces stay ZDR. [DOC] same URL.
- Even under ZDR, data flagged by trust-and-safety systems may be retained up to 2 years. [DOC] same URL.
- Consequence for logging [EXP]: Anthropic cannot replay your prompt for you, so *your own* telemetry (request-id, usage, metadata, optionally content in your approved store) is the only debugging record. Plan content capture explicitly.

**OpenTelemetry GenAI semantic conventions** (status: Development, moved to repo `semantic-conventions-genai`)
- Metrics (all histograms): `gen_ai.client.operation.duration` (s), `gen_ai.server.request.duration`, `gen_ai.server.time_to_first_token` (s; queue + prefill; important for streaming), `gen_ai.server.time_per_output_token`, `gen_ai.invoke_agent.duration`, `gen_ai.invoke_agent.inference_calls`, `gen_ai.invoke_agent.tool_calls`. [OTEL] https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-metrics.md
- Agent spans: operations `create_agent`, `invoke_agent` (LLM drives control flow), `invoke_workflow` (app defines control flow), `plan`, plus `execute_tool` for tools; span name `{operation} {agent.name}`; `gen_ai.agent.name` must be low cardinality; `error.type` set on failure. [OTEL] https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-agent-spans.md (the `execute_tool` and `gen_ai.client.token.usage` names come from a search summary of [3P] blogs plus the doc's pointer, treat their exact attribute tables as [unverified])
- Opt-in content attributes (`gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, `gen_ai.tool.definitions`) are off by default and warned as likely to contain PII. Input tokens include cached tokens. [OTEL] same agent-spans URL.
- Stability caveat: conventions are Development; attribute names may change. [OTEL] same URL; [3P] https://dev.to/azena-ai/opentelemetrys-genai-semantic-conventions-are-not-stable-yet-heres-what-actually-shipped-in-2026-3mke (search snippet only).

**Cost/usage admin APIs** (see also 3.2)
- Usage report: `/v1/organizations/usage_report/messages`; cost report: `/v1/organizations/cost_report`. Need an Admin API key (`sk-ant-admin01-...`) or equivalent; workspace API keys do not work; unavailable to claude.ai Team plan or individual Console accounts. This is the *legacy* API; for new integrations Anthropic recommends the Usage and Cost Analytics API. [DOC] https://platform.claude.com/docs/en/manage-claude/usage-cost-api

### (c) Decision rules and traps

- Need one number to prove a cost spike came from lost caching → compare `cache_read_input_tokens` vs `cache_creation_input_tokens` per request (or `claude_code.token.usage` by `type`) because `input_tokens` alone excludes cached tokens. Trap: summing only `input_tokens` and concluding input shrank.
- Need to correlate a user complaint to a specific API call → log and search by `request-id`; also give it to support. Trap: relying on timestamps or on `message.id` only.
- Agent run is slow and you must find which step → distributed trace with per-model-request and per-tool spans (`ttft_ms`, `tool.execution duration`). Trap: aggregate latency dashboards cannot localize a step.
- Org has ZDR and wants debuggability → capture metadata-only spans by default, enable content mode only to an approved destination with short retention and access control, or sample content. Trap: "disable all telemetry because of ZDR" (loses debuggability; ZDR concerns Anthropic's storage, not your own logs). Trap: assuming ZDR means your observability vendor does not retain content (it does, under its own policy).
- Enabling Claude Code telemetry across a company → set in managed settings, not repo settings (repo files cannot enable it). Trap: documenting it as a per-repo setting.
- Counting tokens from spans → one source only, no double counting of cache attributes; use Usage API for authoritative billing. Trap: adding cache tokens on top of `gen_ai.usage.input_tokens`.
- Metrics cardinality blow-up → do not put session/user/request IDs as metric labels; keep them on traces/logs [EXP]; `gen_ai.agent.name` must be low-cardinality [OTEL].
- Streaming service → measure TTFT separately from total latency; an HTTP 200 can still end in a mid-stream error, so success-by-status-code is wrong. [DOC]/[EXP]
- Browser-side Claude call under ZDR → fails with CORS 401; move to backend. [DOC]
- Distractor: "the Agent SDK emits its own spans" (false; it is the CLI). Distractor: "`console` exporter is fine for local SDK debugging" (false; breaks the stdout channel).

### (d) Self-check (Q / A)

1. Q: Which three usage fields add up to total input tokens? A: `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`.
2. Q: Both cache fields are 0 and no error appeared; likely cause? A: Prompt below the model's minimum cacheable length (or no breakpoint).
3. Q: Which header ties a bad response to Anthropic support? A: `request-id` (same as `request_id` in error body).
4. Q: What are the two OTel content modes for Claude API tracing and the default? A: `metadata_only` (default) and `content`.
5. Q: Under ZDR, can you export full prompt content to your OTel backend? A: Yes for Messages API; Anthropic holds it in memory only until delivery, but your backend's retention then applies.
6. Q: Who actually emits OTel data in the Agent SDK? A: The Claude Code CLI child process.
7. Q: Why must OTLP settings for Claude Code fleets be in managed settings? A: Repo-level settings cannot enable telemetry, destinations, or content capture.
8. Q: Why are exported spans not a billing source of truth? A: Delivery is best-effort and callers can unsample spans; use the Usage and Cost API.

## 3.2 Production Monitoring and Alerting

### (a) Key concepts

- **SLIs for an LLM-backed service** [EXP unless noted]: availability/error rate split by class (4xx client, 429 rate limit, 5xx/529 provider, mid-stream errors, refusals, timeouts, tool failures, schema-invalid output); latency as TTFT *and* total duration (and p50/p95/p99, per model and per request type); throughput/saturation (429 rate, queue depth); cost per request/per task; and **quality** (task success rate from sampled evals/LLM-judge/user feedback, groundedness, refusal rate, stop_reason distribution, tool-call count per task). Quality SLIs are the ones infrastructure monitoring misses.
- **SLOs** express the SLI target over a window (e.g. 99% of interactive requests have TTFT < X). The numeric values are business choices [EXP]. Use error budgets to decide when to freeze changes [EXP].
- **Alerting design**: alert on symptoms that users feel (SLO burn rate), not every cause; separate pages (urgent) from tickets; per-error-class thresholds so a 529 spike (provider side) is not mixed with 400 spikes (your bug); cost alerts on rate-of-change as well as absolute budget.
- **Drift and regression detection**: (1) *after a model update or prompt change* run the same fixed canary/golden set and compare quality, refusal rate, token usage, latency to baseline; (2) segment production metrics by `model` and by release version; (3) watch behavioral signals such as `stop_reason` mix, output length, tool-call count, refusal rate, and retry rate; (4) anomalous usage = unusual tokens per key/workspace/user (possible leaked key, loop, or abuse).
- **Dashboards**: separate views for reliability (error classes, latency), cost (tokens by type, cache hit ratio, cost by workspace/model), quality (eval scores, feedback), and agent behavior (loop length, tool failure rate).

### (b) Concrete facts

- Usage API granularity: `1m` (default 60/max 1,440 buckets), `1h` (24/168), `1d` (7/31). Filters/groupings: API key, workspace, model, service tier, context window, data residency (`inference_geo`), `speed` (standard/fast). Server tool usage tracked. [DOC] https://platform.claude.com/docs/en/manage-claude/usage-cost-api
- Cost API: USD, daily (`1d`) granularity only; group by `workspace_id` and `description` (description yields parsed `model`, `inference_geo`); Priority Tier costs are *not* in the cost endpoint (use usage endpoint, `service_tier=priority`); code execution cost appears in cost endpoint only. [DOC] same URL.
- Freshness: legacy page says data typically appears within about 5 minutes; the OTel page says usage in the Analytics API typically appears within 4 hours. Treat the two as differing claims; do not build real-time alerting on admin APIs [EXP]. [DOC] https://platform.claude.com/docs/en/manage-claude/usage-cost-api and https://platform.claude.com/docs/en/manage-claude/opentelemetry
- Polling: once per minute sustained; cache results for dashboards. [DOC] usage-cost-api URL.
- Playground usage has `api_key_id = null`; default workspace has `workspace_id = null`. [DOC] same URL.
- Partner dashboards listed by Anthropic: CloudZero, Datadog, Grafana Cloud, Harness, Honeycomb, Tempo, Vantage. [DOC] same URL.
- Recommended new API: Usage and Cost Analytics API (more grouping/filtering; Claude Code per-user cost via `products[]=claude_code&group_by[]=actor`). [DOC] same URL.
- Rate limit 429: includes ramp limits (sharp traffic increase can 429 even under limits). [DOC] https://platform.claude.com/docs/en/api/errors
- Stop reasons to track as behavioral signals: `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, `refusal`, `model_context_window_exceeded`. A rising `max_tokens` share = truncation risk; rising `refusal` = classifier/prompt issue. [DOC] https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons (interpretation of what a rise means is [EXP])
- Claude Code trace spans expose `ttft_ms`, `first_content_ms`, `duration_ms`, `error_class`, `stop_reason` for latency/error SLIs. [DOC] https://code.claude.com/docs/en/monitoring-usage
- OTel server metric `gen_ai.server.time_to_first_token` covers queue + prefill. [OTEL] metrics URL above.
- A rising tool-calls-per-run median is an early sign of an agent loop. [3P] https://www.dash0.com/knowledge/opentelemetry-genai-semantic-conventions-explained (search-result summary only; treat as [unverified] detail)

### (c) Decision rules and traps

- Latency SLO for a chat UI → TTFT as primary SLI with total duration secondary, because streaming makes perceived latency TTFT-driven [EXP]. Trap: only average total latency (hides tail and TTFT).
- Quality dropped after switching model versions but error rate and latency are flat → quality SLI/eval-based canary on a fixed golden set, compare by `model` dimension. Trap: "HTTP success rate is 100% so no regression".
- Spend suddenly doubled → group usage by `api_key_id`/workspace/model, then check cache read vs creation tokens and `service_tier`/`speed`; suspect leaked key, loop, cache invalidation (prompt prefix change), or fast mode. Trap: assuming price change.
- Alert on 529/5xx vs 400: 529/5xx = provider-side, retry with backoff/fallback, maybe incident comms; 400 spike = your deploy (e.g. malformed request, unsupported parameter for a model); 429 = capacity/limits (check ramp limits, spend caps). Distinct runbooks per class. [DOC for semantics; runbook is EXP]
- Need near-real-time cost guard → compute from per-request `usage` in your own pipeline; use Usage API for reconciliation. Trap: polling admin API every few seconds (supported once per minute; data delay).
- Anomaly = cost per task up while request count flat → look at tool-call count, context growth, lost caching. [EXP]
- Distractor: setting alerts on average tokens only; use percentiles and per-segment.
- Distractor: using a workspace API key with the Admin usage endpoints (does not work).
- Distractor: expecting Priority Tier in the cost endpoint (not included).

### (d) Self-check

1. Q: Which key type is required for usage/cost endpoints? A: Admin API key (or other admin credential), not a workspace key.
2. Q: Smallest cost-report granularity? A: Daily (`1d`).
3. Q: Where do you find Priority Tier consumption? A: Usage endpoint filtered by `service_tier=priority`.
4. Q: Flat error rate but users complain of worse answers; what SLI was missing? A: A quality SLI (eval/judge/feedback), run by model/version.
5. Q: Which stop_reason rise signals truncation? A: `max_tokens` (and `model_context_window_exceeded`).
6. Q: Why monitor TTFT separately? A: Streaming UX depends on first token; total latency hides it.
7. Q: First dimension to group by when hunting a leaked key? A: `api_key_id` (Analytics/Usage API).
8. Q: Which request-count-flat cost-spike causes should you check? A: Cache misses, context growth, more tool calls/loop, model or speed change.

## 3.3 Trace Analysis at Scale

### (a) Key concepts [mostly EXP; the docs supply the data fields]

- With high trace volume you cannot read traces one by one. Use: **sampling** (what to keep), **aggregation** (metrics/histograms derived from all traces before sampling), **failure-cohort analysis** (group failing traces by shared attributes and compare to the healthy population).
- Sampling strategies: head-based (decide at trace start; cheap but may miss rare failures); tail-based (decide after completion; keep all errors, refusals, slow, expensive, low-score traces plus a random baseline); stratified sampling by model/route/tenant so rare cohorts are not drowned; always-keep rules for flagged outcomes. Keep a uniform random sample as unbiased baseline so rates can be reweighted.
- Aggregation: compute error rate, refusal rate, token and cost distributions, tool failure rate per tool, loop length distribution from *all* spans (metrics), not just sampled traces.
- Failure-cohort analysis: slice failures by model version, prompt version, tool, tenant, input length bucket, language, retrieval source, cache hit/miss, time window; look for an attribute whose failure rate is far above base rate (lift). Quantify: how many requests, what share of failures, what cost. This reveals systemic issues invisible in any single trace (e.g. failures only when context > N tokens, or only for tenant X, or only after deploy Y).
- Rollups need low-cardinality dimensions; high-cardinality IDs belong in trace attributes for drill-down.

### (b) Concrete facts

- Trace attributes available to slice on in Claude Code: `model`, `speed`, `effort`, `query_source`, `attempt`, `status_code`, `error_class`, `stop_reason`, `cache_read_tokens`, `bash_command_class`, `tool_name`, `duration_ms`. [DOC] https://code.claude.com/docs/en/monitoring-usage
- Metrics carry `agent.name`, `skill.name`, `plugin.name`, `mcp_server.name`, `mcp_tool.name` (real names only with `OTEL_LOG_TOOL_DETAILS=1`). [DOC] same URL.
- Resource attributes (`service.version`, `deployment.environment`, `enduser.id`, `tenant.id`) let you cohort by release/tenant. [DOC] https://code.claude.com/docs/en/agent-sdk/observability
- Spans for failed/aborted requests may omit token counts. [DOC] same URL. So token aggregates from spans can under-count failures.
- API span export is best-effort; sampling flag in `traceparent` can exclude requests; dedupe by trace ID + span ID. [DOC] https://platform.claude.com/docs/en/manage-claude/opentelemetry
- Managed Agents: multi-thread sessions; group by `anthropic.session.id`. [DOC] same URL.
- Claude Code traces are beta: span names/attributes may change. [DOC] https://code.claude.com/docs/en/agent-sdk/observability
- Event `event.sequence` is a per-process counter: sort by `event.timestamp` first. [DOC] https://code.claude.com/docs/en/monitoring-usage
- Do not store trace content longer than needed: content truncation (60 KB Claude Code default; 0.75 MB per span for API tracing). [DOC] both URLs above.

### (c) Decision rules and traps

- 1% of requests fail in a way users hate but no single trace looks abnormal → cohort analysis on failure flag vs attributes (model, prompt version, input size, tool, tenant); compute lift. Trap: reading more individual traces or raising log level.
- Head sampling at 1% and the failure is 0.1% rare → switch to tail-based sampling that keeps all errors/refusals/low-quality outcomes plus a random baseline. Trap: "increase retention" (does not recover traces never sampled).
- Need correct overall error rate when error traces are oversampled → compute rates from pre-sampling metrics or reweight with sampling probability. Trap: reporting error share from a biased sample.
- Cost attribution by team → aggregated metrics with low-cardinality `team`/`workspace` attribute; per-user detail in logs/traces. Trap: user ID as metric label.
- Distractor: "store 100% of full content to be safe" (privacy, ZDR intent, cost, size limits).
- Distractor: summing both SDK and API spans for tokens (double count).

### (d) Self-check

1. Q: Why does head sampling fail for rare failures? A: The keep/drop decision is made before the outcome is known.
2. Q: What does tail-based sampling keep? A: Errors, refusals, slow/expensive/low-score traces plus a random baseline.
3. Q: What is a failure cohort? A: A subset of failing traces defined by shared attributes, compared with healthy baseline to find over-represented attributes.
4. Q: Why keep a random baseline sample? A: To estimate true rates and compute lift.
5. Q: Which dimensions belong on metrics vs traces? A: Low-cardinality on metrics; IDs on traces/logs.
6. Q: Can spans alone give complete token totals? A: No (best-effort delivery, unsampled calls, failed requests may lack tokens); reconcile with Usage API.
7. Q: Which span grouping reconstructs a multi-thread Managed Agents session? A: `anthropic.session.id`.
8. Q: What is a good early sign of a looping agent in metrics? A: Rising tool-calls (or inference calls) per run.

# DOMAIN 4: Advanced Debugging and Incident Response (10%)

## 4.1 Complex Failure Diagnosis

### (a) Key concepts

- **Four origin buckets** (blueprint): *model output* (wrong reasoning, hallucination, format drift, refusal), *agent harness* (prompt assembly, context management/truncation, loop control, retry logic, tool-result handling, orchestration), *tools* (bad schema, wrong/failed results, timeouts, permission denials), *data* (stale/missing/corrupt knowledge, retrieval returning wrong chunks, bad inputs). Diagnosis = gather evidence (trace, request/response, tool I/O, retrieved context) and isolate by controlled replay: hold three constant, vary one.
- **Isolation techniques** [EXP]: replay the exact captured request against the model (same model, temperature settings as applicable); swap in a recorded tool result to test the harness; run the tool directly with the captured args; inspect retrieved chunks before generation; compare passing vs failing traces to find the first divergence step.
- **Multi-turn failures**: errors emerge from accumulated context (earlier wrong tool result carried forward, context truncation/compaction dropping a constraint, thinking blocks mishandled). Find the *first* bad turn, not the last. Check what the harness actually sent each turn.
- **Multi-agent failures**: handoff loses information, subagent returns summary lacking evidence, parallel agents conflict, error swallowed by orchestrator. Use the trace tree to see which subagent span failed or diverged. Subagent spans nest under parent tool span. [DOC]
- **Non-deterministic failures**: same input, different outcome. Capture the failing request, run N repeats to estimate failure rate (a rate, not a bug yes/no), then look for variance sources (sampling, tool latency/ordering, retrieval ties, race conditions between parallel tool calls, cache state). Fix with measurable pass-rate target over many runs rather than one passing run. [EXP]
- **Refusals as a failure class**: returned as HTTP 200 with `stop_reason: "refusal"` (not an error), from safety classifiers; `stop_details.category` (cyber, bio, frontier_llm, general_harms, ...; may be null); a harness that only checks HTTP status or only reads `content[0].text` treats it as an empty/odd answer. Diagnose by checking `stop_reason`, category, input features that trigger the classifier (benign work can trigger it), and whether a fallback model handles it.
- **Retrieval-grounding failures**: answer unsupported or contradicted by sources. Diagnose by stage: (1) was the right document in the corpus? (2) chunking/embedding retrieved it? (3) reranking kept it? (4) was it in the prompt (context size/ordering)? (5) did the model use it faithfully / cite it / admit uncertainty? Check retrieved chunks first: if the right evidence was never retrieved, it is a data/retrieval problem, not a model problem.

### (b) Concrete facts

- Refusal is a normal HTTP 200, not an error; check `stop_reason` in the success path; `stop_details` is `null` for other stop reasons; `category` and `explanation` are `null` when the refusal does not map to a named category. [DOC] https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons and https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback
- Categories listed: `cyber`, `bio`, `frontier_llm`, `general_harms` (and a `reasoning_extraction` category named in the billing section). Benign work can trigger cyber/bio/frontier_llm/general_harms. [DOC] refusals-and-fallback URL.
- Handling: retry on a fallback model; server-side fallback via `fallbacks: "default"` with beta header `server-side-fallback-2026-07-01` (beta), or name up to three own fallback models; a `fallback` content block marks where one model's output hands to the next; if the fallback model is rate-limited/overloaded the refusal is returned with `stop_details.recommended_model`. Haiku 5.5 has no server-side fallback (client-side retry needed). [DOC] refusals-and-fallback and handling-stop-reasons URLs.
- Billing of refusals: refusals before any output are billed only for `bio`, `frontier_llm`, `reasoning_extraction` categories (as of Sept 2026 per doc); mid-stream refusals bill input plus streamed output; fallback credit compensates the cache miss. [DOC] refusals-and-fallback URL.
- Claude Code emits `claude_code.api_refusal` events with `category`, so refusals can be counted per model/query_source. [DOC] https://code.claude.com/docs/en/monitoring-usage
- Other stop reasons that look like "wrong answer" but are harness-visible: `max_tokens` (truncated; raise or continue), `pause_turn` (server-tool loop hit iteration limit, default 10; send assistant content back unchanged), `model_context_window_exceeded` (truncated). [DOC] handling-stop-reasons URL.
- Common 400 harness bugs: assistant prefill rejected on Claude 4.6+ models; modifying `thinking`/`redacted_thinking` blocks in the latest assistant message (must be passed back exactly as received, including empty ones); `thinking.type.enabled` rejected on Claude 4.7+ (use adaptive + `output_config.effort`); forced `tool_choice` any/tool not supported on some models; thinking block "bound to a different conversation" when history was edited (keep history append-only). [DOC] https://platform.claude.com/docs/en/api/errors
- Thinking-config specifics: Sonnet 5.5 cannot use `thinking: disabled` (use `between_tools`); `between_tools` with `xhigh`/`max` effort or changing per-message effort returns 400. [DOC] same URL.
- Mid-stream errors can follow a 200; non-streaming long requests risk network drops; `request_too_large` 413 limits: Messages 128 MB, Batch 256 MB, Files 500 MB. [DOC] same URL.
- Caching harness bugs: timestamps in cached block, changed `tool_choice`, unstable JSON key order, parallel requests before first response. [DOC] https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- Claude Code tool span error info: `tool.execution` `success`, `error_class`; `tool_result` event `error_type`, `success`, `duration_ms`; `tool_decision` reject sources (config, hook, user_reject). [DOC] https://code.claude.com/docs/en/monitoring-usage
- Reasoning visibility: `thinking` display `summarized` lets you read reasoning summaries; thinking content in OTel raw bodies is redacted. [DOC] refusals-and-fallback URL and https://code.claude.com/docs/en/agent-sdk/observability

### (c) Decision rules and traps

- Wrong final answer; retrieved chunks do not contain the fact → retrieval/data fix (chunking, query rewrite, hybrid search, reranking, corpus coverage), not prompt tweaks or bigger model. Trap: blaming the model.
- Retrieved chunks contain the fact, but the answer ignores/contradicts them → generation/grounding problem: instruct citation and uncertainty, check chunk placement/length, evaluate faithfulness. Trap: re-indexing.
- Tool returned error/garbage and agent proceeded confidently → harness/tool problem (error handling, tool schema, structured error returned to model). Replay with recorded tool result to prove. Trap: "model hallucinated".
- Same prompt works in playground, fails in production → diff the assembled request (system prompt, tools, history, truncation, parameters) captured via request body/`request-id`. Trap: tuning the prompt before diffing the request.
- Intermittent failure → measure failure rate across repeated runs and by cohort; do not close on a single success. Trap: single-run verification of a non-deterministic fix.
- Multi-turn drift late in conversation → locate first bad turn; examine context truncation/compaction and carried-over bad tool results. Trap: debugging the last turn only.
- Empty or odd output with HTTP 200 → check `stop_reason`: `refusal` (inspect category; consider fallback model, adjust request; do not blindly retry same model repeatedly), `max_tokens` (truncation), `pause_turn` (continue). Trap: treating it as a transient error and retrying with backoff (refusal is deterministic-ish and not a 5xx).
- Refusal rate rose after a prompt/model change → compare `api_refusal` category distribution before/after; check if new content triggers a classifier; add refusal handling and a regression case. [EXP]
- Multi-agent failure → find first span where output diverges from expectation; check handoff payload completeness; check whether orchestrator swallowed a subagent error. Trap: examining only the final agent.
- Suddenly many 400s after model migration → check unsupported params (prefill, thinking mode, forced tool_choice) before anything else. [DOC]
- Distractor: "increase temperature/ add retries" for systematic errors.
- Distractor: "switch to a larger model" without isolating the origin.

### (d) Self-check

1. Q: HTTP status of a classifier refusal? A: 200 with `stop_reason: "refusal"`.
2. Q: Which field names the refusal policy area? A: `stop_details.category` (may be null).
3. Q: Retrieved docs lack the answer; which origin bucket? A: Data/retrieval.
4. Q: First step for "works in playground, fails in prod"? A: Diff the actual assembled request, replay it.
5. Q: How to verify a fix for a 5% intermittent failure? A: Repeat many runs and compare pass rate/cohort rates, not one success.
6. Q: What does `pause_turn` require from harness? A: Send assistant content back unchanged to continue.
7. Q: Which edit to a thinking block causes a 400? A: Any modification of `thinking`/`redacted_thinking` blocks in the latest assistant message.
8. Q: In a multi-turn failure, which turn do you find? A: The first bad turn, not the last.

## 4.2 Incident Response and Learning Loops

### (a) Key concepts

- **Triage**: confirm and size impact (who, how many, which model/route/tenant, since when), classify type (provider outage vs your deploy vs quality regression vs cost runaway vs safety/privacy incident), set severity, assign roles (incident commander, comms, ops). Check provider status first for 5xx/529 patterns [EXP]; check "what changed" (deploy, prompt, model version, config, data/index update).
- **Mitigation before root cause**: stop the bleeding with the least risky reversible action. Options: rollback the last change (prompt/model/config/index), fail over to a fallback model, degrade gracefully (cached/simple answers, disable a feature or tool), rate-limit or shed load, kill switch for runaway agent loops/cost, pause a bad batch job. Pin model versions so you control when behavior changes [EXP].
- **Rollback**: works best when prompts, tool definitions, model IDs, retrieval config are versioned artifacts that can be reverted independently and fast; verify recovery with the same SLIs and a canary eval.
- **Communication**: internal status cadence, customer-facing status with honest scope and ETA, support talking points; for provider-side outages, include request IDs for support. For data/privacy incidents, involve security/legal.
- **Learning loop**: (1) blameless postmortem: impact, timeline, mitigation, root and contributing causes, follow-ups; (2) convert incident to a **regression eval case(s)** (the failing input(s) plus expected behavior, added to the golden/regression suite and CI gate); (3) add **monitoring coverage** (the SLI/alert that would have detected it sooner, or fix a detection gap); (4) fix systemic causes (runbook, guardrail, rollout process like canary/staged rollout).

### (b) Concrete facts

- Blameless postmortem principles: focus on systems not people; written record of incident and impact, mitigation actions, root causes, follow-up actions; triggers include user-visible degradation over a threshold, data loss, on-call intervention such as rollback or traffic rerouting, long resolution time, and monitoring failure (found manually); action items are the point; share in a repository; criteria defined in advance. [3P-but-canonical] Google SRE book https://sre.google/sre-book/postmortem-culture/ (not an Anthropic doc; used as supplement)
- Error semantics for triage: 529 `overloaded_error` can occur from high traffic across all users; 500 `api_error` retry with exponential backoff then contact support with request ID; 429 includes tier spend cap (no `retry-after`, persists until access resumes) and ramp limits; 402 `billing_error`; 400 spend limit reached. [DOC] https://platform.claude.com/docs/en/api/errors
- SDK retry behavior: 2 retries default with backoff, honors `retry-after`. [DOC] same URL. Beware retry amplification under overload [EXP].
- Refusal fallback: server-side `fallbacks` can route declined requests to another model automatically; if the fallback is overloaded the refusal returns, so size fallback capacity. [DOC] https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback
- Spend control: org/workspace spend limit you set returns 400 when reached; useful as a cost-runaway circuit breaker (also an incident cause). [DOC] https://platform.claude.com/docs/en/api/errors
- Data for postmortem: `request-id`, OTel traces (`session.id`, `prompt.id`), usage/cost reports by key/workspace/model. [DOC] URLs from D3.
- Claude Code/Agent SDK events can serve as an audit trail (tool_decision, tool_result, mcp_server_connection) forwarded to SIEM for security incidents. [DOC] https://code.claude.com/docs/en/agent-sdk/observability
- Leaked key investigation: group Usage and Cost Analytics API by `api_key_id` (counts requests without spans). [DOC] https://platform.claude.com/docs/en/manage-claude/opentelemetry
- Anthropic-side status/incident feeds: [unverified] (status page was not fetched).

### (c) Decision rules and traps

- Quality regression right after a deploy that changed prompt/model → roll back that single change first (fast, reversible), then investigate with a replay and cohort analysis. Trap: debugging live while users are impacted, or rolling forward with an unverified fix.
- Provider-side 529/5xx spike, nothing changed on your side → backoff/retry with jitter, fail over to an alternate model/region/provider path, degrade gracefully, notify users; open support ticket with request IDs. Trap: removing retries or hammering retries (amplifies), or rolling back your own unrelated code.
- Cost runaway from agent loop → kill switch / iteration cap, then workspace spend limit; identify via tool-call counts and tokens per task. Trap: waiting for next day's cost report (admin data delayed).
- Many refusals after enabling a new feature/content → add refusal handling and fallback, compare categories; mitigation = fallback model or request rephrase, not retries on same model.
- Model deprecation/update changed behavior → run canary eval against pinned old vs new model; roll back to pinned version while fixing prompts. [EXP]
- Postmortem output should include: a regression eval added to the CI gate, a new alert/SLI or dashboard if detection was late, a runbook update, and an owner/date for each action item. Trap: action items that say "be more careful" or name a person as the cause.
- Communication: state impact, scope, what you are doing, next update time; do not speculate on root cause publicly. [EXP]
- Incident fixed but no regression test added → incident will recur; the exam's "best answer" typically includes closing the loop (eval + monitor + postmortem), not just the hotfix.
- Distractor: "restart the service" with no evidence; "ask the model to be more careful in the prompt" as the only fix; "disable observability to reduce load".
- Distractor: root-cause-first before mitigation when users are actively impacted.

### (d) Self-check

1. Q: First priority during an active user-impacting regression? A: Mitigate (rollback/failover/degrade), then diagnose.
2. Q: Best first mitigation for a regression right after a prompt change? A: Roll back the prompt change.
3. Q: What three artifacts should every LLM incident produce beyond the fix? A: Regression eval case(s), monitoring/alert coverage, blameless postmortem with owned action items.
4. Q: What does "blameless" mean? A: Focus on systemic contributing causes, assume good faith, no individual blame.
5. Q: What does a 429 with no `retry-after` suggest? A: Tier spend-cap reached; retrying will keep failing until access resumes.
6. Q: Why can server-side refusal fallback fail under load? A: If the fallback model is rate-limited/overloaded the refusal is returned.
7. Q: Which identifier do you send Anthropic support? A: The `request-id`.
8. Q: Which data source is best to find a leaked key's usage? A: Usage and Cost Analytics API grouped by `api_key_id`.

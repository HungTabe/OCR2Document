## (a) Key concepts by skill

### Skill 1 — Runtime Guardrail Systems

**Core idea [INTERP, consistent with all sources]:** guardrails are layers. Prompt-level instructions shape what the model tries to do; deterministic controls outside the model decide what can actually happen. For irreversible or high-impact actions, the decisive layer must be enforced by code, OS, or downstream systems, not by the model's judgment.

Layers to know:
1. **Input filtering / harmlessness screen** — a small, cheap model (docs use Claude Haiku 5.5) classifies user input with structured output (a boolean) before the main model sees it. A `stop_reason: "refusal"` from the screening model itself must be treated as a "harmful" verdict.
2. **Output / tool-result filtering** — the same screening pattern applied to tool outputs before they are returned as `tool_result`; if `injection_suspected` is true, return an error or stripped summary instead of raw content.
3. **PII redaction** — redact before data reaches the model, logs, or traces. [INTERP] The docs I read do not describe a specific PII redactor product; treat redaction as an application-layer pre/post-processing step (regex/NER/DLP service) placed outside the model. Least privilege ("don't give Claude access to secrets it doesn't need") is the documented complement.
4. **Hook-based policy enforcement** — Claude Code / Agent SDK `PreToolUse` hooks run custom code before a tool call and can deny it. Exit code 2 (or JSON `permissionDecision: "deny"`) blocks.
5. **Permission rules (deny → ask → allow)** — enforced by the harness, not the model.
6. **Sandboxing** — OS-level filesystem and network isolation of Bash (Seatbelt on macOS, bubblewrap on Linux/WSL2), with a proxy domain allowlist. Grants tool/web access without exposing production systems and holds regardless of what the model chose to run.
7. **Approval gates (human in the loop)** — `ask` rules, `canUseTool` callback, `always_ask` tools, MCP `requiresUserInteraction`.
8. **Refusal handling and safety fallbacks** — refusals are HTTP 200 with `stop_reason: "refusal"`, not errors; retry via fallback model (server-side `fallbacks: "default"` beta, SDK middleware, or manual retry), discard partial output, and distinguish from rate limits (429) and context stops.
9. **Deterministic enforcement for irreversible actions** — deny rules, hooks, sandbox, scoped credentials, DB roles, branch protection. Not prompt text.
10. **False-positive / false-negative tuning** — [INTERP] screens trade over-blocking (FP: legitimate users blocked, e.g., benign security work hitting `cyber` refusal) against under-blocking (FN: attacks pass). Tune with labeled test sets (benign + adversarial), choose threshold by action risk: strict for irreversible actions, lenient + logging for low-risk reads. Anthropic itself notes benign work can trigger refusal categories.

### Skill 2 — Threat Defense and Adversarial Testing for Agentic Systems

- **Two threat models** [DOC]: (i) jailbreak / direct prompt injection (user is adversary); (ii) indirect prompt injection (user trusted, third-party content — web pages, emails, documents, tool results — carries adversarial instructions).
- **Attack surface of tool-using agents** [INTERP + DOC for pieces]: untrusted content ingestion, tool/MCP server trust, tool descriptions, memory/persisted context (memory poisoning), outbound channels (HTTP fetch, email, image URLs, git push, DNS) used for exfiltration, over-broad credentials, unsafe autonomy.
- **Lethal trifecta** [3P, Simon Willison]: private data + untrusted content + ability to communicate externally. Remove at least one leg; cutting the exfiltration path is usually most practical.
- **Defense in depth**: training-level resistance + classifiers + least privilege + sandbox + approval gates + monitoring + red teaming. Anthropic states prompt injection is "far from a solved problem".
- **Secure MCP configuration**: trust only providers you trust or servers you write; managed MCP allowlists; per-client consent for proxies; audience validation (no token passthrough); SSRF protections; scope minimization; sandbox local servers.
- **Red-team exercise design** [INTERP, anchored on DOC "red-team your own agent"]: seed documents/emails/tool outputs with injections; test each trifecta leg; test tool poisoning (malicious tool description/result); test memory persistence; test exfiltration via allowed channels; measure attack success rate before/after each layer; automate as regression eval; include humans (Anthropic reports human red teamers outperform automated ones at novel vectors).
- **Frameworks**: OWASP Top 10 for LLM Applications (2025) and NIST AI RMF + Generative AI Profile (NIST AI 600-1) — see facts.

### Skill 3 — Identity, Secrets, and Audit at Scale

- **Agent identity**: a named non-human identity per workload (Anthropic: service account `svac_...`), separate from human users, so actions are attributable.
- **Workload Identity Federation (WIF)**: workloads exchange a signed JWT from their own IdP (AWS IAM, Google Cloud, GitHub Actions, Kubernetes, SPIFFE, Entra ID, Okta, any OIDC issuer) for a short-lived Anthropic access token. Replaces long-lived `sk-ant-...` keys.
- **Secrets management**: no static secrets in CI/images; credentials injected by the platform; secrets the agent doesn't need are never exposed to it; deny reads on `.env`/secret paths.
- **Least-privilege tool permissioning**: narrow tools, narrow scopes, read-only DB roles, user-scoped OAuth, progressive scope elevation.
- **Audit logging**: log security-relevant actions (tool calls, denials, approvals, scope elevations, auth exchanges) with correlation IDs; distinct identities make logs attributable.

## (b) Concrete facts (each with source URL)

### Hooks, permissions, sandbox (Claude Code / Agent SDK)

1. Hook exit code 0 = success; exit 2 = blocking error that stops the action on events that can block; other codes are non-blocking errors and the action proceeds. [DOC] https://code.claude.com/docs/en/hooks
2. Exit 1 without valid JSON is non-blocking "even though 1 is the conventional Unix failure code. If your hook is meant to enforce a policy, use `exit 2`." [DOC] https://code.claude.com/docs/en/hooks
3. `PreToolUse` supports `hookSpecificOutput.permissionDecision` with values allow/deny/ask/defer plus `permissionDecisionReason`. [DOC] https://code.claude.com/docs/en/hooks
4. A `PreToolUse` call exiting 2 stays blocked even if JSON says `"allow"`. Exit 0 with no output = no decision; the call continues through the normal permission flow ("staying silent doesn't approve it"). [DOC] https://code.claude.com/docs/en/hooks
5. `continue: false` does not block a `PreToolUse` call; to block, also return `permissionDecision: "deny"`. [DOC] https://code.claude.com/docs/en/hooks
6. On hook timeout a `PreToolUse` command hook does not block the tool call unless `onFailure: "block"` is set — "Don't count on a stalled hook to act as a gate." [DOC] https://code.claude.com/docs/en/hooks
7. The hook `if` filter is best-effort: "use the permission system rather than a hook to enforce a hard allow or deny." [DOC] https://code.claude.com/docs/en/hooks
8. `PostToolUse` fires after success; exit 2 shows stderr to Claude but "the tool already ran" (cannot undo). It can add `additionalContext`. [DOC] https://code.claude.com/docs/en/hooks
9. Hook handler types: command, http, mcp_tool, prompt, agent (agent experimental). Matching hooks run in parallel. [DOC] https://code.claude.com/docs/en/hooks (only first ~100k chars of this page were read)
10. Permission rules are evaluated deny → ask → allow; first match decides; a broad deny beats a narrower allow. [DOC] https://code.claude.com/docs/en/permissions
11. "Permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or `CLAUDE.md` shape what Claude tries to do, but they don't change these rules." [DOC] https://code.claude.com/docs/en/permissions
12. A `PreToolUse` hook returning `allow` does not bypass deny or ask rules. A hook exiting 2 stops the call before permission rules are evaluated, even if an allow rule exists. [DOC] https://code.claude.com/docs/en/permissions
13. Agent SDK evaluation order: hooks → deny rules → ask rules → permission mode → allow rules → `canUseTool`. Deny rules apply even in `bypassPermissions` and even when a hook returned allow. [DOC] https://code.claude.com/docs/en/agent-sdk/permissions
14. Auto-approved tools never reach `canUseTool`; to check calls approved by an allow rule, `acceptEdits`, or `bypassPermissions`, use a `PreToolUse` hook. A hook deny applies even in `bypassPermissions`. [DOC] https://code.claude.com/docs/en/agent-sdk/permissions
15. `allowed_tools` does not constrain `bypassPermissions`; use `disallowed_tools` to block specific tools there. A locked-down agent pairs `allowedTools` with `permissionMode: "dontAsk"` (every other call denied). [DOC] https://code.claude.com/docs/en/agent-sdk/permissions
16. A `PreToolUse` `allow` cannot approve recognized critical-path removals such as `rm -rf ~`; the recognizer "can miss some commands". [DOC] https://code.claude.com/docs/en/agent-sdk/permissions
17. Subagents inherit `plan`/`acceptEdits`/`auto`/`bypassPermissions` from the main session; inheriting bypass gives them full autonomous access. [DOC] https://code.claude.com/docs/en/agent-sdk/permissions
18. Bash deny rules match the command "as written"; a deny rule doesn't match the same program by path or inside `sh -c`, so pair with the sandbox network allowlist. For enforcement independent of command text use sandboxing. [DOC] https://code.claude.com/docs/en/permissions and https://code.claude.com/docs/en/security
19. Block file reads with `Read(./.env)`-style deny rules. `.claudeignore` has no effect. Read deny rules for built-in tools are applied best-effort to Grep/Glob. [DOC] https://code.claude.com/docs/en/permissions
20. `permissions.blockWritesOutsideWorkingDirectories` does not limit shell commands, MCP tools, or programs hooks run; use sandboxing. [DOC] https://code.claude.com/docs/en/permissions
21. Sandbox: filesystem writes limited to CWD (+ added dirs, temp); reads default to whole machine except denied dirs (credential files readable by default — protect them). Config files (`.claude/settings*`, hooks, `.mcp.json`, shell rc) are write-protected so a command cannot grant itself permissions. [DOC] https://code.claude.com/docs/en/sandboxing
22. Sandbox network: Linux separate network namespace; macOS Seatbelt blocks all but the proxy; proxy checks hostname against allowed/denied domains; does not inspect TLS by default. Primitives: Seatbelt (macOS), bubblewrap (Linux, WSL2); native Windows runs unsandboxed. [DOC] https://code.claude.com/docs/en/sandboxing
23. "The operating system enforces the sandbox boundary on the running process, so it holds regardless of what the model chose to run." Non-Bash tools (Read, Edit, WebFetch, MCP, hooks) run outside the sandbox. [DOC] https://code.claude.com/docs/en/sandboxing
24. Escape hatch: a failed command may be retried with `dangerouslyDisableSandbox`; disable with `allowUnsandboxedCommands: false` and set `failIfUnavailable`. `excludedCommands` run with full access. Loopback/link-local hostnames (e.g., 169.254.169.254) are refused by the proxy. [DOC] https://code.claude.com/docs/en/sandboxing
25. Auto mode uses a separate classifier model to review actions; explicit ask/deny rules still apply. [DOC] https://code.claude.com/docs/en/security
26. Managed settings enforce org standards; `allowManagedPermissionRulesOnly` makes managed settings the only source of permission rules; `ConfigChange` hooks can audit/block mid-session settings changes; OpenTelemetry metrics for monitoring. [DOC] https://code.claude.com/docs/en/security and https://code.claude.com/docs/en/permissions
27. Cloud sessions: isolated VM, limited network by default, GitHub credentials never enter the VM (proxy attaches them server-side), proxy rejects branch deletions and non-branch pushes, all operations audit-logged. [DOC] https://code.claude.com/docs/en/security
28. Anthropic "does not security-audit or manage any MCP server"; encourages own servers or trusted providers; managed MCP configuration restricts servers org-wide. [DOC] https://code.claude.com/docs/en/security

### Claude API guardrails and refusals

29. Harmlessness screen: lightweight model + structured output boolean; treat `stop_reason: "refusal"` from the screener as harmful verdict. [DOC] https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks
30. For indirect injection: put untrusted content only in `tool_result` blocks (never system/user text); state its source; state an untrusted-content policy in system prompt; JSON-encode untrusted strings; don't place your own instructions inside tool results; apply least privilege, sandbox, narrow permissions; screen tool outputs; red-team before deployment. [DOC] same URL as 29
31. Respond to repeat offenders (throttle/ban); continuous monitoring of outputs for successful injection. [DOC] same URL as 29
32. For computer use / browser use tools, Anthropic runs additional classifiers over screenshots/page text. [DOC] same URL as 29
33. Refusal = HTTP 200 with `stop_reason: "refusal"`, `stop_details.category` (`cyber`, `bio`, `frontier_llm`, `reasoning_extraction`, `general_harms`, or null); `explanation` text is unstable (display, don't parse). [DOC] https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback
34. A refusal can come before output or mid-stream; discard partial output. Billing: pre-output refusals billed for `bio`, `frontier_llm`, `reasoning_extraction`; mid-stream refusals bill input + streamed output. [DOC] same URL as 33
35. `reasoning_extraction` has no recommended fallback model — change the prompt (stop asking for verbatim reasoning in output; use adaptive thinking/summarized thinking blocks). [DOC] same URL as 33
36. Fallback options: server-side `fallbacks: "default"` (beta, header `server-side-fallback-2026-07-01`, Claude API and Google Cloud Anthropic-managed; not on Batches API; not on Haiku 5.5), SDK middleware client-side fallback (any platform), manual retry with fallback credit. [DOC] same URL as 33
37. Error semantics differ: 429 `rate_limit_error`, 529 `overloaded_error`, 5xx retry with backoff; SDK auto-retries twice with exponential backoff. A refusal is not in this error family. [DOC] https://platform.claude.com/docs/en/api/errors
38. Anthropic injection-defense research: layered (RL training, classifiers scanning all untrusted content, red teaming); reported adaptive-attacker success on Opus 4.5 browser-agent test: 8.0% model-only, 1.4% with improved safeguards; "far from a solved problem"; "a 1% attack success rate still represents meaningful risk"; humans outperform automated red teams at novel vectors. [DOC] https://www.anthropic.com/research/prompt-injection-defenses

### Threat frameworks

39. ### MCP security

45. Confused deputy: MCP proxy with static client ID + dynamic client registration + third-party consent cookie + no per-client consent → attacker's code gets issued without user consent. Mitigation: proxy MUST implement per-client consent before third-party flow, exact `redirect_uri` matching, CSRF-protected consent UI, state validation set only after consent, `__Host-` cookies. [DOC] https://modelcontextprotocol.io/specification/draft/basic/security_best_practices
46. Token passthrough is forbidden: MCP servers MUST NOT accept tokens not explicitly issued for the MCP server (audience validation). Risks: control circumvention, broken audit trail/accountability, trust-boundary issues. [DOC] same URL as 45
47. SSRF: malicious server can point OAuth metadata URLs to internal IPs / `169.254.169.254` / localhost / DNS rebinding / redirects. Mitigations: HTTPS, block private/loopback/link-local ranges (use vetted libraries, not hand-rolled parsing), validate each redirect hop, egress proxy (e.g., Smokescreen), pin DNS (TOCTOU). [DOC] same URL as 45
48. Local MCP server compromise: require consent showing the exact command, sandbox with minimal privileges, prefer stdio or restricted IPC/token. [DOC] same URL as 45
49. State handle hijacking: possession of a handle is not authentication; use random handles bound server-side to the authenticated user. (This draft replaces session hijacking; older spec versions describe session IDs.) [DOC] same URL as 45
50. Scope minimization: start with low-risk scopes, step up via `WWW-Authenticate` scope challenges, avoid wildcard/omnibus scopes, log elevation events with correlation IDs. [DOC] same URL as 45
51. OAuth authorization URLs from servers: allow only http/https (http only for loopback), reject `javascript:`/`data:`/`file:`, never open via shell. [DOC] same URL as 45

### Identity, secrets, audit

52. WIF: short-lived OIDC tokens instead of long-lived `sk-ant-...` keys; IdPs: AWS IAM, Google Cloud, GitHub Actions, Kubernetes, SPIFFE, Entra ID, Okta. "There are no static secrets to mint, store in CI, rotate, or leak." [DOC] https://platform.claude.com/docs/en/manage-claude/workload-identity-federation
53. Three Console resources: federation issuer (`fdis_`), service account (`svac_`), federation rule (`fdrl_`). Rule matches on subject prefix / audience / claims / CEL and sets OAuth scope (default `workspace:developer`) and `token_lifetime_seconds` (60–86,400, default 3,600). [DOC] same URL as 52
54. Exchange via `POST /v1/oauth/token` with RFC 7523 jwt-bearer grant; returns `sk-ant-oat01-...` token. Token lifetime = lesser of rule lifetime and 2× remaining IdP JWT lifetime (min 60 s). SDK refreshes advisory at expiry−120 s, mandatory at expiry−30 s. [DOC] same URL as 52
55. JWTs with a `jti` are single-use by default (replay protection; `jti_reused` in auth history); disabling `check_jti` removes replay protection for all rules on that issuer. [DOC] same URL as 52
56. Credential precedence: constructor args → `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_PROFILE` → federation env vars → active profile. A leftover `ANTHROPIC_API_KEY` silently overrides federation; migration = configure WIF in parallel, check with `ant auth status`, unset the key everywhere, delete the key. [DOC] same URL as 52
57. WIF "is not a complete security solution on its own": it is only as strong as the upstream IdP; pair with workload identity binding, conditional access, audit logging. Service accounts make it easier to audit which workload acted. [DOC] same URL as 52
58. Claude Platform on AWS: AWS request ID (`x-amzn-requestid`) is primary and indexed in CloudTrail; Anthropic `request-id` is secondary; requires `aws iam enable-outbound-web-identity-federation` once per AWS account. [DOC] https://platform.claude.com/docs/en/api/errors
59. 401 `authentication_error` = key problem (malformed, revoked, expired); 403 `permission_error` = key lacks permission. [DOC] https://platform.claude.com/docs/en/api/errors
60. Claude Code stores credentials in macOS Keychain when available; Linux file mode 0600. [DOC] https://code.claude.com/docs/en/security

## (c) Decision rules ("when X → choose Y because Z") and traps

**Enforcement location**
- Irreversible action (delete, payment, prod deploy, force-push, send external email) → deterministic control outside the model (deny rule, PreToolUse hook exit 2, sandbox, scoped credential, downstream authorization) because prompt text and model judgment are probabilistic and can be overridden by injection. [INTERP anchored on facts 11, 13, 40]
- Policy must hold even in bypass/auto-approve modes → deny rules or PreToolUse hook (hook deny applies in `bypassPermissions`) because `canUseTool` is skipped for auto-approved calls (facts 13–14).
- Hook meant to enforce → `exit 2` or explicit `deny` JSON, never exit 1, never rely on a timeout/`if` filter (facts 2, 6, 7).
- Need to block `curl`/network egress robustly → sandbox network allowlist, not just a Bash deny rule, because deny rules match text as written (fact 18).
- Prevent > detect when action is irreversible: PostToolUse cannot undo (fact 8); logging/monitoring "do not prevent the issue on their own" (fact 40). Detection + alerting is for reversible/low-risk and as a second layer.

**Untrusted content**
- Agent reads emails/web/docs → deliver as `tool_result`, label source, JSON-encode, state policy, and limit tools (fact 30). Trap: putting retrieved text in system prompt or user turn.
- Agent has private data + untrusted input + outbound channel → remove a leg (cut egress, drop private data, or require approval on outbound) rather than add a "better classifier" because filters are probabilistic (facts 38, 44).
- Classifier-based screens as sole defense → distractor. Layer them; Anthropic itself reports non-zero residual attack success (fact 38).
- Don't put your own instructions in `tool_result`; send them in a following `user` turn (fact 30).

**Refusals**
- `stop_reason: "refusal"` → handle as a distinct class: do not retry the same model with backoff (it is not a transient error), use fallback model/middleware, discard partial output; `reasoning_extraction` → fix the prompt, no fallback (facts 33–37). Trap: treating it like 429/5xx, or like an HTTP error.
- Safety screener returns a refusal → treat as harmful (fact 29). Trap: fail-open.

**Sandbox / approvals**
- Need agent to run code and reach web without exposing production → sandbox with domain allowlist, no prod credentials in the sandbox, `allowUnsandboxedCommands: false`, `failIfUnavailable` (fact 24).
- Headless/unattended agent → `dontAsk` + explicit allowlist (deny by default) rather than `bypassPermissions` (facts 15, 17).
- Approval fatigue → narrow allow rules per command/domain, sandbox auto-allow for contained work, keep approval for irreversible ones. [INTERP + fact on prompt fatigue mitigation in security page]
- Trap: `allowed_tools=["Read"]` with `bypassPermissions` does not restrict anything (fact 15).
- Trap: assuming a PreToolUse `allow` skips prompts or overrides deny (fact 12).

**FP/FN tuning** [INTERP]
- Too many legitimate blocks → measure FP on a benign golden set, narrow the rule or add context; do not disable the guardrail. Attacks slipping through → add adversarial cases to regression eval, add a deterministic layer. Tune strictness by blast radius.

**Frameworks**
- Question names category "agent did damaging action after manipulated output" → OWASP LLM06 Excessive Agency; fix = fewer tools, narrower permissions, human approval. "Model reveals instructions" → LLM07. "Output rendered/executed downstream unsanitized" → LLM05 Improper Output Handling. "Poisoned fine-tuning/RAG data" → LLM04 Data and Model Poisoning. "Retrieval store weaknesses" → LLM08. "Runaway cost/DoS" → LLM10 Unbounded Consumption.
- NIST AI RMF = organizational process (Govern/Map/Measure/Manage); 600-1 = GAI-specific risks and actions. Neither is a technical control; choose them for governance/risk-process questions. [INTERP]

**MCP**
- Server receives a client's token and forwards it downstream → token passthrough violation; fix: validate audience, use separate downstream token (fact 46).
- MCP proxy with static client ID and dynamic registration → per-client consent (fact 45).
- Server-side client fetches OAuth URLs from untrusted MCP servers → SSRF controls + egress proxy (fact 47).
- Token has `files:*`/`admin:*` → scope minimization with step-up (fact 50).
- Third-party/community MCP server → trust review, allowlist via managed MCP, sandbox; Anthropic does not audit them (fact 28).

**Identity**
- CI/Kubernetes/cloud workload using static `ANTHROPIC_API_KEY` → WIF with service account and narrowly scoped federation rule (facts 52–53).
- After enabling WIF, still seeing API key identity → leftover `ANTHROPIC_API_KEY` env var wins (fact 56).
- Replay concerns with JWT → keep `check_jti` on; mint fresh JWT per exchange (fact 55).
- Audit: need attribution → one service account per workload, correlation IDs, audit log of tool calls/denials/scope elevations; trap: shared generic admin key. [INTERP + fact 57]
- Trap: "WIF alone makes it secure" → no; depends on IdP strength (fact 57).

**Common distractors**
- "Add a stronger system prompt" as the fix for a high-risk action.
- "Use a bigger model, it's more resistant" as the only control.
- "Log everything and alert" for irreversible actions.
- "Rotate the static key more often" instead of eliminating it via WIF.
- "Scan only user input" when the threat is indirect injection in tool results.
- "Retry with backoff" on refusals.

## (d) Self-check questions

1. Q: A PreToolUse hook script crashes with exit 1 while enforcing a `rm -rf` block. Does it block? A: No; exit 1 is non-blocking, use exit 2 or a deny JSON.
2. Q: In `bypassPermissions` mode, what still blocks a call? A: Deny rules, ask rules, and hooks (e.g., hook deny); evaluated before the mode check.
3. Q: Which Agent SDK step is skipped for calls approved by an allow rule? A: `canUseTool` — put checks in a PreToolUse hook instead.
4. Q: What is the lethal trifecta and the primary fix? A: Private data + untrusted content + external communication; remove at least one leg (often cut exfiltration).
5. Q: Claude returns `stop_reason: "refusal"` with category `cyber` on a benign security task. Retry-with-backoff or fallback? A: Fallback model (server-side `fallbacks`, middleware, or manual); not a transient error.
6. Q: Where should third-party email content be placed in a Claude API call? A: In a `tool_result` block, labeled and JSON-encoded, with an untrusted-content policy in the system prompt.
7. Q: What does MCP forbid regarding tokens, and why? A: Token passthrough; servers must only accept tokens issued for them (audience validation) to preserve controls and audit trail.
8. Q: A workload migrated to WIF still authenticates with the old key. Why? A: `ANTHROPIC_API_KEY` ranks above federation in credential precedence; unset it and delete the key.
9. Q: Which OWASP LLM 2025 item covers an agent given shell access and a high-privilege identity? A: LLM06 Excessive Agency (functionality, permissions, autonomy).
10. Q: Why is a sandbox stronger than a Bash deny rule for blocking egress? A: The OS enforces it on the process regardless of command text; deny rules match the command as written and miss path/`sh -c` variants.
